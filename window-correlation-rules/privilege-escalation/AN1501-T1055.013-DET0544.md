### **1. Technique Breakdown: T1055.013**

* **What it is:** **Process Injection: Process Doppelgänging**. Adversaries abuse Transactional NTFS (TxF) to create a hollowed process. They create a transaction, overwrite a legitimate executable file (e.g., `svchost.exe`) with a malicious payload, create a memory section from the transacted file, and then *rollback* the transaction. The malicious file never officially touches the disk. They then use undocumented APIs like `NtCreateProcessEx` to create a process from the tainted memory section, and `NtCreateThreadEx` to execute it. This bypasses AV scanners that rely on file-to-disk callbacks.
* **Log Source Requirements:** EDR telemetry (API hooking for TxF functions and undocumented process creation APIs), Sysmon Event ID 1 (Process Creation).
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES (Partial).** Sysmon logs the final process execution (Event ID 1), but lacks visibility into the TxF rollback and native API calls (`NtCreateProcessEx`).
    * **NIDS (Suricata + Zeek): NO.** Completely local filesystem and memory manipulation.

### **2. Custom Sigma Rule**

Because Sysmon cannot see TxF rollbacks natively, this rule relies on detecting the anomalies created by Doppelgänging in **Sysmon Event ID 1 (Process Creation)**: specifically, a process executing with an invalid, missing, or mismatched hash compared to the file on disk.

```yaml
title: Suspicious Process Creation indicating Process Doppelgänging (AN1501)
id: fbbcc3f9-676b-4e6c-a8eb-8b0ab3606f1d
status: experimental
description: Detects anomalies indicative of Process Doppelgänging, such as processes executing with missing file hashes or mismatched image metadata.
author: Krishna Gupta
date: 2026-06-09
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_target:
        Image|endswith:
            - '\svchost.exe'
            - '\explorer.exe'
            - '\lsass.exe'
    selection_anomaly:
        # A missing hash in Sysmon Event ID 1 often indicates the file could not be read from disk 
        # because the transaction was rolled back or locked
        Hashes: '-' 
    selection_anomaly_alt:
        # Or the process image is empty
        Image: ''
    condition: selection_target and (selection_anomaly or selection_anomaly_alt)
fields:
    - Image
    - Hashes
falsepositives:
    - Extreme system load causing Sysmon hashing to time out.
    - Highly specific DRM protections.
level: critical
tags:
    - attack.privilege_escalation
    - attack.defense_evasion
    - attack.t1055.013
    - analytics.an1501
    - detection.det0544
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Sysmon's Limited View**
    * *The Issue:* Relying on a missing `Hashes: '-'` field is highly prone to false positives if the endpoint is under heavy CPU load and Sysmon simply fails to hash the file in time.
    * *The Fix:* Do not rely on Sysmon alone for TxF attacks. EDR solutions must hook kernel callbacks (`ObRegisterCallbacks`) and track the usage of `CreateTransaction`, `CreateFileTransacted`, and `RollbackTransaction` in rapid succession on executable files.

* **Problem 2: Herpaderping Variant**
    * *The Issue:* Process Herpaderping is a similar technique where the attacker writes the payload, maps the file into a section, modifies the file on disk to look benign, and then creates the process from the initial mapped section. This evades TxF monitoring.
    * *The Fix:* Correlate Sysmon Event ID 11 (File Creation) with Sysmon Event ID 1 (Process Creation). If a file is written, heavily modified, and executed within a span of milliseconds, flag it for behavioral review regardless of the APIs used.

* **Problem 3: Valid TxF Usage**
    * *The Issue:* Transactional NTFS was designed for a reason (e.g., safe software updates, database consistency). Overly aggressive hooking of TxF APIs will break legitimate software installations (like Windows Updates).
    * *The Fix:* Baseline TxF usage. Alert only when a TxF rollback is immediately followed by a process creation event `NtCreateProcessEx` using a memory section derived from the transacted file.
