### 1. Technique Breakdown: T1134

* What it is: Access Token Manipulation. Windows uses access tokens to determine the ownership and privileges of a process or thread. Adversaries can duplicate a privileged access token (e.g., from `lsass.exe` or `winlogon.exe` running as `SYSTEM`) using APIs like `DuplicateTokenEx`, and then use `CreateProcessWithTokenW` to spawn a new process under that privileged security context, escalating their privileges without requiring credentials.
* Log Source Requirements: Process creation logs (Sysmon Event ID 1 / Windows Security 4688), Windows Security Event Log (Event ID 4624 - Logon, Event ID 4672 - Special Privileges Assigned).
* Coverage Check:
    * HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 1 logs the `LogonId` and `User`. Correlating the parent user (e.g., standard user) with a child process user (e.g., `SYSTEM`) detects token impersonation.
    * NIDS (Suricata + Zeek): NO. Token manipulation is a core OS-level function occurring entirely in memory.

### 2. Custom Sigma Rule

This rule utilizes Sysmon Event ID 1 (Process Creation) to detect the behavioral outcome of token manipulation: a child process spawning under the `NT AUTHORITY\SYSTEM` context when its direct parent is running under a standard user context.

```yaml
title: Suspicious Privilege Escalation via Token Manipulation (AN0786)
id: fbbcc3f9-676b-4e6c-a8eb-8b0ab3606f1d
status: experimental
description: Detection of suspicious token manipulation chains resulting in a process spawning as SYSTEM from a standard user parent process.
author: Krishna Gupta
date: 2026-06-09
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1
detection:
    selection_child_user:
        User|contains: 'NT AUTHORITY\SYSTEM'
    selection_parent_user:
 # Exclude known SYSTEM parents, looking for standard users
        ParentUser|exclude: 
            - 'NT AUTHORITY\SYSTEM'
            - 'NT AUTHORITY\NETWORK SERVICE'
            - 'NT AUTHORITY\LOCAL SERVICE'
    filter_known_elevators:
 # Whitelist legitimate services that elevate context
        ParentImage|endswith:
            - '\services.exe'
            - '\svchost.exe'
            - '\lsm.exe'
            - '\winlogon.exe'
            - '\User Account Control' # consent.exe
    condition: selection_child_user and selection_parent_user and not filter_known_elevators
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Custom in-house administrative elevation wrappers.
    - Certain third-party software updaters that utilize scheduled tasks inappropriately.
level: critical
tags:
    - attack.privilege-escalation
    - attack.t1134
    - analytic.an0786
    - detection.det0283
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Command Line Obfuscation
  * The Issue: Adversaries can obfuscate command-line arguments using environment variables, caret escapes (^), or base64 encoding, evading simple string matching.
  * The Fix: Implement PowerShell Script Block Logging and utilize regex or script-decoding scripts in the SIEM to check arguments.

* Problem 2: Administrative Activity Noise
  * The Issue: IT administrators legitimately run command-line tools or installers that trigger these rules during system maintenance.
  * The Fix: Establish a baseline of legitimate admin tools, whitelisting specific administrative account names or management servers.

* Problem 3: Masquerading via Renamed Binaries
  * The Issue: Attackers rename native Windows utilities (such as net.exe or cmd.exe) to custom filenames to bypass path-based filters.
  * The Fix: Incorporate Masquerade-resistant criteria, matching on OriginalFileName rather than the static Image path in process creation logs.
