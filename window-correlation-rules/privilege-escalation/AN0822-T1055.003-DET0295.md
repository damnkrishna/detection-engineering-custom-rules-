### **1. Technique Breakdown: T1055.003**

* **What it is:** **Process Injection: Thread Execution Hijacking**. Instead of creating a new thread (like in PE injection), an adversary targets an existing, legitimate thread in a remote process. They suspend the thread (`SuspendThread`), allocate memory and write their payload (`VirtualAllocEx` / `WriteProcessMemory`), modify the thread's instruction pointer (EIP/RIP) using `SetThreadContext` to point to the payload, and finally resume the thread (`ResumeThread`). This evades defenses that trigger purely on `CreateRemoteThread`.
* **Log Source Requirements:** Advanced EDR telemetry (API hooking for `SetThreadContext`), Sysmon Event ID 10 (ProcessAccess).
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES (Partial).** Sysmon logs `ProcessAccess` (Event ID 10) when the handle is opened. However, Sysmon does NOT log `SetThreadContext`.
    * **NIDS (Suricata + Zeek): NO.** Local memory manipulation.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 10 (ProcessAccess)** to detect suspicious access requests targeting critical processes, specifically looking for access masks that imply thread manipulation and context setting, which are prerequisites for Thread Execution Hijacking.

```yaml
title: Suspicious Process Access indicating Thread Hijacking (AN0822)
id: f48b1112-9844-4632-901b-c1284a14f4e8
status: experimental
description: Detects hijacking of an existing thread by monitoring suspicious ProcessAccess requests indicative of thread context manipulation.
author: Krishna Gupta
date: 2026-06-09
logsource:
    category: process_access
    product: windows
    # Relies on Sysmon Event ID 10 collected via Wazuh
detection:
    selection_target:
        TargetImage|endswith:
            - '\explorer.exe'
            - '\svchost.exe'
            - '\winlogon.exe'
    selection_access:
        # Access rights needed to suspend threads and set context
        # THREAD_SUSPEND_RESUME (0x0002) + THREAD_SET_CONTEXT (0x0010)
        GrantedAccess|contains:
            - '0x1F0FFF' # All Access
            - '0x143A'
    filter_known:
        SourceImage|endswith:
            - '\taskmgr.exe'
            - '\MsMpEng.exe'
            - '\csrss.exe'
    condition: selection_target and selection_access and not filter_known
fields:
    - SourceImage
    - TargetImage
    - GrantedAccess
falsepositives:
    - Debugging tools like WinDbg or Process Hacker.
    - EDR agents aggressively scanning process memory.
level: high
tags:
    - attack.privilege_escalation
    - attack.defense_evasion
    - attack.t1055.003
    - analytics.an0822
    - detection.det0295
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Sysmon's Lack of SetThreadContext Logging**
    * *The Issue:* `ProcessAccess` is a very early indicator and highly prone to false positives. To confidently detect Thread Hijacking, you must observe the `SetThreadContext` API modifying the Instruction Pointer (RIP). Sysmon does not log this.
    * *The Fix:* Utilize ETW (Event Tracing for Windows) specifically `Microsoft-Windows-Threat-Intelligence` provider, which logs `SetThreadContext` events. Route this ETW data into your SIEM.

* **Problem 2: Racing the Thread**
    * *The Issue:* The attacker must suspend the thread when it's in a "safe" state. If they alter the context while the thread is deep inside a kernel syscall, the process will likely crash (BSOD or Application Error) upon resumption.
    * *The Fix:* While the attack may fail, the crash itself is an indicator of compromise (IoC). Monitor Windows Application Event ID 1000 (Application Crash) where the faulting module is `ntdll.dll` or `kernelbase.dll` inside `explorer.exe` or `svchost.exe`.

* **Problem 3: Direct Syscalls (SysWhispers)**
    * *The Issue:* Attackers can use direct system calls (e.g., invoking `NtSetContextThread` via an assembly `syscall` instruction) rather than calling the standard `kernel32.dll` API. This completely bypasses user-mode EDR API hooks.
    * *The Fix:* Monitor for anomalies in Call Stack telemetry (if available via EDR). Threads executing entirely from unbacked/anonymous memory without a standard module base are highly suspicious.
