### **1. Technique Breakdown: T1611**

* **What it is:** **Escape to Host**. Adversaries may break out of a container to gain access to the underlying host. This can involve exploiting vulnerabilities in the container runtime, abusing excessive privileges (like `--privileged` in Docker), or mounting host file systems (`/`) inside the container and modifying host configurations to achieve code execution.
* **Log Source Requirements:** Linux Audit logs (auditd) or eBPF-based container security tools, and Kubernetes Audit Logs.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon for Linux or Wazuh agents running on the host node can detect suspicious process execution originating from container runtimes or containerized processes accessing host-level directories.
    * **NIDS (Suricata + Zeek): NO.** Escaping to the host is a local OS-level exploit or misconfiguration abuse.

### **2. Custom Sigma Rule**

This rule detects suspicious activity indicating a container escape attempt, such as a containerized process accessing sensitive host directories like `/etc/shadow`, `/root`, or modifying host binaries, which is commonly seen when a host filesystem is mounted into the container.

```yaml
title: Container Escape via Host Filesystem Access (AN0614)
id: f1a2b3c4-5d6e-7f8a-9b0c-1d2e3f4a5b6c
status: experimental
description: Detection of Windows/Linux container escape attempts by observing processes accessing sensitive host directories or abusing symbolic links.
author: Krishna Gupta
date: 2026-06-09
logsource:
    category: process_creation
    product: linux
    # Relies on Sysmon for Linux or Wazuh auditd integration
detection:
    selection_container:
        # Assuming the environment enriches logs with container context
        # Or identifying common container runtimes as parents
        ParentImage|endswith:
            - '/containerd-shim'
            - '/docker-containerd-shim'
            - '/runc'
    selection_suspicious_cmd:
        CommandLine|contains:
            - '/host/etc/'
            - '/host/root/'
            - '/host/var/run/docker.sock'
            - 'chroot /host'
            - 'nsenter -t 1'
    condition: selection_container and selection_suspicious_cmd
fields:
    - CommandLine
    - Image
    - ParentImage
falsepositives:
    - Administrative maintenance containers explicitly designed to manage host configurations.
level: critical
tags:
    - attack.privilege_escalation
    - attack.t1611
    - analytics.an0614
    - detection.det0219
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Kernel Exploitation Escapes**
    * *The Issue:* If the escape leverages a Linux kernel exploit (e.g., Dirty COW) to overwrite host memory directly, there may be no suspicious `CommandLine` execution logged before the attacker gains root on the host.
    * *The Fix:* Utilize eBPF-based security monitoring tools that track kernel-level syscalls and alert on unexpected privilege escalation (e.g., `commit_creds`) without a standard `setuid` flow.

* **Problem 2: Authorized Daemonsets**
    * *The Issue:* Kubernetes DaemonSets (like logging agents or security monitors) often require mounting the host filesystem (`/var/log`, `/etc`) and running as root.
    * *The Fix:* Baseline known administrative container images and filter out alerts based on the exact SHA256 image hash or the Kubernetes namespace (e.g., `kube-system`).
