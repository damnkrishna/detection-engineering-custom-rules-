### **1. Technique Breakdown: T1546**

* **What it is:** **Event Triggered Execution: WMI Event Subscription**. Windows Management Instrumentation (WMI) can be used to register event filters, event consumers, and filter-to-consumer bindings. When a specific system event triggers the filter (e.g., system startup, time elapsed, or user logon), the WMI service executes the consumer (e.g., `CommandLineEventConsumer` or `ActiveScriptEventConsumer`) with local system (`SYSTEM`) privileges. Adversaries exploit WMI event subscriptions to establish persistent, elevated execution flows.
* **Log Source Requirements:** Endpoint logs capturing process creation and command line arguments (Sysmon Event ID 1 / Windows Security Event ID 4688) or WMI event subscription logs (Sysmon Event IDs 19, 20, 21).
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 logs CLI invocations of `wmic.exe` or PowerShell cmdlets modifying WMI objects. Sysmon Event IDs 19, 20, and 21 log raw WMI consumer/filter additions, providing direct detection coverage.
* **NIDS (Suricata + Zeek): NO.** WMI event subscription registration is a local OS management task and does not generate network logs.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect command-line creation or modification of WMI event consumers, filters, and bindings using `wmic.exe` or PowerShell cmdlets.

```yaml
title: WMI Event Subscription Creation via CLI (AN0024)
id: 71b5eb0d-5a08-48a4-b83c-8556c2b828a4
status: experimental
description: Detects command-line execution of wmic.exe or PowerShell cmdlets configuring WMI event consumers, filters, or bindings, which can be abused for privilege escalation and persistence.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_wmic:
        - Image|endswith: '\wmic.exe'
        - OriginalFileName: 'wmic.exe'
    selection_wmic_args:
        CommandLine|contains:
            - 'ActiveScriptEventConsumer'
            - 'CommandLineEventConsumer'
            - 'EventConsumer'
            - 'EventFilter'
            - 'FilterToConsumerBinding'
    selection_powershell:
        - Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
        - OriginalFileName:
            - 'PowerShell.EXE'
            - 'pwsh.dll'
    selection_powershell_args:
        CommandLine|contains:
            - 'Wmi'
            - 'Cim'
        CommandLine|contains:
            - 'Consumer'
            - 'Filter'
            - 'Binding'
    condition: (selection_wmic and selection_wmic_args) or (selection_powershell and selection_powershell_args)
fields:
    - CommandLine
    - Image
    - OriginalFileName
falsepositives:
    - Legitimate enterprise systems management software (e.g., SCCM, monitoring agents) creating WMI event subscriptions during installation.
level: high
tags:
    - attack.persistence
    - attack.privilege_escalation
    - attack.t1546
    - analytics.an0024
    - detection.det0033
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Direct WMI API / COM/Scripting Methods**
* *The Issue:* Attackers can write compiled programs (e.g., C# using `System.Management` namespace or VB scripts) that modify WMI subscriptions directly using COM interfaces. This bypasses command-line checks entirely because no CLI arguments containing WMI commands are generated.
* *The Fix:* Enable and monitor Sysmon Event ID 19, 20, and 21 logs, which capture WMI Filter, Consumer, and Binding creation events directly at the WMI repository layer, regardless of the command-line utility used.


* **Problem 2: WMI Repository Tampering**
* *The Issue:* Advanced adversaries can directly manipulate the WMI repository database (`OBJECTS.DATA` under `%SystemRoot%\System32\Wbem\Repository`) offline or through driver-level disk access to inject subscriptions, bypassing event subscription logs.
* *The Fix:* Implement file integrity monitoring (FIM) or audit write permissions on the `%SystemRoot%\System32\Wbem\Repository\` folder, and monitor system boots for unrecognized DLL loads inside the Wbem directory.


* **Problem 3: Administration Agent Noise**
* *The Issue:* System management utilities (like Microsoft SCCM, SCOM, or third-party monitoring agents) routinely create and destroy WMI subscriptions to query system states, generating heavy noise.
* *The Fix:* Whitelist known administrative service accounts, focus on `ActiveScriptEventConsumer` registrations (which are rarely used in modern legitimate software), and restrict alerting to non-standard user profiles.
