### **1. Technique Breakdown: T1134.004**

* **What it is:** **Access Token Manipulation: Parent PID Spoofing**. Adversaries explicitly forge the parent of a newly created process. By using the `UpdateProcThreadAttribute` API with the `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` flag during `CreateProcess`, they can make their malicious payload appear to be the child of a legitimate system process (like `explorer.exe` or `services.exe`). If they spoof a SYSTEM-level parent, the child process inherits the SYSTEM access token, resulting in privilege escalation.
* **Log Source Requirements:** Process creation logs (Sysmon Event ID 1), ETW (Event Tracing for Windows) Process/Thread provider.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon actively detects Parent PID spoofing and records both the spoofed parent in the primary fields, but also flags the anomaly.
    * **NIDS (Suricata + Zeek): NO.** Purely an operating system API manipulation.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** which natively detects and flags PPID spoofing by capturing the mismatch between the requesting process and the forged parent process.

```yaml
title: Parent PID Spoofing Detection (AN1351)
id: fbbcc3f9-676b-4e6c-a8eb-8b0ab3606f1d
status: experimental
description: Detects when a process explicitly forges its parent process using Native API paths, resulting in mismatched/implausible lineage (PPID Spoofing).
author: Krishna Gupta
date: 2026-06-09
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_spoof:
        # Sysmon logs the true caller in the details when spoofing is detected
        # depending on Sysmon version, it may populate the "ParentProcessId" differently than the OS
        # Advanced Sysmon configurations flag this directly, but behaviourally we look for impossible chains:
        Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\rundll32.exe'
    selection_impossible_parent:
        ParentImage|endswith:
            - '\lsass.exe'
            - '\spoolsv.exe'
            - '\smss.exe'
            - '\csrss.exe'
    condition: selection_spoof and selection_impossible_parent
fields:
    - Image
    - ParentImage
falsepositives:
    - Highly unusual debugging environments.
level: critical
tags:
    - attack.privilege_escalation
    - attack.defense_evasion
    - attack.t1134.004
    - analytics.an1351
    - detection.det0489
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Sigma's Inability to Catch True Spoofing**
    * *The Issue:* A static Sigma rule checking `Image` vs `ParentImage` is just guessing based on "impossible" chains (e.g., `lsass` doesn't spawn `cmd`). It misses a smart attacker who spoofs `explorer.exe` spawning `cmd.exe` (which is completely normal).
    * *The Fix:* Utilize Endpoint Detection and Response (EDR) telemetry. Modern EDRs compare the ETW `EventHeader ProcessId` (the true process that made the system call) against the `ParentProcessId` provided in the `CreateProcess` struct. If they differ, the EDR flags a definitive "PPID Spoofing" alert.

* **Problem 2: UAC Elevation (Consent.exe)**
    * *The Issue:* When a user right-clicks and selects "Run as Administrator", Windows natively uses a mechanism resembling PPID spoofing via Application Information service (`svchost.exe -k netsvcs`) and `consent.exe`.
    * *The Fix:* Whitelist parent-child relationships originating from UAC elevations where the parent is the `svchost.exe` hosting `Appinfo`.

* **Problem 3: Token Inheritance vs. Just Evasion**
    * *The Issue:* Sometimes PPID spoofing is used purely to evade detection (hiding under `explorer.exe`), not to gain privileges.
    * *The Fix:* To detect the *Privilege Escalation* aspect, correlate the PPID spoofing alert with the resulting `User` of the child process. If the child is `SYSTEM` and the true caller was a standard user, it's an escalation attack.
