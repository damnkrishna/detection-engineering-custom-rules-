### **1. Technique Breakdown: T1134.005**

* **What it is:** **Access Token Manipulation: SID-History Injection**. The `sIDHistory` attribute in Active Directory is used during migrations to preserve access rights from an old domain to a new one. Adversaries can inject SIDs of highly privileged groups (like Enterprise Admins or Domain Admins) into the `sIDHistory` attribute of a standard user account. When this standard user logs in, they receive the permissions of the injected SIDs, effectively granting them domain administrator access while appearing as a normal user.
* **Log Source Requirements:** Windows Security Event Log (Event ID 4742 - Computer account changed, Event ID 4738 - User account changed, Event ID 4769 - Kerberos service ticket requested).
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Windows Security logs on the Domain Controller capture modifications to user and computer accounts, including the `sIDHistory` attribute.
    * **NIDS (Suricata + Zeek): NO.** While LDAP and Kerberos traffic occurs, the specific manipulation of the SID is best caught at the AD audit log level.

### **2. Custom Sigma Rule**

This rule utilizes **Windows Security Event IDs 4742 and 4738** to detect unauthorized modifications to the `sIDHistory` attribute in Active Directory.

```yaml
title: SID-History Injection (AN0383)
id: c9f11a22-45e3-4d6b-9c88-e21e90b77d49
status: experimental
description: Detection of unauthorized modification of Active Directory SID-History attributes to escalate privileges.
author: Krishna Gupta
date: 2026-06-09
logsource:
    product: windows
    service: security
    # Relies on Windows Security Logs on Domain Controllers
detection:
    selection_event:
        EventID:
            - 4738
            - 4742
    selection_attribute:
        SidHistory|contains: '-'
    filter_known_migrations:
        # Whitelist specific accounts or processes handling legitimate migrations
        SubjectUserName|startswith: 'MigrationAdmin'
    condition: selection_event and selection_attribute and not filter_known_migrations
fields:
    - EventID
    - SidHistory
    - TargetUserName
    - SubjectUserName
falsepositives:
    - Legitimate Active Directory domain migrations using authorized tools like ADMT.
level: critical
tags:
    - attack.privilege_escalation
    - attack.t1134.005
    - analytics.an0383
    - detection.det0136
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Mimikatz Golden Tickets with SID History**
    * *The Issue:* Attackers can forge Kerberos Ticket Granting Tickets (Golden Tickets) entirely offline and embed the Enterprise Admin SID directly into the PAC's `sIDHistory` field. This does NOT generate a 4738/4742 attribute change event because AD itself is never modified.
    * *The Fix:* Correlate Event ID 4769 (Kerberos Service Ticket Requested) or 4624 (Logon) looking for anomalies where the `TargetLogonId` has an associated `sIDHistory` containing `S-1-5-21-*-519` (Enterprise Admins) but the account itself is not in the group.

* **Problem 2: Incomplete Audit Policies**
    * *The Issue:* If Advanced Audit Policy for "Audit User Account Management" is not enabled on Domain Controllers, Event ID 4738 and 4742 will not be generated.
    * *The Fix:* Validate DC audit configurations via GPO to ensure Account Management auditing is set to Success and Failure.

* **Problem 3: Finding the True Source**
    * *The Issue:* The Event ID 4738 tells you *which* AD object was modified and by *whom* (SubjectUserName), but not *how* (the specific process or malware on the admin workstation).
    * *The Fix:* Pivot using the `SubjectLogonId` to identify the originating workstation (via Event ID 4624 Network Logon) and correlate with Sysmon Event ID 1 on that workstation to find the tool (e.g., PowerShell using `Set-ADUser` or Mimikatz) that performed the injection.
