### 1. Technique Breakdown: T1134.003

* What it is: Access Token Manipulation: Make and Impersonate Token. Adversaries create a brand-new logon session and associated token using APIs like `LogonUser` or `LsaLogonUser` (often passing credentials explicitly, or using the `/netonly` flag). They then assign or impersonate this new token using `SetThreadToken` or `ImpersonateLoggedOnUser` to execute actions under that freshly created security context. This is heavily used to pivot to different accounts or access network shares without dropping a new process to disk.
* Log Source Requirements: Windows Security Event Log (Event ID 4624 - Logon).
* Coverage Check:
    * HIDS (Sysmon + Wazuh): YES. Windows Security logs natively capture the `LogonUser` API call as an Event ID 4624 Logon event (typically Logon Type 2, 3, or 9).
    * NIDS (Suricata + Zeek): NO. This is a local authentication/token generation mechanism.

### 2. Custom Sigma Rule

This rule utilizes Windows Security Event ID 4624 (Logon) to detect the creation of a new token via explicit credentials, specifically focusing on Logon Type 9 (NewCredentials), which is commonly generated by `runas /netonly` or PowerShell scripts invoking `LogonUserA`.

```yaml
title: Make and Impersonate Token (NewCredentials Logon) (AN1375)
id: fbbcc3f9-676b-4e6c-a8eb-8b0ab3606f1d
status: experimental
description: Detects the creation of a new token via LogonUser (Logon Type 9 - NewCredentials), often used by attackers to authenticate to network resources.
author: Krishna Gupta
date: 2026-06-09
logsource:
    product: windows
    service: security
    # Relies on Windows Security Logs (Event ID 4624)
detection:
    selection_event:
        EventID: 4624
    selection_type:
        LogonType: 9
    filter_known_processes:
 # Whitelist legitimate services that use Type 9 logons
        ProcessName|endswith:
            - '\svchost.exe'
            - '\lsass.exe'
    condition: selection_event and selection_type and not filter_known_processes
fields:
    - EventID
    - LogonType
    - ProcessName
    - TargetUserName
falsepositives:
    - Administrators legitimately using runas /netonly to access network shares from untrusted domains.
    - Application pools in IIS running under specific domain accounts.
level: high
tags:
    - attack.privilege-escalation
    - attack.t1134.003
    - analytic.an1375
    - detection.det0498
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Administrative Action False Positives
  * The Issue: IT personnel performing legitimate maintenance operations can invoke techniques that mirror adversarial persistence or evasion.
  * The Fix: Audit and baseline corporate administration accounts, whitelisting specific approved service accounts and administrative subnets.

* Problem 2: Command and Execution Obfuscation
  * The Issue: Attackers employ encoding, environment variables, or caret insertions to bypass keyword-based detection filters.
  * The Fix: Enable deep logging (such as Script Block Logging) and apply normalization or regex decoding inside the SIEM parsing pipeline.

* Problem 3: Log Deletion and Modification
  * The Issue: Adversaries can clear security logs or stop monitoring agents (like Wazuh or Sysmon) to blind defensive operations.
  * The Fix: Forward all endpoint logs immediately to a centralized write-once SIEM and alert on service stoppage or log clearing events.
