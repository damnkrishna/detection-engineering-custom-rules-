### **1. Technique Breakdown: T1078.001**

* **What it is:** **Valid Accounts: Default Accounts**. Operating systems and software packages are installed with default built-in accounts (e.g., `Administrator`, `Guest` in Windows). Adversaries scan for and exploit default accounts that have default passwords, weak passwords, or are left enabled. Operating systems with default accounts exposed to remote protocols like SMB or RDP represent primary targets.
* **Log Source Requirements:** Windows Security Event Log capturing authentication events (Event ID 4624 for successful logon) containing user names, logon types, and source IP addresses.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Windows Security Event ID 4624 logs all successful authentication sessions. Wazuh retrieves and alerts on specific usernames and logon types.
* **NIDS (Suricata + Zeek): YES (Partial).** Network security tools can identify authentication attempts over SMB (NTLM) or RDP (TLS) containing default usernames but cannot determine if authorization was successful.

### **2. Custom Sigma Rule**

This rule utilizes **Windows Security Event ID 4624 (Successful Logon)** to detect network or remote interactive logons using built-in default accounts (`Administrator`, `Guest`).

```yaml
title: Default Account Remote Logon (AN1283)
id: e6ef5fe7-2752-476e-b1eb-9599b236fd22
status: experimental
description: Detects successful remote network or remote interactive logons using built-in default accounts (e.g., Administrator, Guest).
author: Krishna Gupta
date: 2026-06-07
logsource:
    product: windows
    service: security
    # Relies on Windows Security Event ID 4624
detection:
    selection_event:
        EventID: 4624
    selection_logon_type:
        LogonType:
            - 3 # Network
            - 10 # Remote Interactive
    selection_default_users:
        TargetUserName:
            - 'Administrator'
            - 'Guest'
    condition: selection_event and selection_logon_type and selection_default_users
fields:
    - EventID
    - LogonType
    - TargetUserName
falsepositives:
    - Initial operating system setup or legacy systems where local domain configurations are not yet deployed.
level: high
tags:
    - attack.defense_evasion
    - attack.persistence
    - attack.privilege_escalation
    - attack.t1078.001
    - analytics.an1283
    - detection.det0350
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Default Account Renaming**
* *The Issue:* Many organizations rename the default built-in `Administrator` or `Guest` account to comply with security baselines. Since the account name changes (e.g., to `adm-local`), string-based checks on `TargetUserName` will miss logons exploiting the built-in account.
* *The Fix:* Instead of only checking username strings, audit logons by targeting the default account Security Identifier (SID) suffixes: `S-1-5-21-*-500` (built-in Administrator) and `S-1-5-21-*-501` (built-in Guest) via Windows Event ID 4624 `TargetUserSid` attribute.


* **Problem 2: Domain vs Local Administrator Ambiguity**
* *The Issue:* On domain-joined machines, logging in as `Administrator` can refer to either the local machine's administrator account or the active directory domain administrator. Both generate Logon Event ID 4624, leading to parsing confusion.
* *The Fix:* Distinguish the scope of logon by examining `TargetDomainName`. If it matches the local computer name or `NT AUTHORITY`, it indicates local account usage. If it matches the Active Directory domain, it is domain account abuse.


* **Problem 3: Automation Scripts Noise**
* *The Issue:* Legacy deployment and provisioning automation scripts may still hardcode logons to the local administrator account, generating repeated false alarms during standard builds.
* *The Fix:* Restrict alerting of remote default logons to production subnets, excluding staging/imaging VLANs, or whitelist specific provisioning IP addresses.
