### **1. Technique Breakdown: T1134.001**

* **What it is:** **Access Token Manipulation: Token Impersonation/Theft**. Adversaries duplicate an access token belonging to a highly privileged user (like `SYSTEM` or an administrator) and impersonate that user. This is often accomplished using Windows APIs like `DuplicateToken`, `DuplicateTokenEx`, `ImpersonateLoggedOnUser`, or `SetThreadToken`. This allows a standard process or thread to execute actions with the permissions of the stolen token without needing the user's password.
* **Log Source Requirements:** Process creation logs (Sysmon Event ID 1), Windows Security Event Log (Event ID 4624 - Logon, Event ID 4672 - Special Privileges Assigned).
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES (Partial).** Sysmon tracks command-line utilities (like `runas`) that perform impersonation natively. However, API-level impersonation is best caught via Windows Security Event Logs.
    * **NIDS (Suricata + Zeek): NO.** Token impersonation happens entirely within the local OS kernel.

### **2. Custom Sigma Rule**

This rule utilizes **Windows Security Event ID 4624 (Logon)** to detect suspicious token impersonation, specifically focusing on Logon Type 9 (NewCredentials) originating from unusual parent processes, or explicitly tracking `runas.exe` usage via **Sysmon Event ID 1**.

```yaml
title: Token Impersonation / Theft (AN1324)
id: fbbcc3f9-676b-4e6c-a8eb-8b0ab3606f1d
status: experimental
description: Detects token duplication and impersonation attempts by correlating suspicious command-line executions (e.g., runas) or anomalous NewCredentials logons.
author: Krishna Gupta
date: 2026-06-09
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_runas:
        Image|endswith: '\runas.exe'
    selection_args:
        CommandLine|contains:
            - '/savecred'
            - '/user:NT AUTHORITY\SYSTEM'
            - '/user:Administrator'
    filter_known:
        ParentImage|endswith:
            - '\explorer.exe' # Legitimate user typing runas
    condition: selection_runas and selection_args and not filter_known
fields:
    - CommandLine
    - Image
    - ParentImage
falsepositives:
    - System administrators running scripts that explicitly elevate via runas.
level: high
tags:
    - attack.privilege_escalation
    - attack.t1134.001
    - analytics.an1324
    - detection.det0482
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: In-Memory API Calls Bypass runas**
    * *The Issue:* Advanced malware doesn't use `runas.exe`. It calls `DuplicateTokenEx` directly in C/C++ or via C# reflection. This generates no Sysmon process creation event for `runas`.
    * *The Fix:* Correlate Windows Security Event ID 4624 (Logon Type 9) where the `LogonProcessName` is `seclogo` and the `TargetUserName` is an administrator, originating from a `CallerProcessName` that is not a known Windows service.

* **Problem 2: Named Pipe Impersonation (Cobalt Strike)**
    * *The Issue:* Attackers often use `ImpersonateNamedPipeClient` to steal a token from a connecting SYSTEM process. 
    * *The Fix:* Monitor Sysmon Event ID 17/18 (Named Pipes) for randomly generated pipe names (like Cobalt Strike's default `\pipe\msrpc_*`) and correlate with subsequent privilege escalation events.

* **Problem 3: WMI and WinRM Remote Execution**
    * *The Issue:* When an attacker uses WMI to execute code remotely, the token is technically "impersonated" by `wmiprvse.exe` on the target host. This looks like legitimate administration.
    * *The Fix:* Baseline WMI activity. Alert when `wmiprvse.exe` spawns processes (like `cmd.exe` or `powershell.exe`) with `SYSTEM` tokens, especially if the WMI connection originated from a non-administrative workstation.
