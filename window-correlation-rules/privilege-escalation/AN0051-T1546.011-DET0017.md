### **1. Technique Breakdown: T1546.011**

* **What it is:** **Event Triggered Execution: Application Shimming**. The Microsoft Application Compatibility Infrastructure (shims) provides compatibility fixes for legacy programs. Adversaries exploit shims by creating custom shim databases (`.sdb` files) and installing them using the built-in command-line tool `sdbinst.exe`. Once registered, the compatibility database can be triggered when a specific application executes, allowing the attacker to inject malicious DLLs, bypass User Account Control (UAC), or hook APIs under a privileged execution context.
* **Log Source Requirements:** Endpoint logs capturing process creation and command line arguments (Sysmon Event ID 1 / Windows Security Event ID 4688).
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 logs the execution of `sdbinst.exe` with command line arguments. Additionally, Sysmon Event ID 11 (File Create) and registry monitoring can capture the creation of `.sdb` files under `%SystemRoot%\AppPatch\Custom\`.
* **NIDS (Suricata + Zeek): NO.** Application shimming configuration is a local OS mechanism and does not produce network logs.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect the invocation of `sdbinst.exe` installing custom application shim databases.

```yaml
title: Application Shim Database Installation (AN0051)
id: 19bdd3e0-ad95-40c5-9a35-ff6008893eab
status: experimental
description: Detects the execution of sdbinst.exe used to install custom application shim databases (.sdb), which can be abused for persistence and privilege escalation.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection:
        - Image|endswith: '\sdbinst.exe'
        - OriginalFileName: 'sdbinst.exe'
    condition: selection
falsepositives:
    - Legacy enterprise applications running compatibility scripts during software upgrades or deployment.
level: high
tags:
    - attack.persistence
    - attack.privilege_escalation
    - attack.t1546.011
    - analytics.an0051
    - detection.det0017
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Bypassing sdbinst.exe Installer via Registry Injection**
* *The Issue:* Attackers can bypass `sdbinst.exe` detection by manually writing registry entries to register a custom `.sdb` file under `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Custom` or `InstalledSDB` paths without running the installation utility.
* *The Fix:* Enable registry auditing and monitor Sysmon Event ID 12 (Registry Object Added/Deleted) or Event ID 13 (Registry Value Set) targeting the AppCompat registry keys.


* **Problem 2: Execution of Renamed sdbinst.exe Utility**
* *The Issue:* Attackers can copy `sdbinst.exe` to a user-writable folder, rename it (e.g., `update.exe`), and execute it to install a shim database. This evades detections matching only the filename `sdbinst.exe` under standard paths.
* *The Fix:* Monitor the `OriginalFileName` field in Sysmon Event ID 1, which remains `sdbinst.exe` even if the executable binary has been renamed.


* **Problem 3: Installer Package Noise**
* *The Issue:* Software developers and legacy corporate enterprise applications frequently configure shims during standard deployment.
* *The Fix:* Whitelist `sdbinst.exe` parent processes from trusted software distribution paths (like SCCM client paths or specific installation directories) and monitor for custom `.sdb` files executing from temporary or user profiles (e.g. `C:\Users\...\AppData\`).
