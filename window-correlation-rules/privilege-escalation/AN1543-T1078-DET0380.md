### **1. Technique Breakdown: T1078**

* **What it is:** **Valid Accounts**. Adversaries hijack legitimate credentials of local, domain, or service accounts to gain initial access, establish persistence, or escalate privileges. Because they utilize valid credentials, their activities appear benign. Detection relies on monitoring anomalous authentication indicators, such as remote logons (Logon Type 3 or 10) by highly privileged accounts executing from unexpected source endpoints or during non-business hours.
* **Log Source Requirements:** Windows Security Event Log capturing authentication events (Event ID 4624 for successful logon) containing user names, logon types, domains, and source IP addresses.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Windows Security Event ID 4624 logs logon events with detailed metadata. Wazuh collects and parses these logon attributes.
* **NIDS (Suricata + Zeek): YES (Partial).** Network security tools can log Kerberos or NTLM authentications over protocols like SMB/RDP (Zeek `kerberos` or `ntlm` logs), but lack local session visibility.

### **2. Custom Sigma Rule**

This rule utilizes **Windows Security Event ID 4624 (Successful Logon)** to detect network or remote interactive logons using administrative accounts from unexpected network sources.

```yaml
title: Anomalous Administrative Account Logon (AN1543)
id: cc6e8e88-fa3a-45c9-bc4f-1bf8a6597f2c
status: experimental
description: Detects successful remote network or remote interactive logons using administrative accounts from unexpected network sources or during anomalous operating hours.
author: Krishna Gupta
date: 2026-06-07
logsource:
    product: windows
    service: security
    # Relies on Windows Security Event ID 4624
detection:
    selection_event:
        EventID: 4624
    selection_logon_type:
        LogonType:
            - 3 # Network Logon
            - 10 # Remote Interactive (RDP)
    selection_admin_users:
        TargetUserName|contains:
            - 'admin'
            - 'Administrator'
            - 'adm_'
            - 'svc_'
    selection_anomalous_ip:
        IpAddress|startswith:
            - '192.168.100.'
            - '10.'
            - '172.16.'
    condition: selection_event and selection_logon_type and selection_admin_users and selection_anomalous_ip
fields:
    - EventID
    - IpAddress
    - LogonType
    - TargetUserName
falsepositives:
    - Legitimate administrative tasks performed by administrators during off-hours or maintenance windows.
    - Automated service account activities executing scheduled scans from authorized staging servers.
level: medium
tags:
    - attack.defense_evasion
    - attack.persistence
    - attack.privilege_escalation
    - attack.t1078
    - analytics.an1543
    - detection.det0380
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Session Hijacking and Token Impersonation**
* *The Issue:* Attackers can perform lateral movement using token theft (e.g., via Mimikatz `sekurlsa::tickets` or `make_token`) or session hijacking, which abuses existing local authentication states and does not generate a new remote interactive Logon Event ID 4624.
* *The Fix:* Monitor process execution contexts for token impersonation (Sysmon Event ID 1 / Event ID 10 for process access) and audit Kerberos ticket requests (Event ID 4768 / 4769) for unusual ticket lifetimes or encryption types.


* **Problem 2: IP Address Spoofing/NAT Masquerading**
* *The Issue:* If the attacker executes remote logons through an authorized gateway (like a VPN concentrator or jump box), the source IP address in the log will display the gateway's IP, bypassing anomalous source subnet matches.
* *The Fix:* Correlate VPN logon logs with internal endpoint authentication logs, and look for multi-factor authentication (MFA) bypasses or simultaneous connections from the same user account from two different endpoints (geographical anomalies).


* **Problem 3: Standard Administrative Activity Noise**
* *The Issue:* Legitimate system administrators routinely access servers remotely to perform scheduled maintenance, triggering alerts.
* *The Fix:* Baseline administrative behavior to whitelist specific jump hosts or administrative subnets, and integrate the detection with change management tickets to suppress alerts during approved windows.
