### **1. Technique Breakdown: T1112**

* **What it is:** **Modify Registry**. Adversaries interact with the Windows Registry to hide configuration information, store payloads (fileless malware), establish persistence, or disable security tools. The registry is incredibly vast, so attackers abuse it constantly to blend in with legitimate system noise.
* **Log Source Requirements:** Detecting this requires highly granular endpoint telemetry focused on Registry Key/Value creation and modification, or process creation logs if they use native command-line tools.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** This is exactly what Sysmon Event IDs 12 (Registry object added/deleted), 13 (Registry value set), and 14 (Registry object renamed) are designed to capture.
* **NIDS (Suricata + Zeek): NO.** The registry is an internal operating system database. Modifying it generates zero network traffic.

### **2. Custom Sigma Rule**

Because T1112 is a massive category, a rule that just says "alert on registry modification" will crash your SIEM with false positives. To make DET0280 actionable, this rule focuses on one of the most critical manifestations of T1112: **Adversaries modifying the registry to disable endpoint security controls (Windows Defender, UAC, or AMSI).**

This rule uses **Sysmon Event ID 13 (Registry Value Set)**.

```yaml
title: Suspicious Registry Modification - Security Control Tampering (AN0781)
id: 6f7a8b9c-0d1e-2f3a-4b5c-6d7e8f9a0b1c
status: experimental
description: Detects registry modifications aimed at disabling or tampering with core Windows security controls like Windows Defender, UAC (EnableLUA), or AMSI, indicating Defense Evasion via Modify Registry (T1112).
author: Krishna Gupta
date: 2026-06-05
logsource:
    category: registry_set
    product: windows
    # Relies on Sysmon Event ID 13 collected via Wazuh
detection:
    selection_defender_keys:
        TargetObject|contains:
            - '\Microsoft\Windows Defender\DisableAntiSpyware'
            - '\Microsoft\Windows Defender\Real-Time Protection\DisableRealtimeMonitoring'
            - '\Microsoft\Windows Defender\Real-Time Protection\DisableBehaviorMonitoring'
    selection_uac_amsi:
        TargetObject|contains:
            - '\Microsoft\Windows\CurrentVersion\Policies\System\EnableLUA'
            - '\Software\Microsoft\Windows Script\Settings\AmsiEnable'
    selection_malicious_values:
        # Looking for the value being set to '1' (disabled) or '0' depending on the key
        Details: 
            - 'DWORD (0x00000001)'
            - 'DWORD (0x00000000)'
    condition: (selection_defender_keys or selection_uac_amsi) and selection_malicious_values
falsepositives:
    - IT administrators deploying Group Policy Objects (GPOs) to manage legacy software requirements.
    - Automated endpoint management tools (e.g., SCCM, Intune) applying approved baseline configurations.
level: high
tags:
    - attack.defense_evasion
    - attack.t1112
    - analytics.an0781
    - detection.det0280

```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: The Sysmon Configuration Bottleneck**
* *The Issue:* Sysmon does not log every registry change by default (it would brick the machine). It only logs the keys you explicitly tell it to monitor in your `sysmonconfig.xml`. If an attacker stores a fileless malware payload (like a base64 encoded Cobalt Strike beacon) in a random, unmonitored registry key like `HKCU\Software\Classes\CustomKey`, this Sigma rule—and Sysmon itself—will completely miss it.
* *The Fix:* You must constantly update your Sysmon configuration file (look into SwiftOnSecurity or Olaf Hartong's Sysmon-Modular configs) to ensure the paths monitored align with current threat intel, and deploy those updates via Wazuh.


* **Problem 2: Kernel-Level Blinding**
* *The Issue:* Advanced adversaries (or ransomware operators like BlackBasta) use "Bring Your Own Vulnerable Driver" (BYOVD) attacks. They drop a signed but vulnerable driver (like `gdrv.sys`) to gain kernel access. Once in the kernel, they strip the callbacks that Sysmon uses to monitor the registry. The registry modification happens, but Sysmon goes completely silent.
* *The Fix:* You need rules that detect the *precursor*—the loading of known vulnerable drivers (Sysmon Event ID 6 - Driver Loaded).


* **Problem 3: GPO / SCCM Alert Fatigue**
* *The Issue:* If your helpdesk uses scripts to temporarily disable UAC for troubleshooting, or if a GPO pushes a Defender exclusion, this rule will trigger.
* *The Fix:* You need to baseline the `Image` (the process making the registry change). If `svchost.exe` (acting as the Group Policy Client) makes the change, you might downgrade the alert. If `powershell.exe` or `cmd.exe` makes the change, keep it Critical.
