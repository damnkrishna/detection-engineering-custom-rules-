### **1. Technique Breakdown: T1125**

* **What it is:** **Video Capture**. Adversaries record video from the host webcam or screen using built-in software or custom malware commands. The collected video can be used to gather credentials, observe user actions, or perform espionage. On Windows endpoints, this is typically done by loading video capture libraries (like `avicap32.dll`, `capwin.dll`, or DirectShow/Media Foundation `mf.dll` wrappers) or executing CLI-based media tools (like `ffmpeg.exe`) targeting local camera devices.
* **Log Source Requirements:** Sysmon Library Load logs (Event ID 7) or process creation logs (Event ID 1).
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 7 records process library loads, enabling detection when an unsigned application loads `avicap32.dll`. Sysmon Event ID 1 tracks command line execution.
    * **NIDS (Suricata + Zeek): NO.** Network sensors have no visibility into local system driver initialization or camera hardware actions.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 7 (Library Load)** to detect unsigned or anomalous applications loading the core Windows video capture library (`avicap32.dll`), which indicates potential unauthorized webcam access.

```yaml
title: Collection - Anomaly Video Capture Library Load (AN0568)
id: 5b4e4f8a-439b-4530-ae78-dab6179de228
status: experimental
description: Detects unsigned or non-standard executables loading the Windows video capture DLL (avicap32.dll), suggesting unauthorized webcam recording or capture.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: image_load
    product: windows
    # Relies on Sysmon Event ID 7 collected via Wazuh
detection:
    selection_dll:
        ImageLoaded|endswith: '\avicap32.dll'
    filter_signed:
        # Exclude standard web-meeting and system binaries (e.g. Teams, Chrome, Zoom, Camera App)
        Image|endswith:
            - '\chrome.exe'
            - '\msedge.exe'
            - '\teams.exe'
            - '\zoom.exe'
            - '\skype.exe'
            - '\WindowsCamera.exe'
            - '\obs64.exe'
    condition: selection_dll and not filter_signed
fields:
    - Image
    - ImageLoaded
falsepositives:
    - Legitimate corporate web collaboration tools or third-party camera management utilities not covered in the static exclusion list.
level: high
tags:
    - attack.collection
    - attack.t1125
    - analytics.an0568
    - detection.det0197
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Use of DirectShow or Media Foundation (No avicap32.dll)**
    * *The Issue:* Modern applications use newer APIs (DirectShow `dshow` or Media Foundation `mf.dll`) rather than the legacy `avicap32.dll`. If an attacker uses these APIs, this rule will not trigger.
    * *The Fix:* Add a complementary rule tracking loads of DirectShow assemblies (`qcap.dll`, `ksproxy.ax`) by unsigned binaries.

* **Problem 2: Headless systems / Servers**
    * *The Issue:* Production servers rarely have webcams or video capture capabilities, so camera library alerts on servers are highly confident but rare, while user laptops will generate many false alarms.
    * *The Fix:* Increase the severity level to Critical for server segments and focus exclusions only on corporate laptop builds.

* **Problem 3: Virtual Camera Drivers**
    * *The Issue:* Software like OBS Studio or virtual webcam apps register custom virtual camera devices, loading these DLLs dynamically and triggering false positives.
    * *The Fix:* Verify the code signature of the loading process and ensure it matches a known list of approved corporate software vendors.
