### **1. Technique Breakdown: T1114.001**

* **What it is:** **Local Email Collection**. Adversaries access locally stored email data files to harvest communications, credentials, or sensitive business information. On Windows, Microsoft Outlook stores email locally in Personal Storage Table files (`.pst`) and Offline Storage Table files (`.ost`) within the user's profile directory (`%USERPROFILE%\Documents\Outlook Files\` or `%LOCALAPPDATA%\Microsoft\Outlook\`). Adversaries use shell commands, PowerShell, or custom tools to locate and copy these large data files, which can contain years of email history, attachments, calendar items, and contact information — often without triggering email server-side logging.
* **Log Source Requirements:** File event logs (Sysmon Event ID 11) for access to `.pst`/`.ost` files, and process creation logs (Sysmon Event ID 1) for utilities enumerating or copying Outlook data.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 11 captures file creation events for `.pst`/`.ost` files being copied or opened by non-Outlook processes. Sysmon Event ID 1 logs process launches with file paths pointing to Outlook data directories.
    * **NIDS (Suricata + Zeek): NO.** Accessing local `.pst`/`.ost` files is a host filesystem operation. Subsequent exfiltration (e.g., uploading to a file share) may generate network events, but the collection step itself is local.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 11 (File Create/Access)** to detect non-Outlook processes accessing or copying local Outlook PST/OST data files, and **Sysmon Event ID 1** to detect command-line tools searching for or copying email archive files.

```yaml
title: Local Outlook Email Archive Access by Non-Outlook Process (AN0130)
id: 4f2556db-5086-447d-b495-f443160d7880
status: experimental
description: Detects non-Outlook processes accessing or copying local Outlook PST or OST email data files, which may indicate adversarial email collection for intelligence gathering or credential harvesting.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: file_event
    product: windows
    # Relies on Sysmon Event ID 11 collected via Wazuh
detection:
    selection_pst_ost:
        TargetFilename|endswith:
            - '.pst'
            - '.ost'
    selection_outlook_paths:
        TargetFilename|contains:
            - '\Microsoft\Outlook\'
            - '\Outlook Files\'
            - '\Documents\Outlook'
    filter_outlook:
        Image|endswith:
            - '\OUTLOOK.EXE'
            - '\outlook.exe'
    condition: (selection_pst_ost or selection_outlook_paths) and not filter_outlook
fields:
    - Image
    - TargetFilename
falsepositives:
    - Backup software copying Outlook PST files as part of user profile backups. Email archival tools like Mimecast or Barracuda that access local PST files.
level: high
tags:
    - attack.collection
    - attack.t1114.001
    - analytics.an0130
    - detection.det0047
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Legitimate Backup Software Accessing PST Files**
    * *The Issue:* Enterprise backup agents copy user profile directories — including Outlook PST/OST files — as part of regular scheduled backups. This generates high-severity alerts from legitimate backup processes.
    * *The Fix:* Build an allow-list of known backup agent process paths and service account contexts. Restrict alerts to cases where the accessing process is an interactive shell, scripting engine, or unknown binary rather than a known signed backup tool.

* **Problem 2: Exchange or Office 365 Migration Tools**
    * *The Issue:* During email migrations (e.g., migrating from on-premises Exchange to Office 365), Microsoft-provided tools like `PST Capture` or third-party tools legitimately open and process PST files. These would trigger the rule.
    * *The Fix:* Schedule migration windows and temporarily suppress alerts during approved migration activities. Alternatively, scope the rule to alert only when PST access occurs outside business hours or from unexpected host types (e.g., end-user workstations rather than migration servers).

* **Problem 3: In-Memory Email API Collection (MAPI)**
    * *The Issue:* Sophisticated adversaries can use the MAPI (Messaging Application Programming Interface) to directly query Outlook's data store through COM automation without ever touching PST/OST files on disk. No file event is generated.
    * *The Fix:* Monitor for suspicious Office COM automation by detecting `OUTLOOK.EXE` spawning child processes or making outbound network connections immediately after being launched by a non-user process. Complement with PowerShell Script Block Logging detecting Outlook COM object instantiation (`New-Object -ComObject Outlook.Application`).
