### **1. Technique Breakdown: T1123**

* **What it is:** **Audio Capture**. Adversaries capture audio from the host microphone using local APIs or recording tools. They use this capability for room monitoring or industrial espionage. On Windows endpoints, audio recording requires interacting with the Windows Multimedia API or DirectSound, which involves loading libraries like `winmm.dll` or `dsound.dll`. Identifying unsigned or anomalous processes loading these DLLs is a primary host-based detection approach.
* **Log Source Requirements:** Sysmon Library Load logs (Event ID 7) or process creation logs (Event ID 1).
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 7 logs when applications load `winmm.dll` or `dsound.dll`. Wazuh correlates these to trigger alerts.
    * **NIDS (Suricata + Zeek): NO.** Network sensors monitor IP streams and cannot track physical audio card capture states.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 7 (Library Load)** to detect unsigned or anomalous applications loading the core Windows multimedia/audio libraries (`winmm.dll` or `dsound.dll`) for recording.

```yaml
title: Collection - Anomaly Audio Capture Library Load (AN0619)
id: 67879061-32be-4edb-83c3-66c3d77a1a5c
status: experimental
description: Detects unsigned or non-standard executables loading Windows multimedia and audio recording DLLs (winmm.dll, dsound.dll), indicating potential unauthorized microphone recording.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: image_load
    product: windows
    # Relies on Sysmon Event ID 7 collected via Wazuh
detection:
    selection_dll:
        ImageLoaded|endswith:
            - '\winmm.dll'
            - '\dsound.dll'
    filter_signed:
        # Exclude known web conferencing and system media programs
        Image|endswith:
            - '\chrome.exe'
            - '\msedge.exe'
            - '\teams.exe'
            - '\zoom.exe'
            - '\skype.exe'
            - '\slack.exe'
            - '\discord.exe'
            - '\audacity.exe'
            - '\obs64.exe'
            - '\SoundRecorder.exe'
    condition: selection_dll and not filter_signed
fields:
    - Image
    - ImageLoaded
falsepositives:
    - Authorized corporate meeting applications or screen recording packages not covered in the static exclusion list.
level: high
tags:
    - attack.collection
    - attack.t1123
    - analytics.an0619
    - detection.det0221
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: WASAPI / Audio Graph API Usage**
    * *The Issue:* Modern Windows 10/11 applications often use the Windows Audio Session API (WASAPI) or the newer AudioGraph namespace, which loads different libraries (like `audioclient.dll` or `AudioSes.dll`), bypassing `winmm.dll`/`dsound.dll` checks.
    * *The Fix:* Add a complementary rule tracking loads of WASAPI libraries (`audioclient.dll`) by unsigned binaries.

* **Problem 2: Web Browsers (Meeting tools)**
    * *The Issue:* Users run meeting tools directly from browsers (e.g. Google Meet or Jitsi in Chrome/Edge), which legitimately load multimedia DLLs to access the microphone.
    * *The Fix:* Ensure standard web browsers (`chrome.exe`, `msedge.exe`, `firefox.exe`) are whitelisted, and verify their digital signature validity.

* **Problem 3: Virtual Audio Cable / Loopback**
    * *The Issue:* Attackers can record system audio loopbacks using custom audio driver software, which loads virtual drivers instead of system sound libraries.
    * *The Fix:* Monitor driver installation logs (UserPnp Event ID 20001) for class `MEDIA` indicating new virtual audio cards being registered.
