### **1. Technique Breakdown: T1207**

* **What it is:** **Rogue Domain Controller**. Adversaries register a rogue Domain Controller (DC) in the Active Directory (AD) environment (a technique commonly known as DCShadow) to inject malicious objects (like changing user passwords, SID history, or group memberships) without triggering standard monitoring controls. This relies on replicating changes directly to the legitimate DC via Active Directory replication protocols. Detection focuses on monitoring directory service additions/modifications (such as `nTDSDSA` object class changes in the configuration partition), unusual DRSUAPI (Directory Replication Service) RPC calls originating from non-DC hosts, or Kerberos ticket requests (Event 4769) for DRS SPNs by non-DC machines.
* **Log Source Requirements:** Windows Security Event Log Event ID 5136 (AD changes), Event ID 4662 (Object access), or Event ID 4769 (Kerberos ticket requests).
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Host logs on the Active Directory Domain Controllers capture Event ID 5136 for object alterations and Event ID 4769 for Kerberos service tickets.
    * **NIDS (Suricata + Zeek): YES.** Network filters capture DRSUAPI replication calls (such as `DrsReplicaAdd` or `DrsAddEntry`) between non-DC computer IPs and the DC on port 135/rpc.

### **2. Custom Sigma Rule**

This rule utilizes **Windows Security Event ID 4769 (Kerberos Service Ticket Requested)** to detect non-Domain Controller systems requesting service tickets for the Directory Replication Service (DRS) SPN GUID (`E3514235-4B06-11D1-AB04-00C04FC2DCD2`), suggesting DCShadow or replication abuse.

```yaml
title: Rogue Domain Controller - Kerberos DRS SPN Request by Non-DC Host (AN0770)
id: 33b5dfcd-fce4-48f1-9b11-70c583e472e8
status: experimental
description: Detects Kerberos service ticket requests (Event ID 4769) for the Directory Replication Service (DRS) SPN class GUID by computer accounts not belonging to the Domain Controllers group.
author: Krishna Gupta
date: 2026-06-08
logsource:
    product: windows
    service: security
    # Requires Kerberos Service Ticket auditing enabled on DCs
detection:
    selection_event:
        EventID: 4769
    selection_spn:
        # Directory Replication Service SPN GUID
        ServiceName|contains: 'E3514235-4B06-11D1-AB04-00C04FC2DCD2'
    filter_dc:
        # Exclude legitimate Domain Controller computer accounts (usually end in $)
        # This can be baselined to match only approved DC computer account names
        TargetUserName|endswith: '$'
    condition: selection_event and selection_spn and not filter_dc
fields:
    - EventID
    - ServiceName
    - TargetUserName
falsepositives:
    - Legitimate Exchange server directory service sync tasks or AD backup software.
level: critical
tags:
    - attack.defense_evasion
    - attack.t1207
    - analytics.an0770
    - detection.det0276
```

title: Rogue Domain Controller - Kerberos DRS SPN Request by Non-DC Host (OCSF-Normalized)

    category: system
    product: ocsf

    condition: selection_auth and selection_spn and not filter_dc

    - authentication.auth_protocol

    - Normal DC to DC replication.
level: critical

    - attack.defense_evasion

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Missing Kerberos Service Ticket Auditing**
    * *The Issue:* If Kerberos Service Ticket Auditing is disabled or filtered on Domain Controllers to reduce event volume, Event ID 4769 will not be logged.
    * *The Fix:* Enable "Audit Kerberos Service Ticket Operations" under the Advanced Audit Policy Configuration on all DCs.

* **Problem 2: Abuse of DC computer accounts (Impersonation)**
    * *The Issue:* If an attacker compromises a legitimate Domain Controller computer account and runs DCShadow, the computer account endswith `$` filter will ignore the activity.
    * *The Fix:* Correlate DRS ticket requests with the source IP address (Event ID 4769 Client Address). Confirm that the requesting IP belongs to the subnet of the designated DC host, and monitor for sudden logins of DC accounts from workstation subnets.

* **Problem 3: Schema partition changes (Noise)**
    * *The Issue:* Legitimate schema upgrades (e.g., deploying Exchange, SCCM, or Windows Server updates) modify objects in the configuration partition, mimicking DCShadow.
    * *The Fix:* Ensure schema modifications are pre-approved and temporarily whitelist the administrative account conducting the upgrade.
