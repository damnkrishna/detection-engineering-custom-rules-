### **1. Technique Breakdown: T1553.002**

* **What it is:** **Code Signing**. Adversaries abuse code signing to bypass security controls (like Windows Defender Application Control/AppLocker) that filter unsigned or untrusted binaries. They accomplish this by signing malicious code with stolen certificates, purchasing certificates using fake identities, or generating self-signed certificates and installing them into the victim's trusted root store.
* **Log Source Requirements:** Endpoint logs capturing process creation or module loads with associated digital signature metadata (e.g., Sysmon Event ID 7 for Image Load or Event ID 1 for Process Creation).
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 7 (Image Loaded) captures the file signature status (`Signed`, `Signature`, `SignatureStatus`) for loaded DLLs and EXEs. Wazuh can parse this to alert on revoked or invalid states.
* **NIDS (Suricata + Zeek): NO.** Code signing validation is an endpoint-local cryptographic process. Network tools cannot verify the validity or signature status of binaries in transit.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 7 (Image Loaded)** to detect DLLs or executables loaded from suspicious, user-writable directories (like `%TEMP%`, `C:\Users\Public\`, or `%APPDATA%`) that have an invalid, expired, or revoked digital signature status.

```yaml
title: Execution of DLL with Suspicious or Revoked Code Signature (AN0643)
id: a7e3d81b-5c2f-4b92-8c7a-5f6d7e8a9b0e
status: experimental
description: Detects the loading of images (DLLs/EXEs) from user-writable directories that possess an invalid, expired, or explicitly revoked digital signature.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: image_load
    product: windows
    # Relies on Sysmon Event ID 7 collected via Wazuh
detection:
    selection_paths:
        ImageLoaded|contains:
            - '\AppData\Local\Temp\'
            - '\Users\Public\'
            - '\Windows\Temp\'
            - '\AppData\Roaming\'
    selection_signature_status:
        SignatureStatus:
            - 'invalid'
            - 'revoked'
            - 'expired'
    condition: selection_paths and selection_signature_status
falsepositives:
    - Legacy corporate applications compiled internally with expired certificates executing from user directories.
    - Specialized software components performing auto-updates into local user profiles.
level: high
tags:
    - attack.defense_evasion
    - attack.t1553.002
    - analytics.an0643
    - detection.det0230
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Stolen but Cryptographically Valid Certificates**
* *The Issue:* The most sophisticated attackers use cryptographically valid certificates stolen from legitimate software vendors (e.g., LAPS, Nvidia) or purchased from underground marketplaces. Because the certificate is valid and not yet revoked, `SignatureStatus` will show as `valid`, completely bypassing this signature-status rule.
* *The Fix:* You must monitor for anomalous combinations of publisher metadata and execution context. For example, alert when a binary signed by "Nvidia Corporation" executes from a temporary folder and spawns `cmd.exe` or makes outbound network connections.


* **Problem 2: Performance Overhead of Image Load Logging**
* *The Issue:* Sysmon Event ID 7 (Image Loaded) logs every single DLL loaded by every process on the system. Enabling this globally will cause severe disk I/O and CPU overhead, and flood the SIEM with high-volume logs.
* *The Fix:* Scope Sysmon configuration rules tightly. Only log image loads for high-risk processes (like `explorer.exe`, `lsass.exe`, scripting hosts, or browsers) or only for files loaded from user-writable directories.


* **Problem 3: Self-Signed Root Certificate Installation**
* *The Issue:* If attackers have administrator privileges, they can generate their own self-signed CA certificate, install it into the system's Root Trust Store, and sign their malware. The signature status will show as `valid` because the system now trusts their root certificate.
* *The Fix:* Couple this rule with detections for trust control subversion (MITRE T1553.004 / AN0153), monitoring the registry paths where root certificates are added (like `HKLM\SOFTWARE\Microsoft\SystemCertificates\ROOT`).
