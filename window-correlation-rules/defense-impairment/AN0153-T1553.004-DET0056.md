### **1. Technique Breakdown: T1553.004**

* **What it is:** **Install Root Certificate**. Adversaries install untrusted root certificates into the victim's Trusted Root Certification Authorities store to subvert trust controls. Once installed, the operating system and web browsers will trust any TLS/SSL certificate signed by the adversary's certificate authority (CA). This allows adversaries to perform middle-person (MitM) inspection of encrypted traffic, bypass code signing restrictions (allowing malware to run as "trusted" signed software), or establish persistence.
* **Log Source Requirements:** Endpoint logs capturing process execution and command line parameters (specifically administrative certificate utility tools like `certutil.exe`, `certmgr.exe`, or PowerShell command-lines).
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 (Process Creation) logs the execution of utilities like `certutil.exe`, `certmgr.exe`, or PowerShell cmdlets with parameters containing flags like `-addstore` or `/add` directed at the `root` store.
* **NIDS (Suricata + Zeek): NO.** Certificate store modification is a host-local configuration change. It does not produce a distinct network signature (though network tools may observe the resulting decrypt-and-inspect MitM activity later).

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect command-line installations of certificates into the Windows Trusted Root Certification Authorities store using `certutil.exe`, `certmgr.exe`, or PowerShell.

```yaml
title: Installation of Root Certificate via CLI (AN0153)
id: b3c8d1e2-4f3b-4a2e-9d8c-5b6c7d8e9f0a
status: experimental
description: Detects command-line execution of certutil.exe, certmgr.exe, or PowerShell cmdlets adding a certificate to the local Trusted Root Certification Authorities store.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_certutil:
        - Image|endswith: '\certutil.exe'
        - OriginalFileName: 'CertUtil.exe'
    selection_certutil_args:
        CommandLine|contains|all:
            - '-addstore'
            - 'root'
    selection_certmgr:
        - Image|endswith: '\certmgr.exe'
        - OriginalFileName: 'certmgr.exe'
    selection_certmgr_args:
        CommandLine|contains|all:
            - '/add'
            - 'root'
    selection_powershell:
        - Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
        - OriginalFileName:
            - 'PowerShell.EXE'
            - 'pwsh.dll'
    selection_powershell_cmdlets:
        CommandLine|contains|all:
            - 'Import-Certificate'
            - 'Root'
    condition: (selection_certutil and selection_certutil_args) or (selection_certmgr and selection_certmgr_args) or (selection_powershell and selection_powershell_cmdlets)
falsepositives:
    - Internal IT administrator scripts deployed to distribute enterprise PKI root certificates.
    - Security agent or VPN installations that require installing custom root certificates.
level: high
tags:
    - attack.defense_evasion
    - attack.t1553.004
    - analytics.an0153
    - detection.det0056
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Registry-Level Root Certificate Injection (Bypassing CLI tools)**
* *The Issue:* Attackers with administrative access can write the certificate binary data directly to the registry under the SystemCertificates keys (e.g. `HKLM\SOFTWARE\Microsoft\SystemCertificates\Root\Certificates\<Thumbprint>\Blob`) using native APIs, `.reg` import files, or custom scripts without calling `certutil` or `certmgr`. This process command-line rule will not see it.
* *The Fix:* Enable registry auditing and monitor Sysmon Event ID 12/13 (Registry Event) or Windows Security Event ID 4657 targeting keys matching `\Microsoft\SystemCertificates\Root\Certificates\`.


* **Problem 2: Execution from Alternate Binary Paths or Renamed Binaries**
* *The Issue:* Attackers can rename `certutil.exe` or `certmgr.exe` to a non-standard name (e.g., `update.exe`) or load the certificate using a custom C++ application that calls the CryptoAPI `CertAddCertificateContextToStore`.
* *The Fix:* Monitor the process execution by using `OriginalFileName` (e.g. `CertUtil.exe`) or monitor API invocations using Sysmon Event ID 10 (ProcessAccess) or ETW (Event Tracing for Windows) providers like `Microsoft-Windows-CAPI2`.


* **Problem 3: Standard Administrative/Software Noise**
* *The Issue:* Corporate environment domain administrators regularly deploy new enterprise certificates, and legitimate local software (e.g., Docker, VPN clients, internal proxies) can add root certificates during installation.
* *The Fix:* Baselines of known-good certificates and exclusions for verified automated software deployments or specific parent processes (like SCCM `ccmexec.exe`).
