### **1. Technique Breakdown: T1499.002**

* **What it is:** **Endpoint DoS: Service Exhaustion Flood**. Adversaries degrade the availability of critical host applications (like local web services, database services, or API endpoints) by flooding them with high-frequency network connection requests (such as TCP SYN floods, slow-connection attacks, or TLS renegotiations). Detections monitor for execution of load testing/flooding tools or command-line scripting interpreters executing connection loops targeting web services.
* **Log Source Requirements:** Endpoint logs capturing process creation (Sysmon Event ID 1 / Windows Security Event ID 4688) or network connection logs (Sysmon Event ID 3).
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 logs CLI command parameters for flooding/testing utilities. Sysmon Event ID 3 captures outbound socket connections. Wazuh can group and count these events to identify threshold anomalies.
* **NIDS (Suricata + Zeek): YES.** Zeek `conn.log` captures connection rate spikes targeting specific application ports.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect the execution of known load testing or HTTP flooding utilities (like `ab.exe` or `slowhttptest.exe`) or scripting engines executing rapid connection loops.

```yaml
title: Potential Endpoint Service Exhaustion Flood Tool Execution (AN0489)
id: 82fb95e2-2fa9-4a85-80fb-2d5a50d399f3
status: experimental
description: Detects the execution of known load testing or HTTP flooding utilities (like ab.exe or slowhttptest) or scripting engines running parameters indicative of a service exhaustion flood.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_tools:
        - Image|endswith:
            - '\ab.exe'
            - '\slowhttptest.exe'
            - '\hping3.exe'
        - OriginalFileName:
            - 'ab.exe'
            - 'slowhttptest.exe'
            - 'hping3.exe'
    selection_scripts:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\cmd.exe'
    selection_script_args:
        CommandLine|contains:
            - 'while($true)'
            - 'while(1)'
            - 'for /l'
        CommandLine|contains:
            - 'Invoke-WebRequest'
            - 'Invoke-RestMethod'
            - 'curl'
            - 'wget'
    condition: selection_tools or (selection_scripts and selection_script_args)
fields:
    - CommandLine
    - Image
    - OriginalFileName
falsepositives:
    - Authorized application load testing conducted by QA teams or web developers within testing subnets.
level: medium
tags:
    - attack.impact
    - attack.t1499.002
    - analytics.an0489
    - detection.det0173
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Distributed Denial of Service (DDoS) / External Floods**
* *The Issue:* Real service exhaustion floods are distributed (originating from thousands of external botnet IPs) and target internal services. Since the attack traffic originates from outside the host and the local host only generates incoming socket logs (not process creation or outbound connections), process-creation or outbound network connection rules on the victim server will not alert.
* *The Fix:* Implement perimeter firewall or load balancer connection limits, and configure SIEM correlation rules that flag high rates of incoming TCP connections (Windows Security Event ID 5156) from multiple unique external IPs.


* **Problem 2: Stealthy Slow-Rate Floods (Slowloris)**
* *The Issue:* Attacks like Slowloris use very low transmission rates to keep connections open as long as possible, exhausting thread pools without generating a massive burst or rate spike, bypassing simple volume-threshold alerts.
* *The Fix:* Configure web server timeout thresholds (e.g. limiting connection lifetimes and header timeouts) and monitor application server thread pool exhaustion logs.


* **Problem 3: Standard Performance/Load Testing Noise**
* *The Issue:* QA developers running benchmark tools (like ApacheBench) during staging deployment audits will trigger false alerts.
* *The Fix:* Whitelist specific QA developer subnets and schedule test windows, or exclude testing IP ranges from active paging alerts.
