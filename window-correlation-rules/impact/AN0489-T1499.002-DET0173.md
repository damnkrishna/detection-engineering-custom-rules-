### 1. Technique Breakdown: T1499.002

* What it is: Endpoint DoS: Service Exhaustion Flood. Adversaries degrade the availability of critical host applications (like local web services, database services, or API endpoints) by flooding them with high-frequency network connection requests (such as TCP SYN floods, slow-connection attacks, or TLS renegotiations). Detections monitor for execution of load testing/flooding tools or command-line scripting interpreters executing connection loops targeting web services, and the resulting high-frequency outbound network connections.
* Log Source Requirements: Host process creation and command line logs (Sysmon Event ID 1 / Windows Security Event ID 4688) tracking execution, and network connection logs (Sysmon Event ID 3).
* Coverage Check:
  * HIDS (Sysmon + Windows Defender): YES. Sysmon Event ID 1 logs CLI command parameters for flooding/testing utilities. Sysmon Event ID 3 captures outbound socket connections.
  * Windows Security Logs: YES. Standard Security Logs track process execution (Event ID 4688) containing the command line arguments.
* Log Sources Covered:
  - Sysmon Event ID 1 (process_creation)
  - Sysmon Event ID 3 (network_connection)
* Log Sources Missing / Unused:
  - None.
* Conclusion: Service exhaustion flood tool execution can be detected using process creation and network connection logs.

### 2. Custom Sigma Rule

The detection logic is split into command-line utility execution and outbound network connection monitoring.

Rule 1 of 2: Potential Endpoint Service Exhaustion Flood Tool Execution via CLI (Process Creation)
```yaml
title: Potential Endpoint Service Exhaustion Flood Tool Execution via CLI (AN0489-A)
id: 82fb95e2-2fa9-4a85-80fb-2d5a50d399f3
status: experimental
description: Detects the execution of known load testing or HTTP flooding utilities (like ab.exe or slowhttptest) or scripting engines running parameters indicative of a service exhaustion flood.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
detection:
    selection_tools:
        - Image|endswith:
            - '\ab.exe'
            - '\slowhttptest.exe'
            - '\hping3.exe'
        - OriginalFileName:
            - 'ab.exe'
            - 'slowhttptest.exe'
            - 'hping3.exe'
    selection_scripts:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\cmd.exe'
    selection_script_loop:
        CommandLine|contains:
            - 'while($true)'
            - 'while(1)'
            - 'for /l'
    selection_script_cmd:
        CommandLine|contains:
            - 'Invoke-WebRequest'
            - 'Invoke-RestMethod'
            - 'curl'
            - 'wget'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: (selection_tools or (selection_scripts and selection_script_loop and selection_script_cmd)) and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Authorized application load testing conducted by QA teams or web developers within testing subnets.
level: medium
tags:
    - attack.impact
    - attack.t1499.002
    - analytic.an0489
    - detection.det0173
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Distributed Denial of Service (DDoS)
  * The Issue: Real service exhaustion floods are distributed and target internal services. Since the attack traffic originates from outside the host and the local host only generates incoming socket logs, process-creation or outbound network connection rules on the victim server will not alert.
  * The Fix: SIEM correlation rules that flag high rates of incoming TCP connections (Windows Security Event ID 5156) from multiple unique external IPs.

* Problem 2: Stealthy Slow-Rate Floods (Slowloris)
  * The Issue: Slow-rate floods use very low transmission rates to keep connections open, bypassing simple volume-threshold alerts.
  * The Fix: Configure web server timeout thresholds and monitor application server thread pool exhaustion logs.

* Problem 3: Standard Performance/Load Testing Noise
  * The Issue: QA developers running benchmark tools during staging deployment audits will trigger false alerts.
  * The Fix: Whitelist specific QA developer subnets and schedule test windows.
