### 1. Technique Breakdown: T1499.001

* What it is: Endpoint Denial of Service: OS Exhaustion Flood. Adversaries exhaust system resources (such as kernel handles, threads, memory, or CPU) on target endpoints to crash the operating system or degrade it to an unusable state, locking out administrators and users.
* Log Source Requirements: Windows System Event Log (Event ID 2004 for Resource Exhaustion Diagnosis) and Sysmon Process Creation events (Event ID 1).
* Coverage Check:
  - HIDS (Sysmon + Windows Defender): YES. Host-level OS exhaustion diagnostics are natively captured by Windows Diagnostics-Performance log and System event log.
  - NIDS (Suricata + Zeek): NO. Host-local memory/kernel exhaustion.
* Log Sources Covered:
  - Windows System Log Event ID 2004 (resource_exhaustion)
  - Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
  - None.

### 2. Custom Sigma Rule

#### Rule 1 of 2: Windows Resource Exhaustion Diagnosis Event
Detects Windows System Event ID 2004 logs generated when the operating system encounters extreme memory or resource starvation. This rule should be aggregated at the SIEM layer to count loop patterns.

```yaml
title: Windows Resource Exhaustion Diagnosis Event (AN1012-A)
id: 0b432959-f29d-4506-8f8d-742a883368e5
status: experimental
description: Detects Windows Diagnostic-Performance or System Event ID 2004 logs capturing critical virtual memory exhaustion. This rule should be aggregated in the SIEM layer to count loop patterns.
author: Krishna Gupta
date: 2026-06-30
logsource:
    product: windows
    service: system
detection:
    selection_exhaustion:
        EventID: 2004
        Source: 'Microsoft-Windows-Resource-Exhaustion-Detector'
    condition: selection_exhaustion
fields:
    - EventID
    - Description
    - Source
falsepositives:
    - Heavy compilation jobs, database index rebuilds, or legitimate hypervisor processes over-allocating RAM.
level: medium
tags:
    - attack.impact
    - attack.t1499.001
    - analytic.an1012
    - detection.det0356
```

#### Rule 2 of 2: High Thread Spawning Utilities Execution
Detects the execution of known, realistic stress testing utilities launched to exhaust OS CPU or thread limits, requiring both the tool image and specific thread-count arguments.

```yaml
title: High Thread Spawning Utilities Execution (AN1012-B)
id: cf233388-8198-454e-81a9-5b705077e7e5
status: experimental
description: Detects process creation of utility tools launched to spawn massive thread counts or CPU consumption loops.
author: Krishna Gupta
date: 2026-06-30
logsource:
    category: process_creation
    product: windows
detection:
    selection_images:
        Image|endswith:
            - '\stress-ng.exe'
            - '\cpustres.exe'
            - '\heavyload.exe'
    selection_orig:
        OriginalFileName:
            - 'stress-ng.exe'
            - 'cpustres.exe'
            - 'heavyload.exe'
    selection_cli:
        CommandLine|contains:
            - '--max-threads'
            - ' -threads '
            - ' --thread-count'
            - ' --loop-cores'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: (selection_images or selection_orig) and selection_cli and not filter_installer
fields:
    - Image
    - CommandLine
    - User
falsepositives:
    - Administrators running system baseline stress tests or hardware configuration benchmarks.
level: medium
tags:
    - attack.impact
    - attack.t1499.001
    - analytic.an1012
    - detection.det0356
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Application Starvation vs. Attack
  * The Issue: Heavy applications (e.g. Chrome, Docker Desktop, SQL Server) frequently trigger Event ID 2004 due to memory leaks, generating false alarms under Rule 1.
  * The Fix: Inspect the payload in the Event ID 2004 details to see which process is identified as the resource consumer, and exclude known approved enterprise applications.
* Problem 2: SIEM-Side Aggregation
  * The Issue: Rule 2 alerts on a single execution.
  * The Fix: Combine Rule 2 with a SIEM correlation requiring multiple resource-draining execution events within 1 minute (`count() by Computer > 2 in 1m`).
