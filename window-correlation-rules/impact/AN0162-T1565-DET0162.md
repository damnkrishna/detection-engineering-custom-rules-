### **1. Technique Breakdown: T1565**

* **What it is:** **Data Manipulation**. Adversaries modify structured data (such as SQL databases, SQLite files, audit logs, or financial logs) to cause operational disruption, alter transaction details, or conceal evidence of their activity. Detections monitor local file modification events targeting database formats (`.db`, `.sqlite`, `.mdf`) or audit logs (`.evtx`) by non-standard command shells or scripting engines.
* **Log Source Requirements:** Endpoint logs capturing file creation, modification, or write events (Sysmon Event ID 11 / Windows Security Event ID 4663).
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 11 logs file path names, extensions, and writing processes. Wazuh aggregates these activities to detect unauthorized writes.
* **NIDS (Suricata + Zeek): NO.** Local database file modification occurs entirely within the host filesystem. Network tools can audit SQL queries over network databases, but cannot track local file modifications.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 11 (File Create)** to detect database files (`.db`, `.sqlite`, `.mdf`) or system log files (`.evtx`) being created or modified by scripting hosts or command-line interpreters.

```yaml
title: Database or Log File Modification by Non-Database Process (AN0162)
id: 8d8ac882-8adc-4630-bf06-7df142bfe220
status: experimental
description: Detects command-line interpreters or scripting hosts modifying or creating database files (e.g., .db, .sqlite, .mdf) or system log files (.evtx), which can indicate unauthorized data manipulation or log tempering.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: file_event
    product: windows
    # Relies on Sysmon Event ID 11 collected via Wazuh
detection:
    selection_process:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\cmd.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\mshta.exe'
    selection_files:
        TargetFilename|endswith:
            - '.db'
            - '.sqlite'
            - '.sqlite3'
            - '.mdf'
            - '.ldf'
            - '.mdb'
            - '.accdb'
            - '.evtx'
    condition: selection_process and selection_files
falsepositives:
    - Legitimate administration scripts managing local SQLite databases or backing up event log files (.evtx).
level: medium
tags:
    - attack.impact
    - attack.t1565
    - analytics.an0162
    - detection.det0162
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Database Engine API Execution (SQL Injection)**
* *The Issue:* If the attacker has access to a database console (e.g. via SQL injection or compromised credentials), they can modify data inside database tables by running standard SQL queries (`UPDATE`, `DELETE`). This occurs entirely inside the database process (e.g. `sqlservr.exe` writing to `.mdf`), which does not spawn scripting hosts, bypassing file modification audits.
* *The Fix:* Enable query auditing within the database management system (DBMS) itself and monitor database transaction logs for anomalous modifications to critical tables.


* **Problem 2: Log Wiping via Clear-EventLog API**
* *The Issue:* Attackers can clear Windows event logs using built-in APIs (like `Clear-EventLog` in PowerShell or `wevtutil.exe cl`), which causes the system to wipe the `.evtx` file without spawning separate file modification events.
* *The Fix:* Monitor the execution of `wevtutil.exe` with clearing arguments (Event ID 1) and audit Security Event ID 1102 (The audit log was cleared).


* **Problem 3: Standard Application Database Syncs**
* *The Issue:* Many desktop applications (like web browsers, chat clients) use local SQLite databases to store history or local configs, and standard scripts may routinely query or backup these databases.
* *The Fix:* Restrict this rule to monitor changes to high-value server directories (such as database storage paths or the system Event Log folder `%SystemRoot%\System32\Winevt\Logs\`).
