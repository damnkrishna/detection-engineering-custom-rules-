### 1. Technique Breakdown: T1564.011

* What it is: Ignore Process Interrupts. Adversaries configure scripts or processes to suppress error handling, ignore interrupt signals, and continue executing silently regardless of failures. On Windows, this is most commonly observed in PowerShell scripts using `-ErrorAction SilentlyContinue` or `$ErrorActionPreference = 'SilentlyContinue'`, which prevents error messages from appearing in console output or event logs. This technique allows adversaries to run reconnaissance or exploitation commands silently even when some steps fail, reducing detection likelihood from error-based monitoring.
* Log Source Requirements: PowerShell Script Block Logs (Event ID 4104) and Sysmon process creation logs (Event ID 1).
* Coverage Check:
    * HIDS (Sysmon + Wazuh): YES. PowerShell Script Block Logging (Event ID 4104) captures the content of PowerShell scripts including error suppression parameters. Sysmon Event ID 1 captures PowerShell launches with `-ErrorAction` or `$ErrorActionPreference` in the command line.
    * NIDS (Suricata + Zeek): NO. Error suppression is a scripting-level construct that has no network representation.

### 2. Custom Sigma Rule

This rule utilizes PowerShell Script Block Logging (Event ID 4104) and Sysmon Event ID 1 to detect PowerShell scripts configured to silently suppress errors, which is a strong indicator of adversarial scripting attempting to avoid detection through error noise.

```yaml
title: PowerShell Silent Error Suppression for Evasion (AN0182)
id: 9a3f90f1-ab32-4acf-8fbf-4d9f22336a17
status: experimental
description: Detects PowerShell execution with error action preference set to SilentlyContinue or Ignore, used by adversaries to suppress error output and execute commands without alerting users or detection tools.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: ps_script
    product: windows
    # Relies on PowerShell Script Block Logging (Event ID 4104)
detection:
    selection_silence:
        ScriptBlockText|contains:
            - '-ErrorAction SilentlyContinue'
            - '-EA SilentlyContinue'
            - '$ErrorActionPreference = ''SilentlyContinue'''
            - '$ErrorActionPreference = "SilentlyContinue"'
            - '-ErrorAction Ignore'
            - '$ErrorActionPreference = ''Ignore'''
            - 'SilentlyContinue'
    selection_combined_with_execution:
        ScriptBlockText|contains:
            - 'Invoke-Expression'
            - 'IEX'
            - 'DownloadString'
            - 'WebClient'
            - 'Start-Process'
            - 'Invoke-Command'
    condition: selection_silence and selection_combined_with_execution
fields:
    - ScriptBlockText
falsepositives:
    - Legitimate administrative automation scripts that use SilentlyContinue to gracefully handle expected failures in deployment or configuration management tasks.
level: medium
tags:
    - attack.defense-evasion
    - attack.t1564.011
    - analytic.an0182
    - detection.det0067
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Ubiquity of SilentlyContinue in Legitimate Scripts
  * The Issue: -ErrorAction SilentlyContinue is an extremely common PowerShell idiom in legitimate scripts (configuration management, CI/CD pipelines, software deployment tools). Alerting on it in isolation produces massive noise.
  * The Fix: Require co-occurrence with execution primitives (IEX, WebClient.DownloadString, Invoke-Command) as this combination specifically indicates an attempt to silently execute remote or encoded content. The rule already implements this correlation — tune further by adding parent process context.

* Problem 2: Encoded Command Bypassing Script Block Logging
  * The Issue: Adversaries may base64-encode their entire payload (using powershell.exe -EncodedCommand) and only set $ErrorActionPreference within the encoded payload. The Script Block log captures the decoded script content, but only if Script Block Logging is enabled.
  * The Fix: Enforce PowerShell Script Block Logging and Transcription Logging via Group Policy. Complement with Sysmon Event ID 1 detection for -EncodedCommand or -enc combined with suspicious parent processes.

* Problem 3: Non-PowerShell Error Suppression (cmd.exe, Python)
  * The Issue: Error suppression also occurs in cmd.exe scripts (using 2>nul or >nul 2>&1) and Python/Bash scripts (in WSL). These don't produce PowerShell Script Block events.
  * The Fix: Add a companion rule detecting cmd.exe with command lines containing 2>nul or >nul 2>&1 combined with network commands (certutil, curl, bitsadmin) or other suspicious utilities.
