### 1. Technique Breakdown: T1133

* What it is: External Remote Services. Adversaries leverage external-facing remote access solutions (such as virtual private networks (VPNs) or remote desktop protocols (RDP)) to gain initial access to the internal network. Once they authenticate using compromised credentials, they immediately initiate host reconnaissance by spawning built-in system administration utilities (`whoami.exe`, `net.exe`, `ipconfig.exe`, `nltest.exe`) from the remote session shell.
* Log Source Requirements: Windows Security Event Log Event ID 4624 (Logon) and Sysmon process creation logs (Event ID 1).
* Coverage Check:
  * HIDS (Sysmon + Wazuh): YES. Windows Security log captures remote RDP connections (Logon Type 10) and network logins (Logon Type 3) along with the source IP address. Sysmon Event ID 1 captures the user session initiating system discovery commands.
  * NIDS (Suricata + Zeek): YES. Network logs track RDP and VPN connections to gateways, but host logs are needed to correlate the logon with subsequent shell actions.
* Log Sources Covered:
  - Sysmon Event ID 1 (process_creation)
  - Windows Security Event ID 4624 (authentication)
* Log Sources Missing / Unused:
  - None.
* Conclusion: External remote services authentication and follow-on execution can be detected using process creation and security logon logs.

### 2. Custom Sigma Rule

The detection logic is split into monitoring suspicious commands run in remote user sessions and monitoring successful remote logon events.

Rule 1 of 2: External Remote Services - Suspicious Command Execution Post-Remote Logon (Process Creation)
```yaml
title: External Remote Services - Suspicious Command Execution Post-Remote Logon (AN1004-A)
id: 5caaaa9d-ec1b-4eda-b30d-c638d1b44c1f
status: experimental
description: Detects the execution of system discovery or network configuration commands shortly after a successful RDP (Logon Type 10) or Network (Logon Type 3) logon event, indicating post-intrusion reconnaissance.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: process_creation
    product: windows
detection:
    selection_logon_context:
        LogonId|not: '0x3e7' # Exclude SYSTEM session
    selection_commands:
        - Image|endswith:
            - '\whoami.exe'
            - '\net.exe'
            - '\net1.exe'
            - '\ipconfig.exe'
            - '\nltest.exe'
            - '\systeminfo.exe'
            - '\quser.exe'
            - '\query.exe'
            - '\qwinsta.exe'
        - OriginalFileName:
            - 'whoami.exe'
            - 'net.exe'
            - 'net1.exe'
            - 'ipconfig.exe'
            - 'nltest.exe'
            - 'systeminfo.exe'
    condition: selection_logon_context and selection_commands
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - IT administrators logging in remotely to troubleshoot system issues or gather host configuration metrics.
level: high
tags:
    - attack.initial-access
    - attack.t1133
    - analytic.an1004
    - detection.det0354
```

Rule 2 of 2: External Remote Services - Successful Remote Logon Event (Windows Security)
```yaml
title: External Remote Services - Successful Remote Logon Event (AN1004-B)
id: 8b9fbae7-439b-4238-9bdc-60f065c94b8f
status: experimental
description: Detects successful remote desktop logons (Logon Type 10) or network logons (Logon Type 3), which are paths for external remote service logins.
author: Krishna Gupta
date: 2026-06-16
logsource:
    product: windows
    service: security
detection:
    selection_logon:
        EventID: 4624
        LogonType:
            - 3  # Network
            - 10 # Remote Interactive
    filter_common:
        TargetUserName|endswith: '$'
        TargetUserName:
            - 'ANONYMOUS LOGON'
            - 'SYSTEM'
    condition: selection_logon and not filter_common
fields:
    - EventID
    - IpAddress
    - LogonType
    - TargetUserName
falsepositives:
    - Legitimate administrative or user remote network logons.
level: medium
tags:
    - attack.initial-access
    - attack.t1133
    - analytic.an1004
    - detection.det0354
```

```xml
        actor.user.uid|not: 'S-1-5-18'

    - process.cmd_line
    - actor.user.name

    - unmapped.parent_cmd_line

    - attack.initial-access

```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Administrative Script Automation
  * The Issue: Automated IT monitoring servers use remote service accounts (Logon Type 3) to run routine inventory scripts (gathering network or user info), triggering high volumes of false alerts.
  * The Fix: Whitelist approved service account user names and exclude inventory script execution paths (e.g. paths matching corporate asset management agents).

* Problem 2: Tunneling RDP over SSH / HTTP (Port Forwarding)
  * The Issue: If an attacker tunnels RDP traffic through a local SSH tunnel or reverse HTTP proxy on the host, the Security log will record the Logon Type 10 source IP as local host (`127.0.0.1` or `::1`), hiding the external source.
  * The Fix: Monitor network socket creations by remote access processes or SSH services, and alert on connections to `127.0.0.1` on port 3389.

* Problem 3: Use of Administrative API Interfaces (WMI/WinRM)
  * The Issue: If the attacker connects via WinRM (PowerShell Remoting) or WMI rather than interactive RDP, the shell commands run under `wsmprovhost.exe` or `wmiprvse.exe` contexts, which may run silently without triggering desktop session baselines.
  * The Fix: Enable PowerShell operational log auditing (Event ID 4104) and monitor process spawns originating from the WinRM parent process (`wsmprovhost.exe`).
