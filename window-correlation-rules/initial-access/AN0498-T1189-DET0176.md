### **1. Technique Breakdown: T1189**

* **What it is:** **Drive-by Compromise**. Adversaries gain initial access by exploiting a user's web browser when they visit a compromised or malicious website. Successful browser exploitation is identified by the browser process (e.g., Chrome, Edge, Firefox) directly spawning shell interpreters, scripting hosts, binary loaders, or downloading and launching payloads from temporary user directories.
* **Log Source Requirements:** Sysmon process creation logs (Event ID 1) capturing parent-child process relationships and command-line arguments.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 provides detailed visibility when a browser process (e.g., `chrome.exe`) spawns a shell or script host.
    * **NIDS (Suricata + Zeek): YES.** Network monitoring can identify downloads of binary payloads with anomalous headers or from high-risk domains, but host-based process monitoring is needed to verify execution.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect web browsers spawning shell interpreters, scripting hosts, binary registration tools, or payload loaders, indicating potential exploit execution.

```yaml
title: Drive-by Compromise - Suspicious Child Process Spawned by Browser (AN0498)
id: 4bc0789f-5d87-43bb-86f3-637cef4eb0a0
status: experimental
description: Detects suspicious processes (e.g., cmd.exe, powershell.exe, wscript.exe, rundll32.exe, mshta.exe) spawned directly by web browser processes, which indicates browser exploitation or user opening dangerous downloaded files.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_parent:
        ParentImage|endswith:
            - '\chrome.exe'
            - '\msedge.exe'
            - '\firefox.exe'
            - '\brave.exe'
            - '\opera.exe'
            - '\iexplore.exe'
            - '\safari.exe'
    selection_child:
        - Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\mshta.exe'
            - '\rundll32.exe'
            - '\regsvr32.exe'
            - '\certutil.exe'
            - '\bitsadmin.exe'
            - '\curl.exe'
            - '\scrcons.exe'
        - OriginalFileName:
            - 'Cmd.Exe'
            - 'PowerShell.EXE'
            - 'wscript.exe'
            - 'cscript.exe'
            - 'mshta.exe'
            - 'rundll32.exe'
            - 'regsvr32.exe'
            - 'certutil.exe'
            - 'bitsadmin.exe'
            - 'curl.exe'
    condition: selection_parent and selection_child
fields:
    - Image
    - OriginalFileName
    - ParentImage
falsepositives:
    - Legitimate web applications running on localhost (e.g., local development servers, admin dashboards) that spawn shell windows.
    - Automated browser-based test tools (e.g. Selenium, Puppeteer) spawning command prompts to run testing scripts.
level: high
tags:
    - attack.initial-access
    - attack.t1189
    - analytics.an0498
    - detection.det0176
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Development Server localhost Exceptions**
    * *The Issue:* Web developers run local services (like Jupyter Notebooks, Node.js development servers, or local admin web GUIs) that legitimately spawn command prompts or shell tools, causing excessive alerting.
    * *The Fix:* Add exclusions to whitelist process chains when the command line matches local-host development setups, or when the parent browser process was started with specific developer command-line options.

* **Problem 2: Browser Extensions spawning helper applications**
    * *The Issue:* Native messaging browser extensions (like password managers, security scanners, or smart-card signing extensions) legitimately spawn helper binaries, which may trigger generic parent-child alerts.
    * *The Fix:* Add explicit whitelist exclusions for the specific, signed binary paths associated with verified native-messaging browser extensions.

* **Problem 3: Sandboxed Exploit Execution (No Child Process)**
    * *The Issue:* If a browser exploit does not spawn a new process on the system, but executes shellcode completely inside the browser process memory space (e.g. executing a remote web socket connection within Chrome's sandboxed renderer process), parent-child process checks will see nothing.
    * *The Fix:* Implement system exploit mitigation monitoring (DEP/ASLR enforcement, AppLocker, or Windows Defender Exploit Guard events) to detect injection attempts, and monitor browser network sockets for connections to unusual ports.
