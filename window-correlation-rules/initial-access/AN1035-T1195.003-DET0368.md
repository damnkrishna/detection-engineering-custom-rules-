### 1. Technique Breakdown: T1195.003

* What it is: Supply Chain Compromise: Compromise Hardware Supply Chain. Adversaries insert malicious physical modifications or subverted firmware (such as tampered UEFI/BIOS, customized network cards, or compromised baseboard management controllers) during manufacturing or distribution. Detecting this post-delivery requires monitoring host BIOS flashing utilities, TPM validation errors, or Secure Boot policy changes.
* Log Source Requirements: Sysmon process creation logs (Event ID 1) auditing firmware tools.
* Coverage Check:
  * HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 1 tracks BIOS flashing tool executions.
  * Windows Security/Defender Logs: NO. These sources do not capture low-level firmware changes directly, though UEFI/Secure Boot logs can be queried via advanced firmware interfaces.
* Conclusion: Standard BIOS firmware flashing tool executions can be detected via Sysmon process creation.

### 2. Custom Sigma Rule

This rule utilizes Sysmon Event ID 1 (Process Creation) to detect the execution of known firmware/BIOS flashing tools.

```yaml
title: Hardware Supply Chain - Firmware Flashing Tool Execution (AN1035)
id: 726cb1ab-0135-4b44-8dcb-5bd5254fb757
status: experimental
description: Detects the execution of known firmware/BIOS flashing tools, which may indicate unauthorized BIOS/firmware modification.
author: Antigravity
date: 2026-06-12
logsource:
    category: process_creation
    product: windows
detection:
    selection_process:
        Image|endswith:
            - '\flashrom.exe'
            - '\fwupd.exe'
            - '\afuwingu.exe' # AMI Firmware Update Utility
            - '\HpbiosUpdate.exe'
            - '\DellBiosProvider.exe'
            - '\WinFlash.exe'
    condition: selection_process
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Authorized IT firmware upgrades or hardware maintenance tasks by technicians.
level: high
tags:
    - attack.initial-access
    - attack.t1195.003
    - analytic.an1035
    - detection.det0368
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Routine OEM updates (Lenovo/HP/Dell automated updates)
  * The Issue: Vendor support software (like Lenovo Vantage or Dell SupportAssist) routinely checks and applies BIOS/firmware updates silently in the background, triggering alerts.
  * The Fix: Whitelist flashing utility executions when spawned by legitimate, signed vendor service wrappers (checking signature status and vendor parent path).

* Problem 2: Device driver loading of flash utilities
  * The Issue: Flash utilities often load kernel-mode drivers dynamically (e.g. winring0.sys) to talk to BIOS hardware. If the flashing tool executable itself is disguised, the direct process name check fails.
  * The Fix: Monitor the registry write events for new driver registrations (HKLM\System\CurrentControlSet\Services) corresponding to known low-level access drivers (like WinRing0).

* Problem 3: Off-line Firmware Flashing (ChIP programmer)
  * The Issue: If the adversary compromises the hardware supply chain by physically removing the BIOS chip and flashing it using a hardware programmer before shipment, no OS-level events will record the write.
  * The Fix: Rely on remote attestation services (such as Windows Defender System Guard and TPM-based measurements) to validate the system boot sequence against a known good PCR baseline on boot.
