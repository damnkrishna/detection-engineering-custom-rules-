### 1. Technique Breakdown: T1558.003

* What it is: Steal or Forge Kerberos Tickets: Kerberoasting. Adversaries abuse the Kerberos protocol to request Service Ticket (TGS) for accounts with Service Principal Names (SPNs) configured—usually highly privileged service accounts. Active Directory grants these tickets encrypted with the service account's password hash. The attacker extracts this ticket from memory and cracks it offline to get the cleartext password.
* Log Source Requirements: Host process creation and command line logs (Sysmon Event ID 1 / Windows Security Event ID 4688) tracking execution.
* Coverage Check:
  * HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 1 (Process Creation) is excellent for catching the enumeration phase (e.g., using native setspn.exe) or the execution of known tools like Rubeus.
  * Windows Security Logs: YES. Standard Security Logs track process execution (Event ID 4688) containing the command line arguments.
* Conclusion: Kerberoasting tool execution and native SPN query commands can be detected using process creation and command line logs.

### 2. Custom Sigma Rule

This rule utilizes Sysmon Event ID 1 (Process Creation) to detect native SPN enumeration using setspn.exe and the execution of the command-line utility Rubeus targeting Kerberoasting.

```yaml
title: Suspicious SPN Enumeration and Kerberoasting Activity (AN0444)
id: e5b6c7d8-2f3a-4b1c-9d0e-1a2b3c4d5e6f
status: experimental
description: Detects command-line parameters associated with Service Principal Name (SPN) enumeration via setspn.exe or direct Kerberoasting attacks using Rubeus.
author: Krishna Gupta
date: 2026-06-12
logsource:
    category: process_creation
    product: windows
detection:
    selection_setspn:
        - Image|endswith: '\setspn.exe'
        - OriginalFileName: 'setspn.exe'
    selection_setspn_args:
        CommandLine|contains:
            - '-q'
            - '-Q'
            - '/q'
            - '/Q'
    selection_setspn_query:
        CommandLine|contains:
            - '*/*'
    selection_rubeus:
        CommandLine|contains:
            - 'kerberoast'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: ((selection_setspn and selection_setspn_args and selection_setspn_query) or selection_rubeus) and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Active Directory administrators running legitimate SPN checks or audits.
    - Automated identity management platforms checking service account configurations.
level: high
tags:
    - attack.credential-access
    - attack.t1558.003
    - analytic.an0444
    - detection.det0157
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: The Missing DC Telemetry (The Biggest Gap)
  * The Issue: The absolute best way to detect Kerberoasting isn't actually Sysmon—it's Windows Security Event ID 4769 (A Kerberos service ticket was requested) gathered directly from the Domain Controllers. If an attacker runs a custom script purely in memory (bypassing Sysmon ID 1), Event 4769 on the DC is the only host-based way to catch the anomalous RC4 (0x17) encryption request downgrade.
  * The Fix: You must ensure your Wazuh agents are deployed to your Domain Controllers and are configured to ingest Security Event ID 4769, filtering for Ticket Options: 0x40810000 and Ticket Encryption Type: 0x17.

* Problem 2: "Targeted" Kerberoasting (Low and Slow)
  * The Issue: Traditional Kerberoasting alerts trigger when an attacker requests tickets for all SPNs in the domain at once. Advanced adversaries now perform "Targeted Kerberoasting"—they quietly enumerate AD, find a single, highly privileged service account (like a SQL service admin), and request one ticket.
  * The Fix: This defeats volume-based Zeek rules and DC log thresholds. To catch this, you need to set up "Honey SPNs" (fake, highly privileged-looking service accounts with uncrackable passwords) and alert immediately if any TGS request is made for them.

* Problem 3: PowerShell and .NET Abuse
  * The Issue: Attackers frequently use the Invoke-Kerberoast.ps1 script or native C# assemblies loaded into memory. Our Sigma rule above misses this entirely because it focuses on setspn.exe and Rubeus.exe.
  * The Fix: You need to ensure PowerShell Script Block Logging (Event ID 4104) is enabled and forwarded to Wazuh. You would write a supplementary rule looking for strings like System.IdentityModel.Tokens.KerberosRequestorSecurityToken inside the script blocks.
