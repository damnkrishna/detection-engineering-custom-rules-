### **1. Technique Breakdown: T1606.002**

* **What it is:** **Forge Web Credentials: SAML Tokens** (widely known as a **Golden SAML** attack). Adversaries who compromise an Identity Provider (IdP) like Active Directory Federation Services (AD FS) steal the token-signing certificate and the Distributed Key Manager (DKM) key. With these secrets, they can offline-forge perfectly valid SAML tokens. This allows them to bypass multi-factor authentication (MFA) and access federated cloud services (like Microsoft 365 or AWS) as any user in the domain, even if the user's password changes.
* **Log Source Requirements:**
* *Phase 1 (Theft):* Endpoint process execution, WMI querying, or file access monitoring on the AD FS server and Domain Controllers.
* *Phase 2 (Usage):* Cloud Identity Provider logs (e.g., Entra ID/Azure AD Sign-ins) or SaaS access logs.


* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): PARTIAL.** Sysmon will *not* see the forged token being used. However, it can catch the attacker executing tools on the AD FS server to extract the certificates and keys from the Windows Internal Database (WID) or via PowerShell.
* **NIDS (Suricata + Zeek): NO.** SAML assertions are passed securely inside encrypted HTTPS traffic directly between the client's browser and the cloud provider. Your on-premise NIDS stack is entirely blind to this payload.

### **2. Custom Sigma Rule**

Because your current stack lacks Cloud/SaaS logs, we cannot write a rule for the *usage* of the forged token (which happens off-network). Instead, this rule targets **Sysmon Event ID 1 (Process Creation)** on your AD FS servers to catch the critical *precursor* to T1606.002: adversaries using `sqlcmd.exe` or known tooling to query the WID for the AD FS configuration and token-signing certificates.

```yaml
title: Suspicious AD FS Database Query for SAML Certificate Extraction (AN0420)
id: 4f3a2b1c-8d7e-9f0a-1b2c-3d4e5f6a7b8c
status: experimental
description: Detects command-line execution attempting to query the Windows Internal Database (WID) to extract AD FS configuration and token-signing certificates, a precursor to Golden SAML token forging (T1606.002).
author: Krishna Gupta
date: 2026-06-05
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh on AD FS servers
detection:
    selection_sqlcmd:
        - Image|endswith: '\sqlcmd.exe'
        - OriginalFileName: 'SQLCMD.EXE'
    selection_pipe:
        CommandLine|contains:
            - 'np:\\.\pipe\microsoft##ssee\tsql\query'
            - 'np:\\.\pipe\WID\tsql\query'
    selection_db:
        CommandLine|contains:
            - 'AdfsConfiguration'
            - 'IdentityServerPolicy'
    selection_adfs_tools:
        CommandLine|contains:
            - 'ADFSpoof'
            - 'Export-AdfsCertificate'
    condition: (selection_sqlcmd and selection_pipe and selection_db) or selection_adfs_tools
falsepositives:
    - Rare AD FS backup or migration scripts executed by identity administrators.
level: critical
tags:
    - attack.credential_access
    - attack.defense_evasion
    - attack.t1606.002
    - analytics.an0420
    - detection.det0148

```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: The Cloud Blind Spot (The Ultimate Evasion)**
* *The Issue:* Your specific Analytics ID (AN0420) relies on a very specific correlation: detecting an access event to SaaS/O365 via SAML *without* a prior Kerberos TGT request for that user. Because your current stack is strictly Sysmon and Suricata/Zeek, you have zero visibility into the O365 access event itself. If the attacker already has the certificate, they will forge and use the token entirely outside your monitored infrastructure.
* *The Fix:* You must integrate cloud IdP logs (like Entra ID Sign-in logs or AWS CloudTrail) into Wazuh to perform the cross-environment correlation AN0420 requires.


* **Problem 2: WMI and API Extraction**
* *The Issue:* Advanced adversaries do not need to drop `sqlcmd.exe` or `ADFSpoof` onto the server. They can extract the token-signing certificates by querying the WMI namespace `ROOT\ADFS` or by using direct .NET API calls in memory. Sysmon Event ID 1 will completely miss this.
* *The Fix:* You need to configure Wazuh to monitor WMI Activity (Event IDs 5858, 5859, 5861) specifically targeting the AD FS namespaces.


* **Problem 3: DCsync for the DKM Key**
* *The Issue:* Stealing the token-signing certificate is only half the battle. To decrypt the certificate, the attacker also needs the DKM key, which is stored in Active Directory. They will typically use Mimikatz (`lsadump::dcsync`) or similar tools to pull this key from the Domain Controller.
* *The Fix:* You need a supplementary detection strategy focused on Domain Controllers, specifically looking for anomalous replication requests (Event ID 4662) originating from IPs that are not authorized Domain Controllers.
