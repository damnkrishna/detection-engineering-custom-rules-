### **1. Technique Breakdown: T1556**

* **What it is:** **Modify Authentication Process**. Adversaries modify authentication mechanisms to bypass access controls or intercept credentials. Because you didn't specify a sub-technique, we will target the most common and dangerous endpoint manifestation: **Password Filter DLLs and LSA modifications (T1556.002)**. Attackers register a malicious DLL in the Windows Local Security Authority (LSA) registry keys. Once registered, every time a user logs in or changes their password, the malicious DLL intercepts the cleartext password.
* **Log Source Requirements:** This requires robust registry monitoring to catch the specific keys being altered, and potentially file creation logs to catch the malicious DLL being dropped into `C:\Windows\System32`.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event IDs 12, 13, and 14 (Registry Events) are perfectly positioned to catch this modification. Wazuh will easily trigger an alert on these specific key paths.
* **NIDS (Suricata + Zeek): NO.** Altering the local LSA registry and loading a DLL into memory are purely host-based actions. Your network stack will remain completely quiet until the DLL actually tries to exfiltrate the stolen passwords over the network.

### **2. Custom Sigma Rule**

This rule leverages **Sysmon Registry Events (Event IDs 12, 13, 14)** to detect when an adversary attempts to register a new authentication package or password filter in the LSA registry keys.

```yaml
title: Suspicious LSA Authentication Package Modification (AN0287)
id: c1b49a55-8274-4b5c-a192-3c28f74e92b6
status: experimental
description: Detects modifications to the LSA Authentication, Notification, or Security Packages registry keys, indicating the potential installation of a malicious password filter DLL or authentication bypass (T1556 / T1556.002).
author: Krishna Gupta
date: 2026-06-05
logsource:
    category: registry_event
    product: windows
    # Relies on Sysmon Event IDs 12, 13, 14 collected via Wazuh
detection:
    selection_target:
        TargetObject|contains:
            - '\CurrentControlSet\Control\Lsa\Authentication Packages'
            - '\CurrentControlSet\Control\Lsa\Notification Packages'
            - '\CurrentControlSet\Control\Lsa\Security Packages'
            - '\CurrentControlSet\Control\Lsa\OSConfig\Security Packages'
    condition: selection_target
fields:
    - TargetObject
falsepositives:
    - Legitimate installation of enterprise identity and access management (IAM) software (e.g., Okta, CyberArk).
    - Deployment of organizational password synchronization utilities.
level: critical
tags:
    - attack.credential_access
    - attack.defense_evasion
    - attack.persistence
    - attack.t1556
    - attack.t1556.002
    - analytics.an0287
    - detection.det0104

```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Direct Memory Patching (Bypassing the Registry)**
* *The Issue:* Highly advanced adversaries (using tools like Mimikatz's `misc::memssp` module) do not bother with registry persistence. They inject their malicious code directly into the running `lsass.exe` process in memory to intercept passwords. Sysmon Registry events will be completely blind to this because the registry is never touched.
* *The Fix:* You must supplement this rule with **Sysmon Event ID 10 (Process Access)**. You need a rule looking for unauthorized processes requesting high-privilege access rights (like `0x1010` or `0x1410`) to the `lsass.exe` process.


* **Problem 2: The Scope of T1556 (Cloud & Network Blind Spots)**
* *The Issue:* T1556 is a massive technique category. It includes bypassing Multi-Factor Authentication (T1556.006) which happens entirely in the cloud (e.g., Azure AD or Okta), and modifying Network Device Authentication (T1556.004) which happens on routers/switches.
* *The Fix:* Your current Sysmon/Suricata stack cannot see cloud-based MFA fatigue attacks or token forging. To cover the *entirety* of T1556, you would eventually need to ingest IdP logs (like Azure AD sign-in logs) into Wazuh.


* **Problem 3: Authorized IAM Installations**
* *The Issue:* If your IT team pushes out a new password sync tool via SCCM, this rule will fire and create a critical false positive, as legitimate tools use the exact same registry keys.
* *The Fix:* You must baseline your environment. Add exclusions for known, signed binaries executed by authorized service accounts (e.g., `filter_okta: Details|contains: 'OktaPasswordFilter.dll'`).
