### **1. Technique Breakdown: T1110.002**

* **What it is:** **Brute Force: Password Cracking**. This involves adversaries attempting to recover usable, cleartext passwords from stolen cryptographic hashes (like the NTLM hashes they might have grabbed from the SAM dump in our previous rule). While adversaries *usually* do this offline on their own hardware, they occasionally drop and execute cracking utilities (like Hashcat or John the Ripper) directly onto compromised endpoints, especially if the target machine has high CPU/GPU compute power.
* **Log Source Requirements:** Since the actual cracking process happens entirely within the CPU/GPU, this requires endpoint telemetry focusing on process creation and command-line execution.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 (Process Creation) is the primary telemetry source here. Wazuh can easily parse this to identify known cracking binaries or their specific command-line flags.
* **NIDS (Suricata + Zeek): NO.** Password cracking is a localized, offline computational process. It generates absolutely zero network traffic, making Suricata and Zeek completely blind to the cracking phase itself (though they might catch the initial download of the cracking tool).

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect the execution of common password cracking utilities or their distinct command-line parameters on Windows hosts.

```yaml
title: Local Password Cracking Activity (AN0292)
id: 9b2d8e41-3a1f-4b92-8c7a-5f6d7e8a9b0c
status: experimental
description: Detects the execution of known password cracking utilities (like Hashcat or John the Ripper) or their associated command-line arguments on a local endpoint, indicating T1110.002.
author: Krishna Gupta
date: 2026-06-05
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_tools:
        - Image|endswith: '\hashcat.exe'
        - Image|endswith: '\john.exe'
        - OriginalFileName: 'hashcat.exe'
        - OriginalFileName: 'john.exe'
    selection_cmdline_hashcat:
        CommandLine|contains|all:
            - '-a '      # Attack mode
            - '-m '      # Hash type
    selection_cmdline_john:
        CommandLine|contains:
            - '--wordlist='
            - '--format=NT'
    condition: selection_tools or selection_cmdline_hashcat or selection_cmdline_john
fields:
    - CommandLine
    - Image
    - OriginalFileName
falsepositives:
    - Authorized penetration testing or red team engagements.
    - Password auditing conducted by the internal security team.
level: high
tags:
    - attack.credential_access
    - attack.t1110.002
    - analytics.an0292
    - detection.det0105

```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: The "Offline" Reality (The Ultimate Evasion)**
* *The Issue:* The biggest limitation is that an advanced adversary almost never cracks hashes on the victim's machine. They will exfiltrate the SAM hive (or NTDS.dit) to their own infrastructure and crack it offline.
* *The Fix:* This specific rule will not save you if the data leaves the network. You must rely heavily on detecting the *dumping* (our DET0085 rule) and the *exfiltration* (tuning Zeek/Suricata for large, anomalous outbound data transfers).


* **Problem 2: Binary Renaming & Custom Tools**
* *The Issue:* Attackers can rename `hashcat.exe` to `svchost.exe` or compile their own bespoke cracking scripts in Python or Go. The `selection_tools` block will fail if the binary name and PE metadata are stripped or altered.
* *The Fix:* You must rely on the command-line arguments (`selection_cmdline_hashcat`). However, you can also supplement this by using Wazuh to hunt for the presence of common wordlists (like `rockyou.txt`) touching the disk, or by tracking unusually high and sustained CPU/GPU spikes in your performance monitoring logs.


* **Problem 3: PowerShell In-Memory Execution**
* *The Issue:* If an attacker loads a cracking module entirely into memory via PowerShell (e.g., Invoke-Mimikatz variant functions), Sysmon Event ID 1 won't see the specific binary execution.
* *The Fix:* You need Script Block Logging (Event ID 4104) enabled in Windows and ingested into Wazuh to look for cracking syntax inside the raw PowerShell scripts.
