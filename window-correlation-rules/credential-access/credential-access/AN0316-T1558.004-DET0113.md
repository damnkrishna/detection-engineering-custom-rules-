### **1. Technique Breakdown: T1558.004**

* **What it is:** **Steal or Forge Kerberos Tickets: AS-REP Roasting**. Adversaries hunt for Active Directory user accounts that have the "Do not require Kerberos preauthentication" flag enabled. If this flag is set, anyone can request an Authentication Service (AS) ticket for that user. The Domain Controller will happily respond with an AS-REP message that contains a chunk of data encrypted with the user's password hash. The attacker saves this data and cracks it offline.
* **Log Source Requirements:** Detecting the *execution* requires endpoint command-line monitoring. Detecting the *actual attack* requires either Domain Controller Security logs (Event ID 4768) or Network Traffic Analysis parsing Kerberos.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 (Process Creation) is great for catching the command-line execution of tools like Rubeus, PowerView, or Impacket targeting these vulnerable accounts.
* **NIDS (Suricata + Zeek): YES.** Zeek's `kerberos.log` can monitor traffic on port 88 and detect the unique network signature of AS-REP roasting: an AS-REQ without pre-authentication followed by an AS-REP.

### **2. Custom Sigma Rule**

This rule leverages **Sysmon Event ID 1 (Process Creation)** to detect the execution syntax of the three most common frameworks used for AS-REP Roasting: Rubeus, PowerView/SharpHound, and Impacket's GetNPUsers.

```yaml
title: AS-REP Roasting Tool Execution (AN0316)
id: 8a4c3f1b-7d2e-491a-b60c-5e9f2d1a3b4c
status: experimental
description: Detects command-line parameters associated with AS-REP Roasting attacks, targeting accounts with Kerberos pre-authentication disabled to extract crackable hashes (T1558.004).
author: Krishna Gupta
date: 2026-06-05
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_rubeus:
        CommandLine|contains:
            - 'asreproast'
    selection_powerview:
        CommandLine|contains:
            - 'PreauthNotRequired'  # Catches Get-DomainUser filters
    selection_impacket:
        CommandLine|contains:
            - 'GetNPUsers'
    condition: selection_rubeus or selection_powerview or selection_impacket
falsepositives:
    - Internal security teams conducting routine Active Directory misconfiguration audits.
    - Automated IAM tools querying for vulnerable account flags.
level: high
tags:
    - attack.credential_access
    - attack.t1558.004
    - analytics.an0316
    - detection.det0113

```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: The "Rogue Device" Blind Spot**
* *The Issue:* Unlike Kerberoasting (which usually requires an authenticated user context first), AS-REP Roasting requires *no authentication*. An attacker can plug a rogue Linux laptop into a wall jack, point Impacket's `GetNPUsers.py` at your Domain Controller, and pull the hashes. Because they aren't executing the script on a corporate Windows machine, Sysmon sees absolutely nothing.
* *The Fix:* You must pivot to your **Zeek NIDS**. You need to write a Wazuh correlation rule analyzing Zeek's `kerberos.log` to look for sudden spikes in AS-REQ traffic from unmanaged IP addresses, or AS-REQs where the `success` flag is true but pre-authentication was explicitly bypassed.


* **Problem 2: The Domain Controller Telemetry Gap**
* *The Issue:* If an attacker uses an in-memory .NET assembly to roast accounts, Sysmon Event ID 1 won't catch the command line. The definitive host-based indicator is on the DC itself.
* *The Fix:* You need to ensure Wazuh is pulling Windows Security logs from your Domain Controllers, specifically looking for **Event ID 4768 (A Kerberos authentication ticket was requested)**. The exact filter you need to build is: `EventID=4768 AND Pre-Authentication Type=0 AND Ticket Encryption Type=0x17 (RC4)`.


* **Problem 3: Finding the Vulnerability vs. Stopping the Attack**
* *The Issue:* AS-REP roasting is a symptom of a configuration flaw. If the rule fires, the hashes have already been exfiltrated to the attacker's machine. The damage is instantly done.
* *The Fix:* Detection engineering is great, but preventative posture is better here. Your team should write a script to periodically query AD for `userAccountControl:1.2.840.113556.1.4.803:=4194304` (the LDAP filter for PreauthNotRequired) and disable that setting on any account that doesn't strictly need it for legacy application compatibility.
