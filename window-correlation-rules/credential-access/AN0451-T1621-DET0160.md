### **1. Technique Breakdown: T1621**

* **What it is:** **Multi-Factor Authentication Request Generation** (commonly known as MFA Fatigue or MFA Spamming). Adversaries who have already compromised a user's primary password repeatedly spam the user's mobile device with MFA push notifications. The goal is to annoy, confuse, or exhaust the user into accidentally (or intentionally) tapping "Approve" just to make the notifications stop.
* **Log Source Requirements:** This attack happens entirely at the authentication boundary. It requires Identity Provider (IdP) logs (e.g., Azure AD, Okta, Duo) or VPN Gateway authentication logs.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): NO (Currently).** Sysmon cannot see this because the attack does not execute on the Windows endpoint; it targets the cloud/IdP infrastructure and the user's phone.
* **NIDS (Suricata + Zeek): NO.** The network traffic for the authentication request happens over encrypted HTTPS between the attacker's machine and your cloud IdP. Your internal network sensors are completely blind to this.
* **The Fix:** To get coverage, you must configure **Wazuh to pull logs via API** from your IdP (e.g., using the Wazuh Office 365 or Okta integration).

### **2. Custom Sigma Rule**

Because your current Sysmon/Zeek stack cannot see this, I have written this Sigma rule targeting generic `authentication` logs. To make this rule work in your environment, you will need to forward your IdP or VPN logs into Wazuh.

This rule uses Sigma's thresholding capabilities to detect rapid, successive failed or ignored MFA prompts for a single user.

```yaml
title: Potential MFA Fatigue Attack (AN0451)
id: 5a2c4e6b-1d3f-4a8c-9b7e-0d1f2a3b4c5d
status: experimental
description: Detects a high volume of denied, ignored, or timeout MFA push notifications targeting a single user within a short timeframe, indicating an MFA Fatigue attack (T1621).
author: Krishna Gupta
date: 2026-06-05
logsource:
    category: authentication
    # Note: Requires integration with Azure AD, Okta, Duo, or VPN logs via Wazuh.
detection:
    selection_mfa_events:
        # These fields will need to be mapped to your specific IdP's schema
        action:
            - 'mfa_denied'
            - 'mfa_ignored'
            - 'mfa_timeout'
            - 'push_sent'
    condition: selection_mfa_events | count() >= 5
    timeframe: 10m
falsepositives:
    - Users experiencing genuine connectivity issues with their authenticator app.
    - A user accidentally triggering multiple logins due to a stalled application (like an email client stuck in an auth loop).
level: high
tags:
    - attack.credential_access
    - attack.t1621
    - analytics.an0451
    - detection.det0160

```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: The Telemetry Void (Your Biggest Issue)**
* *The Issue:* As mentioned, if you are strictly relying on Sysmon and Suricata/Zeek for this, you have zero visibility. An attacker can spam your users all day and your SIEM will be completely silent.
* *The Fix:* You must extend Wazuh's reach into the cloud using its native API integrations for O365, AWS, or Okta.


* **Problem 2: The "Successful" Bypass Alert**
* *The Issue:* The rule above only detects the *attempt* (the spamming). The most critical event is if the user actually clicks "Approve."
* *The Fix:* You need a secondary correlation rule. In a mature SIEM setup, you would correlate the alert above (5+ failed MFA attempts) with a `success` login event for that *same user* originating from the *same IP* within the next 5 minutes. If that sequence occurs, the alert level escalates from "High" to "Critical" because the attacker is now inside.


* **Problem 3: Mitigation Trumps Detection**
* *The Issue:* MFA Fatigue is a human-factor vulnerability. Staring at alerts while a user is being spammed is a losing battle.
* *The Fix:* From a defensive engineering standpoint, you should advocate for implementing **Number Matching MFA** (where the user must type a 2-digit number displayed on their screen into their phone) or rate-limiting push notifications at the IdP level. This fundamentally neutralizes T1621.
