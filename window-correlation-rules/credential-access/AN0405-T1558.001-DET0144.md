### **1. Technique Breakdown: T1558.001**

* **What it is:** **Steal or Forge Kerberos Tickets: Golden Ticket**. If an adversary compromises your Domain Controller and extracts the `KRBTGT` account password hash, they can use it to cryptographically forge their own Kerberos Ticket-Granting Tickets (TGTs). This "Golden Ticket" grants them unfettered, persistent administrative access to virtually any resource in the Active Directory domain, even if the user account they are impersonating has its password changed.
* **Log Source Requirements:** Detecting the *creation* of the ticket requires endpoint process/command-line monitoring. Detecting the *usage* of the ticket requires Network Traffic Analysis (NTA) parsing Kerberos protocols, or Domain Controller Security Event logs (Event IDs 4768 and 4769).
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 (Process Creation) can detect the command-line execution of popular forging tools like Mimikatz or Rubeus on compromised endpoints.
* **NIDS (Suricata + Zeek): YES (Highly Effective).** Zeek parses Kerberos traffic natively into `kerberos.log`. It is incredibly effective at spotting the network anomalies generated when a Golden Ticket is actually used against a service.

### **2. Custom Sigma Rule**

This rule targets the **HIDS (Sysmon)** side, focusing on Event ID 1 to catch the execution syntax of the two most common tools used to forge Golden Tickets: Mimikatz and Rubeus.

```yaml
title: Golden Ticket Forging Tool Execution (AN0405)
id: d4c3b2a1-1a2b-3c4d-5e6f-7a8b9c0d1e2f
status: experimental
description: Detects command-line parameters associated with the forging or injection of Kerberos Golden Tickets using tools like Mimikatz or Rubeus (T1558.001).
author: Krishna Gupta
date: 2026-06-05
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_mimikatz:
        CommandLine|contains|all:
            - 'kerberos::golden'
            - '/krbtgt:'
    selection_rubeus:
        CommandLine|contains|all:
            - 'golden'
            - '/krbtgt:'
            - '/domain:'
    selection_rubeus_inject:
        CommandLine|contains|all:
            - 'golden'
            - '/ptt'   # Pass-The-Ticket (injects the forged ticket into memory)
    condition: selection_mimikatz or selection_rubeus or selection_rubeus_inject
falsepositives:
    - Authorized red team engagements or adversary emulation exercises.
level: critical
tags:
    - attack.credential_access
    - attack.t1558.001
    - analytics.an0405
    - detection.det0144

```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: In-Memory Execution & API Abuse (The Evasion)**
* *The Issue:* An advanced threat actor will not drop `Rubeus.exe` to disk or run it through `cmd.exe`. They will use a C2 framework (like Cobalt Strike's `execute-assembly` or Covenant) to execute the tool entirely within the memory of a hijacked process. Sysmon Event ID 1 will see absolutely nothing.
* *The Fix:* **Pivot to your NIDS stack.** This is where your Zeek `kerberos.log` becomes critical. You need to write a Zeek script or Wazuh correlation rule analyzing Zeek logs for **RC4 Encryption Downgrades**. Historically, forged Golden Tickets default to RC4 encryption (`cipher=23`) instead of the modern AES-256 (`cipher=18`). If your environment is purely AES, an RC4 Kerberos ticket traversing the network is a massive red flag.


* **Problem 2: The "Overpass-the-Hash" Masking**
* *The Issue:* Modern attackers know that a standard 10-year Golden Ticket stands out. They will forge tickets that mimic the exact lifetime policies of your domain (usually 10 hours) and use AES-256 instead of RC4 to blend in with normal network traffic, blinding your Zeek rules.
* *The Fix:* You must ingest Domain Controller Security Logs (specifically Event ID 4769 - Kerberos Service Ticket Requested). A Golden Ticket bypasses the initial Authentication Service request. If you see a 4769 (TGS Request) for a user, but there is no corresponding 4768 (TGT Request) for that same user in the preceding 10 hours, it means they fabricated the TGT themselves.


* **Problem 3: KRBTGT Password Resets**
* *The Issue:* If the krbtgt account password hasn't been reset twice in the last year, any previously stolen hash remains valid forever. Your rules might trigger on an old, dormant backdoor re-entering the network.
* *The Fix:* Ensure that responding to this alert includes an immediate, double-reset of the krbtgt domain account to invalidate the cryptographic material the attacker is using.
