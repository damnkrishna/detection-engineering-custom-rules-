### **1. Technique Breakdown: T1201**

* **What it is:** **Password Policy Discovery**. Adversaries query local or domain password policies to understand account lockout thresholds, minimum password lengths, and complexity requirements. This informs credential attacks — for example, discovering a 10-attempt lockout threshold allows attackers to safely attempt 9 passwords per account without triggering lockouts. Common tools include `net.exe accounts`, `secedit.exe /export`, or PowerShell Active Directory cmdlets like `Get-ADDefaultDomainPasswordPolicy`.
* **Log Source Requirements:** Host process creation and command line logs (Sysmon Event ID 1), PowerShell Script Block Logs (Event ID 4104), and Windows Security Event Log (Event ID 4688).
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 captures execution of `net.exe`, `secedit.exe`, and PowerShell along with their command-line arguments.
    * **NIDS (Suricata + Zeek): NO.** Local password policy queries execute within the host OS. LDAP queries to domain controllers for policy information may leave network traces, but require host-level process correlation.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect execution of commands used to query password policies from local systems or Active Directory domains.

```yaml
title: Password Policy Discovery via CLI and PowerShell (AN0455)
id: a5745601-f38f-45f4-b908-edf1345decb1
status: experimental
description: Detects adversarial execution of commands querying local or domain password policy settings such as net accounts, secedit /export, or PowerShell AD cmdlets for password policy discovery.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_net:
        - Image|endswith: '\net.exe'
        - OriginalFileName: 'net.exe'
    selection_net_args:
        CommandLine|contains: ' accounts'
    selection_secedit:
        - Image|endswith: '\secedit.exe'
        - OriginalFileName: 'secedit.exe'
    selection_secedit_args:
        CommandLine|contains: '/export'
    selection_powershell:
        - Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
        - OriginalFileName:
            - 'PowerShell.EXE'
            - 'pwsh.dll'
    selection_powershell_args:
        CommandLine|contains:
            - 'Get-ADDefaultDomainPasswordPolicy'
            - 'Get-ADFineGrainedPasswordPolicy'
            - 'Get-LocalUser'
            - 'PasswordPolicy'
    condition: (selection_net and selection_net_args) or (selection_secedit and selection_secedit_args) or (selection_powershell and selection_powershell_args)
falsepositives:
    - Security compliance scripts or audit tools that query password policies as part of regular CIS benchmark assessments.
level: medium
tags:
    - attack.discovery
    - attack.t1201
    - analytics.an0455
    - detection.det0161
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Compliance and Audit Tools Generating Noise**
    * *The Issue:* Enterprise security compliance tools (e.g., Tenable Nessus, CyberArk, or CIS-CAT) regularly query password policies during scheduled scans. This generates alert noise every time a scan runs.
    * *The Fix:* Maintain an allow-list of known vulnerability scanner service accounts and scheduled scan task processes. Correlate the alert with the parent process — compliance tools should be the direct parent, not a command shell.

* **Problem 2: Policy Discovery via LDAP without CLI**
    * *The Issue:* Attackers can query password policies directly from domain controllers using LDAP queries against the `ms-DS-PasswordSettings-Container` or default domain policy object. This bypasses `net.exe` or PowerShell cmdlets.
    * *The Fix:* Enable directory service access auditing (Security Event ID 4662) on domain controllers for read accesses to policy containers, particularly from non-DC hosts.

* **Problem 3: Fine-Grained Password Policy Discovery via BloodHound or Similar Tools**
    * *The Issue:* Tools like BloodHound or SharpHound enumerate fine-grained password policies (PSOs) via LDAP enumeration in bulk. The individual LDAP queries may not trigger PowerShell-specific detection rules.
    * *The Fix:* Monitor for LDAP query patterns characteristic of bulk AD enumeration on domain controllers using network inspection or Windows ETW-based LDAP auditing. Alert on large volumes of LDAP reads from workstations in short windows.
