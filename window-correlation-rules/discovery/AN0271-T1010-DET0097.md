### 1. Technique Breakdown: T1010

* What it is: Application Window Discovery. Adversaries may enumerate open windows to identify active applications, discover visible user activity, or determine the presence of monitoring tools on a compromised host. On Windows, tools use Win32 API calls like `EnumWindows()` or `GetForegroundWindow()` to list all top-level window handles and their associated titles. This information is used for situational awareness, screenshot targeting, or keylogger targeting.
* Log Source Requirements: PowerShell Script Block Logging (Event ID 4104) and Sysmon process creation logs (Event ID 1).
* Coverage Check:
    * HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 1 captures spawning of PowerShell or scripting engines; Script Block logging captures the actual content of window enumeration cmdlets.
    * NIDS (Suricata + Zeek): NO. Window enumeration is a host-local operation using the Windows USER32 API and produces no network traffic.

### 2. Custom Sigma Rule

This rule utilizes Sysmon Event ID 1 (Process Creation) and PowerShell Script Block Logging (Event ID 4104) to detect PowerShell or scripting hosts invoking window enumeration keywords.

```yaml
title: Application Window Enumeration via Scripting Host (AN0271)
id: ee6d9543-b752-4ee7-870d-209907f63480
status: experimental
description: Detects processes using PowerShell or scripting utilities to enumerate open application windows via Win32 API calls or cmdlets, which may indicate reconnaissance or data collection activity.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: ps_script
    product: windows
    # Relies on PowerShell Script Block Logging (Event ID 4104)
detection:
    selection_keywords:
        ScriptBlockText|contains:
            - 'EnumWindows'
            - 'GetForegroundWindow'
            - 'GetWindowText'
            - 'FindWindow'
            - '[System.Runtime.InteropServices.Marshal]'
    condition: selection_keywords
fields:
    - ScriptBlockText
falsepositives:
    - Legitimate automation or accessibility tools (e.g., AutoHotkey, UI testing frameworks) that enumerate windows for productivity workflows.
level: medium
tags:
    - attack.discovery
    - attack.t1010
    - analytic.an0271
    - detection.det0097
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Compiled Native Binaries Using API Directly
  * The Issue: Attackers can compile custom C/C++ or Go binaries that call EnumWindows() directly from Win32 without invoking PowerShell or scripting hosts. These won't appear in Script Block logs.
  * The Fix: Enable API call auditing via Windows ETW (Event Tracing for Windows) hooks or endpoint security agents that perform user-space API hooking. Look for processes making user32.dll calls outside of known user applications.

* Problem 2: Whitelisted Automation Tools
  * The Issue: Popular desktop automation tools (AutoHotkey, Selenium WebDriver, or screen reader accessibility tools) regularly call GetForegroundWindow() and EnumWindows() as normal operation.
  * The Fix: Maintain an approved list of signed automation tool binaries and filter their process image paths from alerting. Restrict alerting to cases where window enumeration appears in the same session as other discovery or collection commands.

* Problem 3: PowerShell Script Block Logging Not Enabled
  * The Issue: If PowerShell Script Block Logging is not enabled in Group Policy (HKLM\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging), script-level API calls won't be logged, making keyword-based detection impossible.
  * The Fix: Enforce PowerShell Script Block Logging via Group Policy and audit via compliance scanning. Fall back to command-line monitoring via Sysmon Event ID 1 for known modules like User32.dll P/Invoke patterns.
