### **1. Technique Breakdown: T1102.002**

* **What it is:** **Web Service: Bidirectional Communication**. Adversaries leverage legitimate web services (such as Slack, Telegram, Discord, Dropbox, or Box APIs) as bidirectional Command and Control channels. They pull commands from the API (GET requests) and upload stolen data or command output (POST requests). Because these services are TLS-encrypted and trusted by organizations, this C2 channel successfully evades basic network boundary restrictions.
* **Log Source Requirements:** Endpoint network connection logs (Sysmon Event ID 3) or DNS logs (Sysmon Event ID 22), combined with initiating process context.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 3 logs outbound network connections including the destination IP, host name, and requesting process. Wazuh maps these to detect anomalous connections.
* **NIDS (Suricata + Zeek): YES.** Zeek `ssl.log` and `http.log` capture destination server names (SNI) and HTTP method requests (GET/POST) to cloud services.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 3 (Network Connection)** to detect non-standard processes (command-line interpreters, scripting hosts, and execution shells) establishing network connections to common web service API domains.

```yaml
title: Bidirectional C2 Communication via Web Service API (AN0100)
id: 933d2bd3-ba04-4d5d-95b5-39c4e3a225a6
status: experimental
description: Detects command-line interpreters or scripting hosts initiating network connections to common web service API domains (e.g., Telegram, Slack, Dropbox) used for bidirectional C2 communication.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: network_connection
    product: windows
    # Relies on Sysmon Event ID 3 collected via Wazuh
detection:
    selection_process:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\cmd.exe'
            - '\rundll32.exe'
            - '\mshta.exe'
            - '\regsvr32.exe'
            - '\wscript.exe'
            - '\cscript.exe'
    selection_domains:
        DestinationHostname|contains:
            - 'api.telegram.org'
            - 'api.slack.com'
            - 'slack.com'
            - 'dropboxapi.com'
            - 'discordapp.com'
            - 'discord.com'
            - 'api.box.com'
    condition: selection_process and selection_domains
falsepositives:
    - Legitimate administrative IT scripts using automation channels (such as Slack alerting bots or Box backup utilities).
level: high
tags:
    - attack.command_and_control
    - attack.t1102.002
    - analytics.an0100
    - detection.det0035
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Payload Obfuscation and Custom Webhooks**
* *The Issue:* Attackers can use custom webhook URLs on less common platforms or host their own cloud infrastructure, meaning simple static string checks for `slack.com` or `telegram.org` will not trigger.
* *The Fix:* Implement egress profiling to alert on any unknown process executing network connections to standard external cloud service domains, and monitor for high-frequency connection patterns.


* **Problem 2: API Usage over Legitimate Browsers**
* *The Issue:* If the attacker executes their API commands through a browser process (e.g., using headless Chrome or browser automation hooks), the network connection will appear under `chrome.exe`, causing this rule to miss it.
* *The Fix:* Profile browser parentage to detect headless browser executions (such as Chrome spawned by Python, CMD, or PowerShell) and monitor browser extensions.


* **Problem 3: Administrative API integrations**
* *The Issue:* Many IT organizations use Slack alerts or automated Dropbox backup routines, creating repeated alerts.
* *The Fix:* Baseline and whitelist specific IT administration servers or service account usernames that are allowed to make these API connections.
