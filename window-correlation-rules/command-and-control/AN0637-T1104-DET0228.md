### **1. Technique Breakdown: T1104**

* **What it is:** **Multi-Stage Channels**. Adversaries use multiple command and control channels to segment their activity. A first-stage channel (typically a script, HTA, or light loader) connects to a remote server to download secondary tooling. Once executed, the second-stage process (often a more robust RAT or beacon) establishes outbound connections to a completely different, unrelated destination. This isolates the command infrastructure and complicates security analysis.
* **Log Source Requirements:** Endpoint logs capturing process creation (Sysmon Event ID 1) and network connections (Sysmon Event ID 3), allowing correlation of parent-child execution and socket activity.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 logs parent-child relationships, and Event ID 3 captures network activity. Wazuh correlates these to trace process execution paths to remote connections.
* **NIDS (Suricata + Zeek): YES.** Zeek `conn.log` captures distinct network connections, but endpoint correlations are necessary to identify the multi-stage process lineage.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 3 (Network Connection)** to detect processes spawned by scripting engines (acting as stage-1 loaders) initiating subsequent network connections (acting as stage-2 channels).

```yaml
title: Multi-Stage C2 Channel Process spawning with Network Connection (AN0637)
id: d9279647-6486-4fc5-9acc-a2408d186487
status: experimental
description: Detects process creation patterns typical of multi-stage C2 channels, where a scripting host (stage 1) spawns an unexpected child process (stage 2) that immediately initiates outbound network connections.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: network_connection
    product: windows
    # Relies on Sysmon Event ID 3 collected via Wazuh
detection:
    selection_parent:
        ParentImage|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\mshta.exe'
            - '\hh.exe'
    selection_child_network:
        # The child process itself initiates network activity
        Image|endswith:
            - '\cmd.exe'
            - '\rundll32.exe'
            - '\regsvr32.exe'
            - '\schtasks.exe'
            - '\certutil.exe'
            - '\installutil.exe'
            - '\cvtres.exe'
    condition: selection_parent and selection_child_network
fields:
    - Image
    - ParentImage
falsepositives:
    - Administrative orchestration scripts (e.g. software deployment, patch installation) that execute helper binaries to perform network checks.
level: high
tags:
    - attack.command_and_control
    - attack.t1104
    - analytics.an0637
    - detection.det0228
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Process Injection Evasions**
* *The Issue:* Instead of spawning a child process to initiate the second-stage connection, stage-1 loaders often perform process injection (e.g. process hollowing or DLL injection) into a running, trusted Windows process (like `explorer.exe` or `svchost.exe`). In this case, the network connection will appear under the injected process, bypassing parent-child process checks.
* *The Fix:* Enable and monitor Sysmon Event ID 8 (CreateRemoteThread) and Sysmon Event ID 10 (ProcessAccess) targeting system processes, and correlate process injection logs with immediate network socket activity.


* **Problem 2: Use of Legitimate LOLBins for Stage 2**
* *The Issue:* Attackers can use built-in Windows applications like `msiexec.exe` or `mobsync.exe` as the second-stage network interface, which may produce heavy false alerts due to administrative updates.
* *The Fix:* Audit and whitelist standard update processes by comparing certificate digital signatures, whitelisting corporate domain controllers/update servers, and alerting on unsigned binaries.


* **Problem 3: Script-Only Multi-Stage Operations**
* *The Issue:* The loader can run stage-2 entirely inside the same process space (e.g., executing a second script block in the same PowerShell window), which does not generate parent-child process logs.
* *The Fix:* Enable PowerShell Script Block Logging (Event ID 4104) to audit scripts executing in memory, and detect script code containing network connection commands (e.g., `Net.WebClient` or `Invoke-WebRequest`).
