### **1. Technique Breakdown: T1568**

* **What it is:** **Dynamic Resolution**. Adversaries configure malware to generate C2 domain names dynamically using Domain Generation Algorithms (DGA). This bypasses static firewall blocks and IP domain blacklists because the malware queries a sequence of pseudo-random, high-entropy domains to find the active C2. DGA activity often manifests as system processes that typically perform no internet activity (e.g., `calc.exe`, `notepad.exe`) generating DNS queries.
* **Log Source Requirements:** DNS Query logs (Sysmon Event ID 22 / Windows Security Event ID 3008) capturing query domains and requesting processes.
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 22 logs the queried host alongside the requesting process filename. Wazuh processes these events.
* **NIDS (Suricata + Zeek): YES.** Zeek `dns.log` captures all network-level DNS queries, although endpoint logs are needed to isolate the calling process.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 22 (DNS Query)** to detect DNS query requests originating from system processes that do not legitimately perform network activity.

```yaml
title: DNS Query from Non-Network System Utility (AN0109)
id: 6878c28a-8d5f-4fa8-89ee-0893ee93f26f
status: experimental
description: Detects DNS queries initiated by Windows system utilities that do not standardly perform network communications, which may indicate process injection or DGA beaconing.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: dns_query
    product: windows
    # Relies on Sysmon Event ID 22 collected via Wazuh
detection:
    selection_process:
        Image|endswith:
            - '\calc.exe'
            - '\notepad.exe'
            - '\mspaint.exe'
            - '\regedit.exe'
            - '\systeminfo.exe'
            - '\tasklist.exe'
            - '\chkdsk.exe'
    condition: selection_process
fields:
    - Image
falsepositives:
    - Legitimate user utilities performing automated error checking or crashing (triggering error reporting DNS).
level: high
tags:
    - attack.command_and_control
    - attack.t1568
    - analytics.an0109
    - detection.det0039
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Process Masquerading / Execution of Renamed Binaries**
* *The Issue:* Attackers can rename their malicious binary to look like a legitimate browser (e.g., renaming `malware.exe` to `chrome.exe` and running it from a user folder), which bypasses DNS audits checking only for non-network system names.
* *The Fix:* Audit the binary path and digital signature of the calling process in DNS query logs, ensuring that only verified browsers executing from standard application folders are whitelisted.


* **Problem 2: Tunneling DNS Queries (DNS over HTTPS / DoH)**
* *The Issue:* Modern operating systems and browsers support DNS over HTTPS (DoH), which wraps DNS queries inside encrypted HTTPS POST/GET requests (port 443) to public resolvers (like Cloudflare `1.1.1.1` or Google `8.8.8.8`). This completely bypasses local DNS query logging (Event ID 22).
* *The Fix:* Disable DNS over HTTPS via domain Group Policy (GPO) to force endpoints to use internal corporate DNS servers, and monitor outbound port 443 traffic to public DoH resolver IPs.


* **Problem 3: Crash Dump/Windows Error Reporting Noise**
* *The Issue:* When Windows utilities crash, the OS spawns `werfault.exe` which connects to Microsoft error reporting domains (e.g., `watson.telemetry.microsoft.com`), which can cause false alarms.
* *The Fix:* Whitelist official Microsoft telemetry and error reporting domains in the DNS log filter.
