### **1. Technique Breakdown: T1505.004**

* **What it is:** **IIS Components**. Adversaries install malicious Internet Information Services (IIS) components — including ISAPI filters, ISAPI extensions, or IIS native modules — to achieve persistent code execution on Windows web servers. These components are DLLs that the IIS worker process (`w3wp.exe`) loads automatically, intercepting or manipulating HTTP requests and responses. Adversaries use the IIS administration tool `appcmd.exe` to register the DLL, or directly modify IIS configuration files (`applicationHost.config`). This provides a highly stealthy persistence mechanism since the malicious component runs as part of the trusted IIS process and processes all HTTP traffic.
* **Log Source Requirements:** Sysmon process creation logs (Event ID 1) for `appcmd.exe` usage, IIS Configuration event logs (Microsoft-IIS-Configuration), file event logs (Event ID 11) for DLL writes to IIS directories, and System Event Log (Event ID 7040/7045) for service registration.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 captures `appcmd.exe install module` command-line invocations. Event ID 11 captures DLL files written to IIS directories (e.g., `%windir%\System32\inetsrv\`). Wazuh collects IIS configuration change events.
    * **NIDS (Suricata + Zeek): NO.** IIS module installation is a host-local configuration change. The malicious module's activity (C2 over HTTP) may be visible at the network level, but the installation step is host-side only.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect the use of `appcmd.exe` to install IIS modules or ISAPI filters, and **Sysmon Event ID 11** to detect DLL files written to IIS system directories by non-IIS processes.

```yaml
title: Malicious IIS Module or ISAPI Filter Installation (AN0184)
id: 67145796-ad3c-459b-aa04-a821af14396b
status: experimental
description: Detects adversarial installation of malicious IIS components (native modules, ISAPI filters/extensions) via appcmd.exe or unexpected DLL writes to IIS directories for persistent web server backdooring.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_appcmd:
        - Image|endswith: '\appcmd.exe'
        - OriginalFileName: 'appcmd.exe'
    selection_appcmd_install:
        CommandLine|contains:
            - ' install '
            - ' add '
            - 'module'
            - 'isapi'
            - 'filter'
            - 'handler'
    selection_powershell:
        - Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
        - OriginalFileName:
            - 'PowerShell.EXE'
            - 'pwsh.dll'
    selection_ps_iis:
        CommandLine|contains:
            - 'New-WebConfiguration'
            - 'Add-WebConfiguration'
            - 'isapi'
            - 'GlobalModules'
            - 'system.webServer/modules'
    condition: (selection_appcmd and selection_appcmd_install) or (selection_powershell and selection_ps_iis)
fields:
    - CommandLine
    - Image
    - OriginalFileName
falsepositives:
    - Legitimate IIS administrators installing approved web application modules or ISAPI extensions during application deployment.
level: high
tags:
    - attack.persistence
    - attack.t1505.004
    - analytics.an0184
    - detection.det0068
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Direct applicationHost.config Modification**
    * *The Issue:* Adversaries with write access to the IIS configuration file (`%systemroot%\system32\inetsrv\config\applicationHost.config`) can register malicious modules by directly editing the XML without ever invoking `appcmd.exe` or PowerShell cmdlets. No process creation event is generated for the IIS configuration change.
    * *The Fix:* Monitor Sysmon Event ID 11 (File Create/Modify) for writes to `applicationHost.config` and `web.config` files in IIS directories by processes other than the IIS Configuration Manager or known deployment tools. Enable Windows file auditing via SACL on IIS configuration directories.

* **Problem 2: Malicious DLL Dropped but Not Yet Registered**
    * *The Issue:* Adversaries may drop the malicious DLL into IIS-accessible directories (e.g., application `bin` folders) before registering them, or during deployment of legitimate-looking web applications. The file drop event may occur separately from the registration command.
    * *The Fix:* Complement with a file event rule detecting unsigned DLL files written to `%systemroot%\system32\inetsrv\`, IIS application directories, or `bin` folders within IIS web roots by non-installer processes.

* **Problem 3: IIS Worker Process Anomalous Behavior**
    * *The Issue:* Once an IIS native module is installed, the malicious code runs inside `w3wp.exe` — a completely trusted IIS worker process. Commands executed by the module (e.g., spawning a reverse shell or making outbound C2 connections) appear to come from `w3wp.exe`, which may have some legitimate outbound connectivity.
    * *The Fix:* Establish a behavioral baseline for `w3wp.exe` network connections. Alert on `w3wp.exe` making outbound connections to non-application-server IPs, spawning child processes (especially shells), or reading system credential stores.
