### **1. Technique Breakdown: T1136.002**

* **What it is:** **Domain Account Creation**. Adversaries create new domain user accounts to establish persistent access to compromised environments. Unlike local accounts, domain accounts provide access across all domain-joined systems. On Windows, this is typically performed via `net.exe user /add /domain`, PowerShell Active Directory cmdlets (`New-ADUser`), or LDAP writes to Active Directory. The creation of a new domain account by a non-administrative process or from an unusual workstation is a strong indicator of adversarial persistence.
* **Log Source Requirements:** Windows Security Event Log (Event ID 4720 - A user account was created) on domain controllers, and Sysmon process creation logs (Event ID 1) capturing `net.exe` or PowerShell AD cmdlets.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 captures `net.exe user /add /domain` and `New-ADUser` executions on domain-joined hosts. Windows Security Event ID 4720 is generated on the domain controller upon successful user account creation.
    * **NIDS (Suricata + Zeek): NO.** While LDAP writes to Active Directory produce network traffic (LDAP port 389/636 to the DC), correlating that traffic to specific account creation without host-level context is not reliable.

### **2. Custom Sigma Rule**

This rule utilizes **Windows Security Event ID 4720** (A user account was created) to detect domain account creation events, correlated with **Sysmon Event ID 1** to identify the creating process, especially when initiated from non-DC workstations.

```yaml
title: Domain Account Creation for Persistence (AN0006)
id: f28c1024-46e2-4f98-bc57-bb378cfd47af
status: experimental
description: Detects creation of new domain user accounts via net user /add /domain, PowerShell New-ADUser, or Windows Security Event ID 4720, which may indicate adversarial persistence establishment through domain account backdoors.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_net:
        - Image|endswith: '\net.exe'
        - OriginalFileName: 'net.exe'
    selection_net_args:
        CommandLine|contains:
            - ' user '
            - ' /add '
            - ' /domain'
    selection_powershell:
        - Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
        - OriginalFileName:
            - 'PowerShell.EXE'
            - 'pwsh.dll'
    selection_ps_args:
        CommandLine|contains:
            - 'New-ADUser'
            - 'New-LocalUser'
    condition: (selection_net and selection_net_args) or (selection_powershell and selection_ps_args)
fields:
    - CommandLine
    - Image
    - OriginalFileName
falsepositives:
    - Legitimate IT administrators creating domain accounts during employee onboarding via authorized provisioning scripts.
level: high
tags:
    - attack.persistence
    - attack.t1136.002
    - analytics.an0006
    - detection.det0003
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: LDAP-Based Account Creation Bypassing CLI Tools**
    * *The Issue:* Adversaries can create domain accounts directly via LDAP writes to Active Directory (e.g., using LDAP libraries in Python or .NET) without invoking `net.exe` or PowerShell AD cmdlets. No process creation event for account creation tools is generated.
    * *The Fix:* Monitor Windows Security Event ID 4720 (A user account was created) on domain controllers directly. This event fires regardless of the creation method (CLI, LDAP, ADSI). Correlate the SubjectLogonId in Event ID 4720 with Event ID 4624 (logon) to determine the originating host and session.

* **Problem 2: HR/IT Provisioning Automation Noise**
    * *The Issue:* Automated identity provisioning tools (ServiceNow, SailPoint, Azure AD Connect) regularly create domain accounts as part of employee onboarding workflows. These tools use PowerShell or LDAP and generate identical events to adversarial account creation.
    * *The Fix:* Allow-list known provisioning system service accounts and their source hostnames (typically dedicated IAM servers). Alert only when account creation occurs from unexpected hosts (user workstations, servers) or via interactive sessions rather than service accounts.

* **Problem 3: Account Creation Without Immediate Privilege Assignment**
    * *The Issue:* Adversaries may create a domain account and leave it dormant for an extended period before using it, making immediate correlation with other suspicious activity difficult. Reviewing account creation alone provides limited context.
    * *The Fix:* Implement a delayed correlation rule: flag accounts created in the last 30 days that subsequently perform privileged operations (logon to servers, group policy changes, or service installations) from uncommon workstations.
