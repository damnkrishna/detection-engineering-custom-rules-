### 1. Technique Breakdown: T1129

* What it is: Shared Modules. Adversaries execute malicious payloads by loading them as shared modules (DLLs) into the memory space of trusted processes. This is frequently accomplished via DLL Search Order Hijacking, DLL Side-Loading, or AppInit DLLs. By forcing a signed, legitimate process (like `explorer.exe` or `svchost.exe`) to load a malicious module, the adversary executes code while hiding under the process identity of a trusted Windows system program.
* Log Source Requirements: Endpoint logs capturing module/image loads with digital signature verification (specifically Sysmon Event ID 7 - Image Loaded).
* Coverage Check:
* HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 7 (Image Loaded) captures DLL loading events, reporting the path of the loading process, the path of the loaded DLL (`ImageLoaded`), and signature metadata.
* NIDS (Suricata + Zeek): NO. Shared module execution is local to the operating system's kernel and memory manager. It produces no network traffic.
* Log Sources Covered:
  - Sysmon Event ID 7 (image_load)
  - Sysmon Event ID 4104 (ps_script)
* Log Sources Missing / Unused:
  - None.

### 2. Custom Sigma Rule

The detection logic is split into image load DLL monitoring and PowerShell script block logging of assembly loading.

Rule 1 of 2: Loading of Suspicious DLL from User-Writable Directory (Image Load)
```yaml
title: Loading of Suspicious DLL from User-Writable Directory (AN0052)
id: f47c8d9e-1a2b-3c4d-8e9f-6f7d8e9a0b0d
status: experimental
description: Detects a process loading a shared module (DLL) located in user-writable directories (like AppData, Temp, or Public), which may indicate DLL side-loading or search order hijacking.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: image_load
    product: windows
    # Relies on Sysmon Event ID 7
detection:
    selection_paths:
        ImageLoaded|contains:
            - '\AppData\Local\Temp\'
            - '\Users\Public\'
            - '\Windows\Temp\'
            - '\AppData\Roaming\'
    selection_processes:
        Image|endswith:
            - '\explorer.exe'
            - '\svchost.exe'
            - '\cmd.exe'
            - '\powershell.exe'
            - '\rundll32.exe'
            - '\regsvr32.exe'
            - '\mshta.exe'
    selection_signature:
        Signed: 'false'
    condition: selection_paths and selection_processes and selection_signature
fields:
    - Image
    - ImageLoaded
    - Signed
    - SignatureStatus
falsepositives:
    - Legitimate software installed in user directories (like local profile applications) loading local DLLs.
level: high
tags:
    - attack.execution
    - attack.t1129
    - analytic.an0052
    - detection.det0018
```

Rule 2 of 2: Loading Shared Modules via PowerShell (PowerShell Script Block)
```yaml
title: Loading Shared Modules via PowerShell (AN0052-B)
id: 15ae2656-5122-49f6-a05c-f4c54b8b1c45
status: experimental
description: Detects PowerShell script blocks loading assemblies or DLLs dynamically.
author: Krishna Gupta
date: 2026-06-17
logsource:
    category: ps_script
    product: windows
detection:
    selection:
        ScriptBlockText|contains:
            - '[System.Reflection.Assembly]::Load'
            - 'Add-Type'
        ScriptBlockText|contains:
            - '.dll'
    condition: selection
fields:
    - ScriptBlockText
    - User
falsepositives:
    - Administrative automation or development scripts.
level: medium
tags:
    - attack.execution
    - attack.t1129
    - analytic.an0052
    - detection.det0018
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Administrative Action False Positives
  * The Issue: IT personnel performing legitimate maintenance operations can invoke techniques that mirror adversarial persistence or evasion.
  * The Fix: Audit and baseline corporate administration accounts, whitelisting specific approved service accounts and administrative subnets.

* Problem 2: Command and Execution Obfuscation
  * The Issue: Attackers employ encoding, environment variables, or caret insertions to bypass keyword-based detection filters.
  * The Fix: Enable deep logging (such as Script Block Logging) and apply normalization or regex decoding inside the SIEM parsing pipeline.

* Problem 3: Log Deletion and Modification
  * The Issue: Adversaries can clear security logs or stop monitoring agents (like Wazuh or Sysmon) to blind defensive operations.
  * The Fix: Forward all endpoint logs immediately to a centralized write-once SIEM and alert on service stoppage or log clearing events.
