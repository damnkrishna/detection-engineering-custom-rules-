### **1. Technique Breakdown: T1574**

* **What it is:** **Hijack Execution Flow**. Adversaries modify the environment Windows uses to locate and execute programs (such as DLL load paths, service binary configurations, or application pathways) to hijack execution flow. By changing the `binPath` of a service or pointing a service's `ServiceDll` registry key to a malicious module, they force a high-privilege system process to run their payload.
* **Log Source Requirements:** Endpoint logs capturing process creation and command line parameters (specifically targeting tools that modify service parameters or add service keys).
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 (Process Creation) logs when utilities like `sc.exe` or `reg.exe` are called to modify service executable paths or service parameters.
* **NIDS (Suricata + Zeek): NO.** Service and execution flow modifications are local host tasks. They do not generate network logs.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect command-line attempts to hijack system execution flow by modifying service configurations (`sc.exe config binpath=`) or adding registry keys that change service binary or library paths.

```yaml
title: Service Execution Flow Hijacking via CLI (AN0609)
id: c4e7d1b2-2e1f-4b92-8c7a-5f6d7e8a9b0d
status: experimental
description: Detects command-line service modifications or registry additions that alter the execution flow of system services (such as modifying service binPath or adding custom ServiceDlls).
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_sc:
        - Image|endswith: '\sc.exe'
        - OriginalFileName: 'sc.exe'
    selection_sc_args:
        CommandLine|contains|all:
            - 'config'
            - 'binpath'
    selection_reg:
        - Image|endswith:
            - '\reg.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
        - OriginalFileName:
            - 'reg.exe'
            - 'PowerShell.EXE'
            - 'pwsh.dll'
    selection_reg_args:
        CommandLine|contains|all:
            - 'System\CurrentControlSet\Services'
            - 'add'
        CommandLine|contains:
            - 'ImagePath'
            - 'ServiceDll'
    condition: (selection_sc and selection_sc_args) or (selection_reg and selection_reg_args)
fields:
    - CommandLine
    - Image
    - OriginalFileName
falsepositives:
    - Legitimate software installers configuring service binary paths or creating custom services during application deployment.
level: high
tags:
    - attack.execution
    - attack.persistence
    - attack.privilege_escalation
    - attack.t1574
    - analytics.an0609
    - detection.det0218
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Direct Service Registry Modification via API (Bypassing CLI)**
* *The Issue:* Instead of running `sc.exe` or `reg.exe` commands, custom malware can call the Win32 API functions `ChangeServiceConfigW` or `RegSetValueExW` to directly modify the service paths or registry keys. This process-creation rule will miss such API calls entirely.
* *The Fix:* Enable registry auditing and monitor Sysmon Event ID 12/13 (Registry Event) or Windows Security Event ID 4657 targeting `HKLM\SYSTEM\CurrentControlSet\Services\...\ImagePath` or `...\Parameters\ServiceDll`.


* **Problem 2: Service DLL Replacement**
* *The Issue:* An attacker with write access to the service directories (e.g., in Program Files) can replace the legitimate service DLL with a malicious one of the same name. No command-line changes or registry modifications will occur.
* *The Fix:* Implement File Integrity Monitoring (FIM) or file write auditing (Event ID 4663) on system and service installation directories, and verify module signatures on loaded DLLs.


* **Problem 3: Administrative/Update Noise**
* *The Issue:* Windows updates and legitimate third-party application installers frequently create, configure, or modify services, causing high-volume alerts.
* *The Fix:* Whitelist known-good installers (e.g., signed by trusted vendors) and restrict alerts to modifications initiated by user accounts rather than system accounts like `NT AUTHORITY\SYSTEM`.
