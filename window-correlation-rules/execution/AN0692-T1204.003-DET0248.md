### **1. Technique Breakdown: T1204.003**

* **What it is:** **User Execution: Malicious Image**. In Cloud/IaaS environments (AWS, GCP, Azure), adversaries or malicious insiders may launch a new Virtual Machine or instance from a non-approved, newly-created, or publicly shared malicious machine image (like an AMI). On first boot, embedded agents or `cloud-init` scripts download payloads, establish C2, or begin crypto-mining.
* **Log Source Requirements:** Cloud control plane logs (AWS CloudTrail, Azure Activity Logs, GCP Audit Logs) for instance creation, and host-level logs (Sysmon / Auditd) for post-boot execution.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES (Host side).** Captures the execution of `cloud-init`, `user-data` scripts, or unusual services starting immediately upon boot.
    * **NIDS (Suricata + Zeek): PARTIAL.** NIDS will see the outbound network connections to C2 or mining pools generated by the malicious image.

### **2. Custom Sigma Rule**

This rule utilizes **AWS CloudTrail logs (or equivalent cloud platform logs)** to detect the creation of an instance using an image (AMI) that is not owned by the account or is completely unknown/unapproved.

```yaml
title: Cloud Execution - EC2 Instance Launch from Untrusted AMI (AN0692)
id: fbbcc3f9-676b-4e6c-a8eb-8b0ab3606f1d
status: experimental
description: Detects the launch of an EC2 instance (or cloud VM) using a machine image (AMI) that is not owned by the organization, indicating potential malicious image execution.
author: Krishna Gupta
date: 2026-06-09
logsource:
    product: aws
    service: cloudtrail
    # Relies on CloudTrail RunInstances events
detection:
    selection_event:
        eventName: 'RunInstances'
    selection_image_owner:
        # Assuming the SIEM enriches the CloudTrail log with the Image Owner ID
        # Alternatively, checking if the image ID is not in a whitelist
        responseElements.instancesSet.items.imageId|startswith: 'ami-'
    filter_approved_owners:
        # Replace with your actual trusted AWS Account IDs
        responseElements.instancesSet.items.imageOwnerId: 
            - '123456789012' # Own account
            - 'amazon'       # Official Amazon AMIs
            - 'aws-marketplace'
    condition: selection_event and selection_image_owner and not filter_approved_owners
fields:
    - eventName
    - responseElements.instancesSet.items.imageId
    - responseElements.instancesSet.items.imageOwnerId
falsepositives:
    - Developers testing public community AMIs without prior authorization.
    - Third-party vendor deployments using their own account's AMI.
level: high
tags:
    - attack.execution
    - attack.t1204.003
    - analytics.an0692
    - detection.det0248
```

### OCSF Normalized
```xml
title: Cloud Execution - EC2 Instance Launch from Untrusted AMI (OCSF-Normalized)
id: fbbcc3f9-676b-4e6c-a8eb-8b0ab3606f1d
status: experimental
description: Detects cloud VM launches from untrusted images, mapped to OCSF api_activity.
author: Krishna Gupta

logsource:
    category: cloud
    product: ocsf
    class: api_activity

    selection_event:
        unmapped.api_operation: 'RunInstances'
    selection_image_owner:
        unmapped.resource_type: 'Compute Image'
        unmapped.resource_uid|startswith: 'ami-'
    filter_approved_owners:
        unmapped.resource_owner_uid:
            - '123456789012'
            - 'amazon'
            - 'aws-marketplace'
    condition: selection_event and selection_image_owner and not filter_approved_owners
fields:
    - unmapped.api_operation
    - unmapped.resource_owner_uid
    - unmapped.resource_type
    - unmapped.resource_uid
falsepositives:
    - Developers using public AMIs.
level: high
tags:
    - attack.execution
    - attack.t1204.003
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Ephemeral Container Execution**
    * *The Issue:* The technique applies equally to malicious Docker/Kubernetes container images. Attackers might launch a pod using a malicious image from Docker Hub, which won't trigger `RunInstances` API calls in CloudTrail.
    * *The Fix:* Expand monitoring to Kubernetes Audit logs (e.g., `Create Pod`) looking for image names from untrusted external registries or lacking internal cryptographic signatures.

* **Problem 2: Host vs. Control Plane Disconnect**
    * *The Issue:* The API log (CloudTrail) tells you a bad VM launched, but not *what* it is doing. The host log (Sysmon) tells you bad commands are running, but not that it came from a malicious AMI.
    * *The Fix:* The SIEM must correlate cloud metadata (Instance ID) with the endpoint logs forwarding from that instance. Alert when `RunInstances` from an untrusted AMI is followed immediately by high CPU usage (mining) or outbound connections.

* **Problem 3: Keeping the Whitelist Updated**
    * *The Issue:* Cloud environments change rapidly. Maintaining a static whitelist of approved `imageOwnerId` or specific `ami-` hashes in a Sigma rule is operationally unsustainable.
    * *The Fix:* Use a dynamic lookup table in the SIEM that synchronizes with a cloud security posture management (CSPM) tool, alerting when a deployed image does not match the CSPM's approved registry.
