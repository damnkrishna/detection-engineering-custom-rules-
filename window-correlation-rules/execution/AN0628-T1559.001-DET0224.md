### **1. Technique Breakdown: T1559.001**

* **What it is:** **Inter-Process Communication: Component Object Model**. Adversaries use the Windows Component Object Model (COM) for code execution and persistence. They can interact with COM objects locally or remotely (DCOM) to spawn processes (e.g., using `MMC20.Application` or `ShellWindows`), bypassing typical parent-child process relationships and often evading standard command-line logging.
* **Log Source Requirements:** Process creation logs (Sysmon Event ID 1), Registry modification logs (Sysmon Event ID 12/13/14), and Network connection logs for DCOM (Sysmon Event ID 3).
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 captures unusual processes spawned by `svchost.exe -k DcomLaunch` or `dllhost.exe`. Registry logs capture COM hijacking.
    * **NIDS (Suricata + Zeek): PARTIAL.** Network sensors can identify Distributed COM (DCOM) traffic (RPC/TCP 135 and dynamic ports) indicating remote execution attempts.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect suspicious processes executing as a result of COM instantiation, often indicated by `dllhost.exe` (the COM Surrogate) spawning command shells or script interpreters.

```yaml
title: Component Object Model (COM) Execution (AN0628)
id: cd2593b4-4e2b-47e0-94d8-cf313d42e2a5
status: experimental
description: Detects anomalous use of COM objects for execution, such as dllhost.exe or wmiprvse.exe spawning script engines or command shells.
author: Krishna Gupta
date: 2026-06-09
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_parent:
        ParentImage|endswith:
            - '\dllhost.exe'
            - '\wmiprvse.exe'
            - '\svchost.exe'
    selection_parent_args:
        ParentCommandLine|contains:
            - 'DcomLaunch'
            - '/Processid'
    selection_child:
        Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\regsvr32.exe'
    condition: selection_parent and selection_parent_args and selection_child
fields:
    - Image
    - ParentCommandLine
    - ParentImage
falsepositives:
    - Systems management tools invoking WMI/DCOM for legitimate remote administration.
level: high
tags:
    - attack.execution
    - attack.t1559.001
    - analytics.an0628
    - detection.det0224
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Broken Parent-Child Lineage**
    * *The Issue:* COM execution breaks normal process trees. When malware uses COM to launch an application (like Office), the new process is often spawned by `svchost.exe -k DcomLaunch`, NOT the malware process. This makes tracing the true origin very difficult.
    * *The Fix:* Correlate Sysmon Event ID 1 (Process Creation) with Sysmon Event ID 10 (Process Access) and Event ID 3 (Network Connections) occurring simultaneously on the host to tie the COM execution back to the malicious actor.

* **Problem 2: COM Hijacking Persistence**
    * *The Issue:* Instead of direct execution, attackers often hijack existing COM class identifiers (CLSIDs) in the registry to execute malicious DLLs when legitimate software is launched.
    * *The Fix:* Create a parallel rule monitoring Registry Events (Sysmon ID 12/13) targeting `HKCU\Software\Classes\CLSID\*` and `HKLM\Software\Classes\CLSID\*` for abnormal DLL mappings.

* **Problem 3: In-Process COM Execution**
    * *The Issue:* If an attacker instantiates an in-process COM object (DLL), the code executes within the context of the calling process, generating no new process creation events.
    * *The Fix:* Utilize Endpoint Detection and Response (EDR) memory scanning or monitor Image Loads (Sysmon Event ID 7) for unsigned or unexpected DLLs loaded via COM calls inside host processes.
