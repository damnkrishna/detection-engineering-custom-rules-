### **1. Technique Breakdown: T1574.005**

* **What it is:** **Hijack Execution Flow: Executable Installer File Permissions Weakness**. Adversaries exploit weak directory permissions in software installation paths (such as subfolders in `%TEMP%` or custom application directories created by installers) to overwrite or replace legitimate binaries with their own malicious payloads. When the installer runs again under an elevated context (e.g., local admin or SYSTEM), it executes the replaced binary, resulting in privilege escalation.
* **Log Source Requirements:** Endpoint logs capturing process creation and command line parameters (specifically targeting elevated process execution originating from temporary or user-writable directories).
* **Coverage Check:**
* **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 (Process Creation) logs process executions, including the full resolved path of the executable (`Image`) and the token elevation level (`IntegrityLevel`).
* **NIDS (Suricata + Zeek): NO.** Exploiting local installer directory permission weaknesses is an endpoint-internal privilege escalation method. It generates no network logs.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect when command shell interpreters or script hosts are executed under elevated contexts (High or System Integrity) directly from user-writable temporary or download directories.

```yaml
title: Elevated Execution from Weak Permissions Installer Directory (AN0108)
id: c57f8e8a-2c1b-4d92-8c8d-6f7d8e9a0b0d
status: experimental
description: Detects when processes are launched under elevated contexts (High or System Integrity) from user-writable installer or temporary directories, indicating potential exploitation of installer path permission weaknesses.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_paths:
        Image|contains:
            - '\AppData\Local\Temp\'
            - '\Users\Public\'
            - '\Windows\Temp\'
            - '\AppData\Roaming\'
            - '\Downloads\'
    selection_integrity:
        IntegrityLevel:
            - 'High'
            - 'System'
    filter_known_installers:
        - CommandLine|contains:
            - 'nativeimages'
            - 'PackageStaging'
        - Image|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
            - '\install.exe'
    condition: selection_paths and selection_integrity and not filter_known_installers
falsepositives:
    - Legitimate administrative software installers executing unpacking operations and running child configuration scripts with elevated privileges in local temp folders.
level: high
tags:
    - attack.execution
    - attack.persistence
    - attack.privilege_escalation
    - attack.t1574.005
    - analytics.an0108
    - detection.det0038
```

            - '\Downloads\'
            
    # Targeting suspicious follow-on executables in OCSF process.file.path
    selection_suspicious:
        process.file.path|endswith:
            - '\cmd.exe'

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Administrative Tools running in User Directories**
* *The Issue:* Administrators routinely download and run standalone troubleshooting or administrative tools (like Sysinternals Suite, Wireshark portable, etc.) directly from their `Downloads` folder, leading to false alerts.
* *The Fix:* Implement a process whitelist for known-good hash lists of approved administrative binaries, or restrict this rule to non-domain-admin hosts.


* **Problem 2: Alternate Installer Folders**
* *The Issue:* Attackers can target non-standard installer folders that also have weak permissions (e.g., custom C:\Application folders configured with poor DACLs).
* *The Fix:* Align this detection with file permission auditing (AN0834 / DET0299) to identify directory permission weaknesses on custom application deployment paths.


* **Problem 3: PowerShell Script Block Evasions**
* *The Issue:* If the installer spawns a shell that downloads and executes code directly in memory without writing an executable to the installer folder, this file-path based rule will fail to trigger.
* *The Fix:* Enable PowerShell Script Block Logging (Event ID 4104) and look for network downloads of files inside scripts.
