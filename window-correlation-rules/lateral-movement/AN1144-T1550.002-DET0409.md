### **1. Technique Breakdown: T1550.002**

* **What it is:** **Use Alternate Authentication Material: Pass the Hash**. Adversaries authenticate to remote systems using NTLM password hashes instead of cleartext passwords. By passing the hash directly to the local security provider (LSASS), they establish remote sessions without password knowledge. On Windows target systems, a successful Pass the Hash network logon is characterized by a Network Logon (Event ID 4624, Logon Type 3) using NTLM authentication where the **Key Length is recorded as 0**, because the normal NTLM challenge-response key derivation step is bypassed.
* **Log Source Requirements:** Windows Security Event Log Event ID 4624 (Logon) auditing NTLM parameters.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Windows Security log captures Event ID 4624 details including Logon Type, Authentication Package, and Key Length. Wazuh parses and alerts on these fields.
    * **NIDS (Suricata + Zeek): PARTIAL.** Network sensors track NTLM sessions but cannot inspect the inner LSASS session parameters or key length structures.

### **2. Custom Sigma Rule**

This rule utilizes **Windows Security Event ID 4624 (Logon)** to detect successful NTLM network logons (Logon Type 3) that exhibit a Key Length of 0, which is a signature of NTLM Pass the Hash activity.

```yaml
title: Lateral Movement - NTLM Pass the Hash Detection (AN1144)
id: 7a482b35-be45-4dca-81fd-75cad5bab2cf
status: experimental
description: Detects successful NTLM network logons (Logon Type 3) with a Key Length of 0, indicating alternate credential material (password hash) was used to authenticate.
author: Krishna Gupta
date: 2026-06-08
logsource:
    product: windows
    service: security
detection:
    selection_logon:
        EventID: 4624
        LogonType: 3 # Network Logon
        LmPackageName|startswith: 'NTLM'
        KeyLength: 0
    filter_local:
        # Filter out local loopback connections if necessary
        IpAddress:
            - '127.0.0.1'
            - '::1'
    condition: selection_logon and not filter_local
fields:
    - EventID
    - IpAddress
    - KeyLength
    - LmPackageName
    - LogonType
falsepositives:
    - Certain legacy local service accounts or specific third-party applications using non-standard NTLM authentication calls.
level: high
tags:
    - attack.lateral-movement
    - attack.t1550.002
    - analytics.an1144
    - detection.det0409
```

title: Lateral Movement - NTLM Pass the Hash Detection (OCSF-Normalized)

    - Legacy system authentication setups.
level: high

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Kerberos Authentication Fallback**
    * *The Issue:* If the domain enforces Kerberos and disables NTLM, attackers cannot run NTLM Pass the Hash, but will instead try Pass the Ticket, rendering this NTLM-focused rule blind.
    * *The Fix:* Disable NTLM authentication domain-wide or restrict NTLM usage to local accounts, and monitor Kerberos tickets.

* **Problem 2: Loopback False Positives**
    * *The Issue:* Local applications running on the host connecting to local services (e.g. IIS talking to a database service on localhost) sometimes trigger Type 3 logons with Key Length 0.
    * *The Fix:* Ensure loopback IP addresses (`127.0.0.1`, `::1`) are strictly excluded in the rule filter.

* **Problem 3: Use of Remote Admin tools (Wmi/WinRM)**
    * *The Issue:* PtH can be executed to launch WMI/WinRM remote sessions. While they use PtH, they might not trigger Type 3 NTLM logons if they use Kerberos trusts, requiring separate command execution tracking.
    * *The Fix:* Monitor the target process spawns (e.g. `wsmprovhost.exe` or `wmiprvse.exe` launching cmd prompts) on the destination system.
