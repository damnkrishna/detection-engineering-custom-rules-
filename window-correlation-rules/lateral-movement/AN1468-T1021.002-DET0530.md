### 1. Technique Breakdown: T1021.002

* What it is: Remote Services: SMB/Windows Admin Shares. Adversaries abuse default Windows administrative shares (like `C$`, `ADMIN$`, or `IPC$`) to copy malware files remotely to target hosts and execute them. A classic lateral movement tool that does this is PsExec (or equivalent Impacket scripts like `psexec.py`). When PsExec runs, it copies a service binary (e.g. `PSEXESVC.exe`) to the remote host's administrative share (`ADMIN$`, which is `C:\Windows\`) and uses the Service Control Manager (`services.exe`) to register and start it. The signature endpoint behavior is `services.exe` spawning a non-standard child process representing the PsExec agent.
* Log Source Requirements: Sysmon process creation logs (Event ID 1) auditing system services.
* Coverage Check:
    * HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 1 logs the parent process of newly started services. If `services.exe` spawns an executable from the Windows folder that is not a standard service binary, it is a high-confidence alert.
    * NIDS (Suricata + Zeek): YES. Network filters capture SMB access to administrative shares (ports 139, 445), but endpoint logs are critical to identify the resulting code execution.
* Log Sources Covered:
  - Sysmon Event ID 1 (process_creation)
  - Windows System Log Event ID 7045 (system)
* Log Sources Missing / Unused:
  - None.
* Conclusion: SMB admin share executions can be detected using process creation and system installation logs.

### 2. Custom Sigma Rule

The detection logic is split into process creation monitoring and system event log service installation monitoring.

Rule 1 of 2: Lateral Movement - Suspicious Service Executable Spawned by Services.exe (Process Creation)
```yaml
title: Lateral Movement - Suspicious Service Executable Spawned by Services.exe (AN1468)
id: 7dc408f0-7f7a-445d-9836-e4deaa4578eb
status: experimental
description: Detects the Service Control Manager (services.exe) spawning non-standard, temporary, or suspicious child processes (such as PSEXESVC.exe or administrative tools), indicating lateral movement via SMB shares.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1
detection:
    selection_parent:
        ParentImage|endswith:
            - '\services.exe'
    selection_child:
        - Image|endswith:
            - '\PSEXESVC.exe'
            - '\paexec.exe'
            - '\cmd.exe'
            - '\powershell.exe'
        - OriginalFileName:
            - 'psexesvc.exe'
            - 'PAExec.exe'
            - 'Cmd.Exe'
            - 'PowerShell.EXE'
        - Image|contains:
            - '\Windows\Temp\'
            - '\Windows\psexesvc'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: selection_parent and selection_child and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Legitimate administrative utilities installed as standard services that spawn command shells on startup (highly rare and bad practice).
level: critical
tags:
    - attack.lateral-movement
    - attack.t1021.002
    - analytic.an1468
    - detection.det0530
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Renamed PsExec Service Executables
  * The Issue: Attackers can modify the PsExec tool parameters or use custom tools to rename the service binary (e.g. to update_svc.exe), which bypasses direct checks for the string PSEXESVC.exe.
  * The Fix: Complement this rule by monitoring file creations (Event ID 11) in the C:\Windows\ directory by the System process or network logon accounts, and scan for unsigned executables run as services.

* Problem 2: Execution via Scheduled Tasks
  * The Issue: Instead of installing a new service, attackers can copy a binary via SMB and register a scheduled task to run it. The service manager (services.exe) is bypassed, and the parent of the shell is taskeng.exe or taskhostw.exe.
  * The Fix: Set up a separate rule to monitor task registrations and executions from the C:\Windows\System32\Tasks folders.

* Problem 3: Standard enterprise agents (e.g. McAfee, SCCM)
  * The Issue: Enterprise agents often run as services and periodically spawn update scripts or configuration tasks, triggering false alarms under broad parent-child checks.
  * The Fix: Add explicit whitelist exclusions for the specific, signed service binaries belonging to authorized enterprise agents (e.g. McAfee, Symantec, Tanium).
