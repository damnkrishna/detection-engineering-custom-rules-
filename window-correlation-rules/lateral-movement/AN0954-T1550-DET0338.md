### **1. Technique Breakdown: T1550**

* **What it is:** **Use Alternate Authentication Material**. Adversaries may use alternate authentication material, such as password hashes (Pass-the-Hash), Kerberos tickets (Pass-the-Ticket), or access tokens, to authenticate to a system and move laterally without knowing the plaintext password. On Windows systems, tools like Mimikatz or Rubeus generate a Logon Type 9 (NewCredentials) session when credentials are cloned or impersonated for outbound network usage (e.g. `runas /netonly` or ticket injection).
* **Log Source Requirements:** Windows Security Event Log ID 4624 (Successful Logon) which records the Logon Type and authentication mechanism.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Wazuh collects Windows Security Event ID 4624, which contains the logon type, source IP address, target user account, and process name.
    * **NIDS (Suricata + Zeek): NO.** Alternate authentication using local session cloning or ticket cache injection occurs host-locally before outbound network requests are made. While NIDS can flag anomalies in Kerberos traffic (e.g. unusual encryption types), it cannot directly observe logon session creation details.

### **2. Custom Sigma Rule**

This rule utilizes **Windows Security Event ID 4624 (Successful Logon)** to detect successful logons of Type 9 (NewCredentials), indicating impersonation or alternate credential usage.

```yaml
title: Alternate Authentication Material - Logon Type 9 (AN0954)
id: 74bde7cd-79fb-44ae-bd48-51829210d551
status: experimental
description: Detects successful authentication events utilizing logon type 9 (NewCredentials), which is generated when alternate credentials are used for outbound authentication (e.g. Pass-the-Hash or Pass-the-Ticket).
author: Krishna Gupta
date: 2026-06-07
logsource:
    product: windows
    service: security
    # Relies on Windows Security Event ID 4624
detection:
    selection:
        EventID: 4624
        LogonType: 9
    condition: selection
falsepositives:
    - Administrative scripts or software deployment tools (e.g. runas /netonly, backup utilities) connecting to remote shares under alternate administrative profiles.
level: medium
tags:
    - attack.lateral_movement
    - attack.t1550
    - analytics.an0954
    - detection.det0338
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Administrative Use of runas /netonly**
    * *The Issue:* Network administrators regularly use `runas /netonly` or script tools that access shares under different domain user profiles. This triggers Logon Type 9 events frequently and generates alerts.
    * *The Fix:* Maintain a whitelist of authorized administrator accounts or hostnames that are permitted to perform Logon Type 9 authentications. Filter out automated server backup processes or administrative workstations.

* **Problem 2: Pass-the-Hash Bypassing Logon Type 9 (Local Administrator Restricting Outbound)**
    * *The Issue:* Local Pass-the-Hash (e.g., executing commands as `SYSTEM` via token manipulation or passing local Administrator hashes) may show up as Logon Type 3 (Network) or Logon Type 2 (Interactive) depending on the configuration and targeted services.
    * *The Fix:* Complement this rule by monitoring Event ID 4624 with Logon Type 3 using NTLM authentication instead of Kerberos, especially where the key length is 0 or the workstation name is empty.

* **Problem 3: Kerberos Ticket lifetime / Overpass-the-Hash**
    * *The Issue:* If the ticket is injected directly into a process that was already authenticated under another Logon Type, the logon event has already occurred. Subsequent network operations might use the injected ticket silently without spawning a new Logon Type 9 on the source host.
    * *The Fix:* Monitor active directory domain controller logs (Event ID 4768 - Kerberos Authentication Ticket Requested, and Event ID 4769 - Kerberos Service Ticket Requested) looking for anomalous ticket requests with short lifetimes or mismatched workstation names.
