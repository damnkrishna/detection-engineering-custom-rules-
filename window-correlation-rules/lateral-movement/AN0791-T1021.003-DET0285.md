### **1. Technique Breakdown: T1021.003**

* **What it is:** **Remote Services: Distributed COM**. Adversaries use Distributed Component Object Model (DCOM) interfaces (such as `MMC20.Application`, `ShellWindows`, or `ShellBrowserWindow` COM objects) to execute arbitrary commands remotely on targets. When accessed, the system DCOM service host (`svchost.exe` launching `DcomLaunch`) spawns the corresponding DCOM server host process (like `mmc.exe`, `explorer.exe`, or `dllhost.exe`), which in turn executes the attacker's command by spawning a shell interpreter (`cmd.exe` or `powershell.exe`). This distinctive parent-child-grandchild pattern is highly indicative of DCOM abuse.
* **Log Source Requirements:** Sysmon process creation logs (Event ID 1) capturing process command line and parent/grandparent relationships.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 logs the parent process of a newly spawned shell. If the parent is `mmc.exe` or `explorer.exe` and its parent is `svchost.exe`, this chain represents DCOM execution.
    * **NIDS (Suricata + Zeek): YES.** Network logs capture RPC/DCOM bind requests targeting remote endpoints, but host logs are required to confirm successful command launch.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect command-line interpreters spawned by typical DCOM server binaries (such as `mmc.exe`, `explorer.exe`, or `dllhost.exe`) where the parent process is spawned in a DCOM service host context.

```yaml
title: Lateral Movement - DCOM Server Spawning Suspicious Shell (AN0791)
id: 69555c7e-4226-4d1f-9082-4530593ed5c1
status: experimental
description: Detects command-line interpreters (cmd.exe, powershell.exe) spawned by DCOM server hosts (mmc.exe, explorer.exe, dllhost.exe) that are launched under the system DCOM service, indicating DCOM-based remote code execution.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_parent:
        ParentImage|endswith:
            - '\mmc.exe'
            - '\explorer.exe'
            - '\dllhost.exe'
    selection_child:
        - Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\mshta.exe'
        - OriginalFileName:
            - 'Cmd.Exe'
            - 'PowerShell.EXE'
            - 'wscript.exe'
            - 'cscript.exe'
            - 'mshta.exe'
    filter_user:
        # Standard user-session explorer.exe spawning shells is ignored (needs manual developer checks)
        ParentCommandLine|contains:
            - ' /factory' # COM server flag
            - '-embedding'
    condition: selection_parent and selection_child and filter_user
fields:
    - Image
    - OriginalFileName
    - ParentCommandLine
    - ParentImage
falsepositives:
    - Legitimate administration scripts triggered via COM objects by automated software (e.g., local backup agent launching command triggers).
level: high
tags:
    - attack.lateral-movement
    - attack.t1021.003
    - analytics.an0791
    - detection.det0285
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Explorer.exe running in user context (Zebra spawning)**
    * *The Issue:* Users naturally open command prompts from inside Explorer (`explorer.exe`) by double-clicking batch files or typing `cmd` in the folder address bar. This matches the parent-child rule and generates massive false alarms.
    * *The Fix:* Differentiate by looking for the `/factory` or `-embedding` flags in the parent command line, which denote COM initialization rather than standard desktop user-shell launch.

* **Problem 2: Use of non-standard COM classes**
    * *The Issue:* Attackers can use custom-registered COM applications that are not standard (e.g. custom business application wrappers) to spawn shells, bypassing checks for `mmc.exe` or `explorer.exe`.
    * *The Fix:* Monitor the registry entries for new COM class registrations (`HKLM\Software\Classes\CLSID\`) that define executable paths.

* **Problem 3: Grandparent Process resolution**
    * *The Issue:* Standard process logs only report the direct parent image. If the intermediate process is ephemeral and terminates quickly, identifying the grandparent process (`svchost.exe`) requires event correlation.
    * *The Fix:* Correlate process creation events (Sysmon Event ID 1) utilizing the parent process GUID to trace execution chains back to the root initiator.
