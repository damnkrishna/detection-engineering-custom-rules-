### **1. Technique Breakdown: T1072**

* **What it is:** **Software Deployment Tools**. Adversaries abuse third-party or native enterprise software deployment agents (such as Microsoft Endpoint Configuration Manager/SCCM `CcmExec.exe`, PDQ Deploy, Altiris, or Group Policy installation wrappers) to run administrative tasks or deploy malware laterally across a network of systems. Detection focuses on identifying deployment agent parent processes launching interactive shells (`cmd.exe`, `powershell.exe`) or network utility tools with high privileges.
* **Log Source Requirements:** Sysmon process creation logs (Event ID 1) capturing parent-child process execution contexts.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 1 provides detailed parent process path information, letting defenders look for SCCM or PDQ binaries spawning shells.
    * **NIDS (Suricata + Zeek): PARTIAL.** Network tools can track deployment protocol queries, but cannot verify the specific local process lineage on endpoints.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 1 (Process Creation)** to detect common enterprise software deployment agent binaries spawning command shell interpreters or script hosts.

```yaml
title: Lateral Movement - Deployment Agent Spawning Suspicious Shell (AN0623)
id: 8670912b-6848-44f4-9ee5-98442d5bb2e6
status: experimental
description: Detects software deployment agent processes (such as SCCM, PDQ Deploy, Altiris) spawning command-line interpreters or script hosts, indicating potential lateral movement or deployment abuse.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1 collected via Wazuh
detection:
    selection_parent:
        ParentImage|endswith:
            - '\CcmExec.exe' # SCCM Agent
            - '\PDQDeployService.exe' # PDQ Deploy
            - '\PDQDeployConsole.exe'
            - '\AeXNSAgent.exe' # Symantec/Altiris Agent
            - '\gpscript.exe' # Group Policy Script wrapper
    selection_child:
        - Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\mshta.exe'
        - OriginalFileName:
            - 'Cmd.Exe'
            - 'PowerShell.EXE'
            - 'wscript.exe'
            - 'cscript.exe'
            - 'mshta.exe'
    condition: selection_parent and selection_child
fields:
    - Image
    - OriginalFileName
    - ParentImage
falsepositives:
    - Legitimate software setup scripts or administrative maintenance tasks triggered via Group Policy or corporate SCCM packages.
level: medium
tags:
    - attack.lateral-movement
    - attack.t1072
    - analytics.an0623
    - detection.det0223
```

    - attack.lateral-movement

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: High Volume of Authorized Setup Scripts (Noise)**
    * *The Issue:* Deployment agents routinely run installation batch scripts or configuration scripts during standard enterprise application rollouts, triggering high false alarm rates.
    * *The Fix:* Whitelist approved package installation command lines, or limit alerts to instances where the child process spawns further network utilities (e.g. `curl.exe`).

* **Problem 2: Execution via Service installation wrapper**
    * *The Issue:* PDQ Deploy and SCCM often execute packages by dynamically registering a new Windows Service on target systems that runs target payloads. In this case, the parent of the shell is `services.exe` rather than the deployment agent binary.
    * *The Fix:* Add a rule checking for `services.exe` spawning unexpected cmd/powershell binaries executing out of admin sharing directories (like `ADMIN$\Temp`).

* **Problem 3: In-Memory Script Engine Hosting**
    * *The Issue:* If the deployment package runs a signed C# installer wrapper that leverages internal APIs to run scripts in-memory without spawning `powershell.exe`, parent-child checks are bypassed.
    * *The Fix:* Enable Script Block Logging (Event ID 4104) and look for script block parameters running under the SYSTEM context of the SCCM service process.
