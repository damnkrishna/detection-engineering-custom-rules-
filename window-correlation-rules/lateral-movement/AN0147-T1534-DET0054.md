### **1. Technique Breakdown: T1534**

* **What it is:** **Internal Spearphishing**. Adversaries compromise a trusted internal user account and use it to send spearphishing emails containing malicious links or attachments to other employees inside the same organization. Since the sender is an internal employee, these emails successfully bypass standard external gateway email scanners. Detection focuses on identifying endpoints running scripts or automation commands (like PowerShell or C# SMTP wrappers) that initiate raw network connections to internal mail servers over SMTP/IMAP ports to send messages out-of-band.
* **Log Source Requirements:** Sysmon network connection logs (Event ID 3) and process creation logs (Event ID 1) tracking email execution.
* **Coverage Check:**
    * **HIDS (Sysmon + Wazuh): YES.** Sysmon Event ID 3 logs socket setups by local applications (like PowerShell or Outlook) targeting mail servers (ports 25, 587, 465). Wazuh aggregates these logs.
    * **NIDS (Suricata + Zeek): YES.** Network logs track SMTP headers and file attachments between internal IPs, which is highly effective for detecting internal propagation.

### **2. Custom Sigma Rule**

This rule utilizes **Sysmon Event ID 3 (Network Connection)** to detect non-standard scripting interpreters (like PowerShell, cmd, or cscript) or user applications initiating direct network connections to internal mail gateways over SMTP ports, suggesting programmatic internal spearphishing propagation.

```yaml
title: Lateral Movement - Script Host Initiating Outbound SMTP Connection (AN0147)
id: ee1ce43e-9d39-4a37-852b-712055fb8a84
status: experimental
description: Detects command-line interpreters or scripting hosts initiating direct outbound TCP connections to mail gateway ports (25, 465, 587), suggesting automated internal spearphishing or mail worm propagation.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: network_connection
    product: windows
    # Relies on Sysmon Event ID 3 collected via Wazuh
detection:
    selection_process:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\cmd.exe'
            - '\wsmprovhost.exe'
    selection_ports:
        DestinationPort:
            - 25  # SMTP
            - 465 # SMTPS
            - 587 # SMTP submission
    condition: selection_process and selection_ports
fields:
    - DestinationPort
    - Image
falsepositives:
    - Legitimate administrative scripts or scheduled tasks configured to email log files or reports to the IT team.
level: high
tags:
    - attack.lateral-movement
    - attack.t1534
    - analytics.an0147
    - detection.det0054
```

### **3. Blind Spots & Tuning (The "Problems")**

* **Problem 1: Use of Microsoft Graph API / MAPI COM interfaces**
    * *The Issue:* If the attacker uses Outlook COM APIs (e.g. `$outlook = New-Object -ComObject Outlook.Application`) to send emails, the actual network socket connection to the mail server is initiated by the background Outlook process (`outlook.exe`), not by `powershell.exe`. The parent-child network check will see only legitimate Outlook traffic.
    * *The Fix:* Complement this rule by monitoring script actions that access Outlook COM components (PowerShell Event ID 4104 searching for `Outlook.Application` or `CreateItem`).

* **Problem 2: Authorized IT Alerting Automation (Noise)**
    * *The Issue:* Helpdesk systems, monitor agents, or backup solutions spawn automated scripts daily to send system notification alerts via SMTP, generating false alerts.
    * *The Fix:* Baseline the environment to whitelist specific service account usernames and authorized source IP addresses designated for automated mail notifications.

* **Problem 3: SMTP over Web API (HTTP/HTTPS)**
    * *The Issue:* If the organization uses a cloud email provider (like Microsoft 365 or Google Workspace) and the script sends emails via REST HTTPS API endpoints rather than port 25/587, the destination port will be 443, bypassing static SMTP port checks.
    * *The Fix:* Monitor web proxy logs for high-frequency POST requests to mail service provider API paths (e.g., `graph.microsoft.com/v1.0/users/*/sendMail`) originating from unusual endpoints.
