### 1. Technique Breakdown: T1110.002

* What it is: Brute Force: Password Cracking. This involves adversaries attempting to recover usable, cleartext passwords from stolen cryptographic hashes (like the NTLM hashes they might have grabbed from the SAM dump). While adversaries usually do this offline on their own hardware, they occasionally execute cracking utilities (like Hashcat or John the Ripper) or script-based cracking routines directly onto compromised endpoints.
* Log Source Requirements: Host process creation and command line logs (Sysmon Event ID 1 / Windows Security Event ID 4688) tracking execution, and PowerShell script block logs (Sysmon Event ID 4104) tracking script content.
* Coverage Check:
  * HIDS (Sysmon + Windows Defender): YES. Sysmon Event ID 1 (Process Creation) is the primary telemetry source for binary execution. Sysmon Event ID 4104 (Script Block) is effective at catching script-based crackers run entirely in memory.
  * Windows Security Logs: YES. Standard Security Logs track process execution (Event ID 4688) containing the command line arguments.
* Log Sources Covered:
  - Sysmon Event ID 1 (process_creation)
  - Sysmon Event ID 4104 (ps_script)
* Log Sources Missing / Unused:
  - None.
* Conclusion: Password cracking tool execution on local endpoints can be detected using process creation and PowerShell script block logs.

### 2. Custom Sigma Rule

The detection logic is split into executable execution monitoring and script block content monitoring.

Rule 1 of 2: Local Password Cracking Activity via CLI (Process Creation)
```yaml
title: Local Password Cracking Activity via CLI (AN0292-A)
id: 9b2d8e41-3a1f-4b92-8c7a-5f6d7e8a9b0c
status: experimental
description: Detects the execution of known password cracking utilities (like Hashcat or John the Ripper) or their associated command-line arguments on a local endpoint, indicating local brute-force password cracking.
author: Krishna Gupta
date: 2026-06-12
logsource:
    category: process_creation
    product: windows
detection:
    selection_tools:
        - Image|endswith:
            - '\hashcat.exe'
            - '\john.exe'
        - OriginalFileName:
            - 'hashcat.exe'
            - 'john.exe'
    selection_hashcat_args:
        CommandLine|contains:
            - ' -a '
            - ' --attack-mode '
            - ' -a='
            - ' --attack-mode='
    selection_hashcat_type:
        CommandLine|contains:
            - ' -m '
            - ' --hash-type '
            - ' -m='
            - ' --hash-type='
    selection_cmdline_john:
        CommandLine|contains:
            - '--wordlist='
            - '--format='
            - '--rules'
            - '--single'
            - '--incremental'
            - '--show'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: (selection_tools or (selection_hashcat_args and selection_hashcat_type) or selection_cmdline_john) and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Authorized penetration testing or red team engagements.
    - Password auditing conducted by the internal security team.
level: high
tags:
    - attack.credential-access
    - attack.t1110.002
    - analytic.an0292
    - detection.det0105
```

Rule 2 of 2: Local Password Cracking Activity via PowerShell Script Block (Script Block)

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Offline Cracking (The Ultimate Evasion)
  * The Issue: Most adversaries do not run cracking tools on target machines; they exfiltrate hashes and crack offline.
  * The Fix: Detect the hash dumping and network exfiltration techniques separately.

* Problem 2: Custom Tools and Renaming
  * The Issue: Custom tools or modified names will bypass selection_tools blocks.
  * The Fix: Rely on command-line parameter filters and monitor host GPU utilization spikes.

* Problem 3: PowerShell In-Memory Cracking
  * The Issue: Cracking logic loaded directly into memory bypasses binary execution detection.
  * The Fix: Enable PowerShell Script Block Logging (EID 4104) and match on typical script strings via Rule 2.
