### 1. Technique Breakdown: T1078.003

* What it is: Valid Accounts: Local Accounts. Local accounts exist on individual systems and are managed locally (e.g., the built-in local `Administrator` account). Adversaries exploit local accounts to move laterally between endpoints (using Logon Type 3 network connections) by leveraging credential reuse (where multiple workstations share the same local administrator password). Monitoring successful network logons using local administrative accounts is a highly effective method to identify lateral movement.
* Log Source Requirements: Windows Security Event Log capturing authentication events (Event ID 4624 for successful logon) containing user names, domain names (specifically local domains or Workgroups), logon types, and source IP addresses.
* Coverage Check:
* HIDS (Sysmon + Wazuh): YES. Windows Security Event ID 4624 logs network logon sessions on endpoints. Wazuh aggregates these logs.
* NIDS (Suricata + Zeek): YES (Partial). Network monitoring tools can trace NTLM/SMB handshakes over the network, but cannot verify if the credentials were successfully validated by the local Security Accounts Manager (SAM) database.

### 2. Custom Sigma Rule

This rule utilizes Windows Security Event ID 4624 (Successful Logon) to detect network logons (Logon Type 3) using local administrator accounts, indicating credential reuse or lateral movement.

```yaml
title: Local Administrator Network Logon (AN1137)
id: defed6a9-15e0-4767-b56d-37529bbfcb51
status: experimental
description: Detects successful network logons (Logon Type 3) using local administrator accounts, which is a common indicator of lateral movement or credential reuse.
author: Krishna Gupta
date: 2026-06-07
logsource:
    product: windows
    service: security
    # Relies on Windows Security Event ID 4624
detection:
    selection_event:
        EventID: 4624
    selection_logon_type:
        LogonType:
            - 3 # Network Logon
    selection_local_admin:
        TargetUserName:
            - 'Administrator'
    selection_domain_exclusion:
 # On domain joined machines, local logins will list the computer name or NT AUTHORITY/WORKGROUP as domain, not the Active Directory domain
        TargetDomainName:
            - 'WORKGROUP'
            - 'NT AUTHORITY'
            - 'NT SERVICE'
    condition: selection_event and selection_logon_type and selection_local_admin and selection_domain_exclusion
fields:
    - EventID
    - LogonType
    - TargetDomainName
    - TargetUserName
falsepositives:
    - Automated inventory scanners or local vulnerability assessment agents utilizing local admin credentials.
level: high
tags:
    - attack.defense-evasion
    - attack.persistence
    - attack.privilege-escalation
    - attack.t1078.003
    - analytic.an1137
    - detection.det0360
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Administrative Action False Positives
  * The Issue: IT personnel performing legitimate maintenance operations can invoke techniques that mirror adversarial persistence or evasion.
  * The Fix: Audit and baseline corporate administration accounts, whitelisting specific approved service accounts and administrative subnets.

* Problem 2: Command and Execution Obfuscation
  * The Issue: Attackers employ encoding, environment variables, or caret insertions to bypass keyword-based detection filters.
  * The Fix: Enable deep logging (such as Script Block Logging) and apply normalization or regex decoding inside the SIEM parsing pipeline.

* Problem 3: Log Deletion and Modification
  * The Issue: Adversaries can clear security logs or stop monitoring agents (like Wazuh or Sysmon) to blind defensive operations.
  * The Fix: Forward all endpoint logs immediately to a centralized write-once SIEM and alert on service stoppage or log clearing events.
