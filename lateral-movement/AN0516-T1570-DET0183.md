### 1. Technique Breakdown: T1570

* What it is: Lateral Tool Transfer. Adversaries may transfer tools or other files from one system to another inside a compromised environment (lateral movement). They often copy utilities, scripts, or credential access tools to administrative network shares (such as C$, ADMIN$, IPC$) on a remote machine using built-in command-line copy/move tools (e.g. copy, move, xcopy.exe, robocopy.exe). Once the files are successfully copied, they are executed remotely.
* Log Source Requirements: Host process creation and command line logs (Sysmon Event ID 1 / Windows Security Event ID 4688).
* Coverage Check:
  * HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 1 captures the creation of command-line processes (cmd.exe, powershell.exe, xcopy.exe, robocopy.exe) and lists their full command arguments, allowing checks for network share formats.
  * NIDS (Suricata + Zeek): NO. While network monitoring can inspect SMB file transfer headers, decoding the command line of the process that initiated the transfer on the source system requires host-level auditing.
* Log Sources Covered:
  - Sysmon Event ID 1 (process_creation)
  - Sysmon Event ID 11 (file_event)
* Log Sources Missing / Unused:
  - None.
* Conclusion: Lateral tool transfer can be detected using process creation and file event logs.

### 2. Custom Sigma Rule

The detection logic is split into process creation monitoring and file event monitoring.

Rule 1 of 2: Lateral Tool Transfer to Administrative Shares (Process Creation)
```yaml
title: Lateral Tool Transfer to Administrative Shares (AN0516)
id: 1a59e4fb-05c9-49c1-98ca-bae5c8832b27
status: experimental
description: Detects command-line copy or file transfer utilities (copy, move, xcopy, robocopy) targeting administrative shares (e.g. C$, ADMIN$), which can indicate lateral tool transfer.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
detection:
    selection_utilities:
        - Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\xcopy.exe'
            - '\robocopy.exe'
        - OriginalFileName:
            - 'Cmd.exe'
            - 'PowerShell.EXE'
            - 'pwsh.dll'
            - 'xcopy.exe'
            - 'robocopy.exe'
    selection_shares:
        CommandLine|contains:
            - '\C$'
            - '\ADMIN$'
            - '\IPC$'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: selection_utilities and selection_shares and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Normal administrative scripts or deployment agents transferring tools, configuration scripts, or patches to administrative shares.
level: medium
tags:
    - attack.lateral-movement
    - attack.t1570
    - analytic.an0516
    - detection.det0183
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Custom/Renamed File Transfer Utilities
  * The Issue: Attackers can rename built-in utilities (e.g. renaming xcopy.exe to update.exe) or bring their own custom Go/Rust compiled network copy programs, which will bypass rules checking for specific binary names.
  * The Fix: Complement this rule by monitoring SMB traffic in network logs or auditing directory modifications (Sysmon ID 11) within remote hosts' administrative directories regardless of which source process initiates the write.

* Problem 2: Mapping Shares to Local Drive Letters First
  * The Issue: An attacker can mount an administrative share to a local drive letter first (e.g. net use z: \\Target\C$) and then run a simple copy payload.exe z:\. The copy utility command line will only show z:\ as the target, bypassing shares string matching.
  * The Fix: Monitor command-line options of drive mapping utilities (like net.exe use or New-PSDrive) or track network connections established by host shell processes.

* Problem 3: Legitimate File Server Deployments
  * The Issue: Automated backup services, cluster synchronization scripts, and domain controllers copying Group Policy templates (SYSVOL) frequently write to administrative volumes.
  * The Fix: Maintain a verified list of backup and sync service accounts and ignore transfers initiated from these specific system contexts.
