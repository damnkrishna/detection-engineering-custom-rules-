### 1. Technique Breakdown: T1542

* What it is: Pre-OS Boot. Adversaries may manipulate boot logs or system firmware (e.g. BIOS/UEFI) to establish persistence that survives operating system reinstallation, driver loading checks, and hard drive wiping. This is detected by monitoring the execution of firmware flash utilities or low-level disk access tools that interact with motherboard ROM chips.
* Log Source Requirements:
  * Sysmon Process Creation (Event ID 1) auditing low-level firmware manipulation commands and vendor bios utilities.
* Coverage Check:
  * HIDS (Sysmon): YES. Processes launched to perform bios updates generate telemetry.
  * NIDS (Zeek/Suricata): NO. Firmware modification is entirely local to the endpoint hardware.
* Log Sources Covered:
  * Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
  * None.

### 2. Custom Sigma Rule

The following rule monitors the process creation log for execution of common firmware flashing tools, motherboard vendor BIOS update utilities, or commands containing bios update parameters.

```yaml
title: System Firmware or BIOS Flash Utility Execution (AN2121)
id: f1a2b3c4-e5f6-7a8b-9c0d-1e2f3a4b5c82
status: experimental
description: "Detects the execution of known bios flash utilities, motherboard firmware tools (e.g. flashrom, HpBiosUpdate, WinFlash, ASUS WinFlash), or command lines modifying UEFI settings, indicating potential pre-OS boot persistent modification."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: process_creation
    product: windows
detection:
    selection_images:
        Image|endswith:
            - '\flashrom.exe'
            - '\winflash.exe'
            - '\HpBiosUpdate.exe'
            - '\fwupd.exe'
    selection_ofn:
        OriginalFileName:
            - 'flashrom.exe'
            - 'WinFlash.exe'
            - 'HpBiosUpdate.exe'
            - 'fwupd.exe'
    selection_cli:
        CommandLine|contains:
            - 'bios'
            - 'firmware'
            - 'uefi'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    filter_vendor:
        ParentImage|endswith:
            - '\HPSupportSolutionsFramework.exe'
            - '\AsusSystemControl.exe'
    condition: (selection_images or selection_ofn) and selection_cli and not (filter_installer or filter_vendor)
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - User
falsepositives:
    - IT support personnel or automated system update software executing BIOS/firmware update scripts during maintenance routines.
level: high
tags:
    - attack.persistence
    - attack.t1542
    - analytic.an2121
    - detection.det0978
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Exploitation via signed kernel drivers
  * The Issue: If the attacker loads a signed vulnerable vendor driver (BYOVD) to write directly to physical memory and reprogram the SPI flash chip, no user-mode bios flash utility will be executed.
  * The Fix: Monitor Sysmon Event ID 6 (Driver Load) for vulnerable firmware update drivers (e.g. ASUS/Gigabyte bios drivers) and trace anomalous system calls.
* Problem 2: Vendor-specific update agents
  * The Issue: Dell, HP, Lenovo, and ASUS update clients run firmware checkers periodically, which matches keywords like `bios` or `firmware` and triggers alerts.
  * The Fix: Whitelist the specific executable hashes and parent processes (like vendor update services) in your environment.
* Problem 3: Local script commands
  * The Issue: Scripting queries using WMI classes (e.g., `Get-WmiObject -Class Win32_BIOS`) will trigger alerts due to broad keyword matching.
  * The Fix: Exclude read-only query parameters like `get` or `list` from matching command-line scopes.
