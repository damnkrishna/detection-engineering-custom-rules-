### 1. Technique Breakdown: T1037

* What it is: Boot or Logon Initialization Scripts. Adversaries may use boot or logon initialization scripts to automatically execute malicious payloads during system startup or user logon. For example, attackers can write command strings to registry paths like `HKCU\Environment\UserInitMprLoopbackScript` or alter the `Userinit` registry key, which the system executes during the initialization process before showing the user desktop.
* Log Source Requirements:
  * Sysmon Registry Value Set (Event ID 13) capturing modifications to logon script registry paths.
* Coverage Check:
  * HIDS (Sysmon): YES. Registry writes to the Environment or Winlogon logon script keys generate Event ID 13.
  * NIDS (Zeek/Suricata): NO. Registry manipulation is a local endpoint activity.
* Log Sources Covered:
  * Sysmon Event ID 13 (registry_event)
* Log Sources Missing / Unused:
  * None.

### 2. Custom Sigma Rule

The following rule monitors for the creation or modification of Windows logon and loopback startup script configuration parameters in the registry.

```yaml
title: User Logon Initialization Script Registry Modification (AN2112)
id: f1a2b3c4-e5f6-7a8b-9c0d-1e2f3a4b5c90
status: experimental
description: "Detects modifications to Windows registry keys that configure user logon or initialization scripts (such as UserInitMprLoopbackScript or Userinit parameters), which can be abused by adversaries to achieve persistent execution during user logon."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: registry_set
    product: windows
detection:
    selection_registry_paths:
        TargetObject|contains:
            - '\Environment\UserInitMprLoopbackScript'
            - '\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\Userinit'
            - '\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\VMApplet'
    filter_legitimate_userinit:
        # Default Windows userinit path is normal
        Details: 'C:\Windows\system32\userinit.exe,'
    condition: selection_registry_paths and not filter_legitimate_userinit
fields:
    - TargetObject
    - Details
    - Image
    - User
falsepositives:
    - Group policy updates or domain administrators legitimately deploying logon scripts for user mappings or login notices.
level: high
tags:
    - attack.persistence
    - attack.t1037
    - analytic.an2112
    - detection.det0969
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Local Policy files injection (scripts.ini)
  * The Issue: If the attacker drops the script directly into the local Group Policy templates folder (e.g. `C:\Windows\System32\GroupPolicy\User\Scripts\scripts.ini`) without modifying the `UserInitMprLoopbackScript` registry key, this rule will not trigger.
  * The Fix: Implement a companion rule targeting Sysmon Event ID 11 (File Creation) for any `.ini` files written to the `GroupPolicy` subfolders by non-standard processes.
* Problem 2: Active Directory logon script path
  * The Issue: If the script is configured directly in the Active Directory user object properties (the `scriptPath` attribute in AD) rather than the local machine registry, this rule will not trigger.
  * The Fix: Enable auditing for Directory Service Changes (Event ID 5136) on Domain Controllers and monitor changes to the `scriptPath` attribute of user objects.
* Problem 3: Normal administrative loopback script configurations
  * The Issue: In corporate environments using folder redirection or mapped drives, admins might legitimately configure loopback scripts, causing false positives.
  * The Fix: Create exclusions in the SIEM for trusted central domain paths (e.g. `\\domain.local\SysVol\`).
