### 1. Technique Breakdown: T1098

* What it is: Account Manipulation. Adversaries may manipulate user or computer accounts to gain persistent access, escalate privileges, or evade detection. This can involve adding a user to administrative groups (e.g., Domain Admins or Administrators) or changing account properties (like setting passwords to not expire or enabling delegate options).
* Log Source Requirements:
  * Windows Security Event logs (service: security) capturing group membership modifications and user property changes.
* Coverage Check:
  * HIDS (Windows Security Event Logs): YES. Native Windows event logging generates specific event IDs for account modifications.
  * NIDS (Zeek/Suricata): NO. Active Directory modifications occur locally on Domain Controllers and are audited via host logs.
* Log Sources Covered:
  * Windows Security Event ID 4728 (A member was added to a security-enabled global group)
  * Windows Security Event ID 4732 (A member was added to a security-enabled local group)
  * Windows Security Event ID 4756 (A member was added to a security-enabled universal group)
  * Windows Security Event ID 4738 (A user account was changed)
* Log Sources Missing / Unused:
  * None.

### 2. Custom Sigma Rule

The following rule monitors the Windows Security Event log for modifications that add users to highly privileged security groups or alter critical account flags.

```yaml
title: Privileged Account or Group Membership Manipulation (AN2114)
id: f1a2b3c4-e5f6-7a8b-9c0d-1e2f3a4b5d95
status: experimental
description: "Detects the addition of users to administrative or privileged groups (Domain Admins, Enterprise Admins, Schema Admins, Local Administrators) or critical modifications to account properties (such as enabling Password Not Required or altering logon permissions) in Windows Security logs."
author: Krishna Gupta
date: 2026-07-01
logsource:
    service: security
    product: windows
detection:
    selection_group_adds:
        EventID:
            - 4728
            - 4732
            - 4756
        # Target privileged group names
        TargetUserName:
            - 'Administrators'
            - 'Domain Admins'
            - 'Enterprise Admins'
            - 'Schema Admins'
            - 'Account Operators'
            - 'Backup Operators'
    selection_account_changes:
        EventID: 4738
        # Look for suspicious flag changes like setting password not required or preauth bypass
        UserAccountControl|contains:
            - 'Password Not Required'
            - "Don't Require Preauth"
            - 'Trusted For Delegation'
            - 'Trusted To Authenticate For Delegation'
    filter_machine_accounts:
        # Exclude standard computer account self-updates
        SubjectUserName|endswith: '$'
    condition: (selection_group_adds or selection_account_changes) and not filter_machine_accounts
fields:
    - EventID
    - TargetUserName
    - SubjectUserName
    - MemberName
    - UserAccountControl
falsepositives:
    - Standard identity management workflows or IT administrators creating, modifying, or promoting accounts during onboarding or maintenance.
level: high
tags:
    - attack.persistence
    - attack.t1098
    - analytic.an2114
    - detection.det0971
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Custom/Localized Group Names
  * The Issue: If the target system is localized in another language (e.g., "Administratoren" in German), the hardcoded English group names in `selection_group_adds` will not match.
  * The Fix: Use Group SIDs (such as `S-1-5-32-544` for local Administrators or `S-1-5-21-*-512` for Domain Admins) instead of text strings when querying group addition events.
* Problem 2: Mass administration automation noise
  * The Issue: Service accounts running provisioning scripts (like IAM tools or azure sync agents) add hundreds of users legitimately, causing alerts.
  * The Fix: Whitelist the specific IAM service account usernames in `filter_machine_accounts` or create a separate baseline rule for automated accounts.
* Problem 3: Delegated rights directly to active directory objects
  * The Issue: If permission delegation is configured directly on an AD organizational unit (OU) rather than altering group memberships, Event ID 4728/4732 will not trigger.
  * The Fix: Enable auditing for Directory Service changes (Event ID 5136) and monitor write permissions onto OU ACLs.
