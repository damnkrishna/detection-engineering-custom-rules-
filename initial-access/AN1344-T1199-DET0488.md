### 1. Technique Breakdown: T1199

* What it is: Trusted Relationship. Adversaries exploit existing trust connections between target networks and external entities (such as IT managed service providers (MSPs), supply-chain partners, or vendor remote support services). Once they compromise the partner's network, they use legitimate remote access pathways (e.g., VPNs, remote desktop connections, or dedicated service accounts) to access the target environment, which makes distinguishing malicious activity from normal administration very difficult.
* Log Source Requirements: Windows Security Event Log Event ID 4624 (Logon) capturing Logon Types, user domains, and source IP addresses.
* Coverage Check:
  * HIDS (Sysmon + Wazuh): YES. Windows Security Event ID 4624 logs network logons (Logon Type 3) or RDP logons (Logon Type 10), and tracks the workstation name and IP. Wazuh aggregates these and alerts on anomalous combinations.
  * NIDS (Suricata + Zeek): YES. Network logs track connection activity from known third-party networks, but auditing the credentials used requires endpoint authentication logs.
* Log Sources Covered:
  - Windows Security Event ID 4624 (authentication)
* Log Sources Missing / Unused:
  - None.
* Conclusion: Trusted relationship abuse can be detected using remote authentication logs.

### 2. Custom Sigma Rule

This rule utilizes Windows Security Event ID 4624 (Successful Logon) to detect third-party administrative or vendor support accounts logging in from unusual or non-standard external IP addresses.

```yaml
title: Trusted Relationship Abuse - Anomalous Third-Party Administrative Logon (AN1344)
id: aca5e43c-0be4-43b3-a575-a5a46b7ab571
status: experimental
description: Detects successful authentication events by service provider (MSP) or third-party vendor accounts from non-standard source IP addresses or outside baseline administrative windows.
author: Krishna Gupta
date: 2026-06-08
logsource:
    product: windows
    service: security
detection:
    selection_logon:
        EventID: 4624
        LogonType:
            - 3  # Network logon (e.g., remote administration, API)
            - 10 # RDP logon
    selection_accounts:
        - TargetUserName|contains:
            - 'vendor_'
            - 'msp_'
            - 'admin_'
            - 'support_'
        - TargetDomainName|contains:
            - 'partner'
            - 'vendor'
            - 'service'
    filter_internal:
 # Exclude standard internal subnets if necessary (tune as per business baselines)
        IpAddress:
            - '127.0.0.1'
            - '::1'
    condition: selection_logon and selection_accounts and not filter_internal
fields:
    - EventID
    - IpAddress
    - LogonType
    - TargetDomainName
    - TargetUserName
falsepositives:
    - Legitimate remote administrative support by MSPs or external consultants.
level: high
tags:
    - attack.initial-access
    - attack.t1199
    - analytic.an1344
    - detection.det0488
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Dynamic IP ranges for remote MSP workers
  * The Issue: MSP staff connect from home networks or dynamic customer VPN pools, making static IP blacklists/whitelists highly prone to false positives or blind spots.
  * The Fix: Define static source CIDRs for MSP operations or rely on user authentication baselining (flagging logons originating from geographic areas that deviate from standard user operations).

* Problem 2: Shared Service Accounts
  * The Issue: Organizations often share generic vendor service accounts (e.g. `sql_vendor`), meaning distinguishing malicious use from legitimate access cannot rely on username alone.
  * The Fix: Enforce individual partner logins, use Multi-Factor Authentication (MFA), and correlate RDP logins with change-ticket IDs or approved change windows.

* Problem 3: Inadequate Account Naming Conventions
  * The Issue: If vendor accounts do not follow a standardized naming convention (like `vendor_`) and are indistinguishable from normal employees, this rule will not trigger.
  * The Fix: Implement a security group for all third-party/delegated admin accounts and modify the rule to query membership in that AD security group.
