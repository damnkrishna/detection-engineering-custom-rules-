### 1. Technique Breakdown: T1091

* What it is: Replication Through Removable Media. Adversaries copy malicious files (such as executables, shortcuts, or scripting payloads) to removable storage devices (like USB flash drives) to compromise other systems, especially air-gapped hosts. The detection monitors execution of scripts, interpreters, or binary utilities directly from removable media paths (e.g. drive paths mapped to typical removable letters like `D:\`, `E:\`, `F:\`, `G:\` etc., instead of the system partition `C:\`).
* Log Source Requirements: Sysmon process creation logs (Event ID 1) and PowerShell script block logs (Event ID 4104).
* Coverage Check:
  * HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 1 captures execution paths on non-system drives. Sysmon Event ID 4104 (Script Block) is effective at catching module loads or scripts referencing drive letters directly.
  * NIDS (Suricata + Zeek): NO. Network sensors have no visibility into local file system execution paths on physical host systems.
* Log Sources Covered:
  - Sysmon Event ID 1 (process_creation)
  - Sysmon Event ID 4104 (ps_script)
* Log Sources Missing / Unused:
  - None.
* Conclusion: Replication through removable media execution can be detected using process creation and PowerShell script block logs.

### 2. Custom Sigma Rule

The detection logic is split into command-line process path monitoring and script block content monitoring.

Rule 1 of 2: Removable Media - Execution of Script or Command from Removable Drive (Process Creation)
```yaml
title: Removable Media - Execution of Script or Command from Removable Drive (AN0841-A)
id: e4c87c0f-f578-463a-8a3a-1ab372eac49c
status: experimental
description: Detects command-line interpreters, script hosts, or remote utilities executing directly from non-system drive letters (e.g., D:\, E:\, F:\, G:\, H:\), which may indicate replication from removable USB devices.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: process_creation
    product: windows
detection:
    selection_drives:
        - Image|startswith:
            - 'D:\'
            - 'E:\'
            - 'F:\'
            - 'G:\'
            - 'H:\'
            - 'I:\'
        - CommandLine|contains:
            - 'D:\'
            - 'E:\'
            - 'F:\'
            - 'G:\'
            - 'H:\'
            - 'I:\'
    selection_executables:
        - Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\mshta.exe'
            - '\rundll32.exe'
            - '\regsvr32.exe'
            - '\curl.exe'
        - OriginalFileName:
            - 'Cmd.Exe'
            - 'PowerShell.EXE'
            - 'wscript.exe'
            - 'cscript.exe'
            - 'mshta.exe'
            - 'rundll32.exe'
            - 'regsvr32.exe'
    condition: selection_drives and selection_executables
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Users running legitimate backup scripts, developers testing code from secondary local SSD drives (mapped as D:\ or E:\), or software installs from CD/DVD optical drives.
level: high
tags:
    - attack.initial-access
    - attack.t1091
    - analytic.an0841
    - detection.det0301
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Secondary Internal SSD Mappings (False Positives)
  * The Issue: Many workstations contain multiple internal storage drives (e.g., an OS SSD mapped as `C:\` and a secondary data drive mapped as `D:\` or `E:\`). Users who run scripts from their local secondary drives will trigger false alerts.
  * The Fix: Differentiate between internal SATA/NVMe secondary drives and external USB removable drives by querying disk registration events (such as Kernel-PnP logs) or whitelisting authorized development folders.

* Problem 2: Execution via Copying to Local C:\ drive first
  * The Issue: If the adversary plugs in a USB, but copies the script or binary to `%TEMP%` or `%USERPROFILE%\Downloads` before executing it, this rule will not trigger because the execution path is on `C:\`.
  * The Fix: Correlate file writes (Event ID 11) where the creating process is `explorer.exe` copying files from a non-system drive to `C:\`, followed by execution of that file.

* Problem 3: Virtual/ISO Drive Mounting
  * The Issue: When a user double-clicks an `.iso` file, Windows automatically mounts it as a new virtual DVD drive letter (e.g. `E:\`). Executing payloads from this mounted drive behaves exactly like executing from a USB, which is highly dangerous but can also match legitimate installer mounts.
  * The Fix: Monitor mount events (Event ID 12 in the Microsoft-Windows-VHDMP log) and check if they correlate with immediate process spawns from the newly mounted volume.
