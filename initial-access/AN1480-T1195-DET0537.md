### 1. Technique Breakdown: T1195

* What it is: Supply Chain Compromise. Adversaries compromise third-party software products or updates prior to installation. Once the user installs the package, the installation process or the initial run of the binary triggers post-compromise actions (such as writing persistence registry keys, dropping payload files to temp directories, or spawning command prompts to fetch C2 implants).
* Log Source Requirements: Sysmon process creation logs (Event ID 1) and PowerShell script block logs (Event ID 4104).
* Coverage Check:
  * HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 1 tracks installer processes spawning scripting shells or download tools. Sysmon Event ID 4104 (Script Block) captures scripting activity initiated by installers.
  * NIDS (Suricata + Zeek): PARTIAL. Network tools can spot unusual HTTP payloads during updates, but host audits are necessary to detect the post-install behavior chain.
* Log Sources Covered:
  - Sysmon Event ID 1 (process_creation)
  - Sysmon Event ID 4104 (ps_script)
* Log Sources Missing / Unused:
  - None.
* Conclusion: Supply chain compromise post-installation execution can be detected using process creation and PowerShell script block logs.

### 2. Custom Sigma Rule

The detection logic is split into monitoring processes spawned by software installers and monitoring script block activity associated with installers.

Rule 1 of 2: Supply Chain Compromise - Installer Executing Anomalous Shell (Process Creation)
```yaml
title: Supply Chain Compromise - Installer Executing Anomalous Shell (AN1480-A)
id: 681edcf6-4a0a-44f4-965f-1bcd3fc5a0d3
status: experimental
description: Detects software installers or newly installed application binaries spawning command interpreters, script execution engines, or background shell commands.
author: Krishna Gupta
date: 2026-06-08
logsource:
    category: process_creation
    product: windows
detection:
    selection_installer:
        ParentImage|contains:
            - '\Temp\'
            - '\AppData\Local\'
            - '\msiexec.exe'
            - '\setup.exe'
            - '\install.exe'
    selection_child:
        - Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\mshta.exe'
            - '\curl.exe'
            - '\certutil.exe'
        - OriginalFileName:
            - 'Cmd.Exe'
            - 'PowerShell.EXE'
            - 'wscript.exe'
            - 'cscript.exe'
            - 'mshta.exe'
            - 'curl.exe'
            - 'certutil.exe'
    condition: selection_installer and selection_child
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Legitimate software setup wrappers unpacking and running setup scripts.
level: medium
tags:
    - attack.initial-access
    - attack.t1195
    - analytic.an1480
    - detection.det0537
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Administrative Script Packaging
  * The Issue: Network administrators compile custom batch files or scripts into executable installers (using tools like Bat-To-Exe Converter) to deploy system software. These installers legitimately spawn shells.
  * The Fix: Scope the rule to whitelist administrative deployment tool paths (such as SCCM, Intune, or PDQ Deploy client directories) to avoid alerting on authorized enterprise deployments.

* Problem 2: DLL Sideloading in Installer Directory
  * The Issue: If the tampered installer does not spawn a new process, but performs a DLL sideloading attack during installation (loading a malicious DLL placed alongside the installer), child process monitoring will only see the installer process running, missing the malicious code.
  * The Fix: Enable library load audits (Sysmon Event ID 7) for installer processes to flag any unsigned DLLs loaded from dynamic or user writeable paths (like Temp).

* Problem 3: In-Memory Script Execution
  * The Issue: If the installer leverages built-in API interfaces to load and run scripts directly in-memory (e.g. hosting a PowerShell automation runspace inside the installer program), no `powershell.exe` process is spawned.
  * The Fix: Enable Script Block Logging (Event ID 4104) and scan for anomalous cmdlet execution blocks running under the user context of the setup process.
