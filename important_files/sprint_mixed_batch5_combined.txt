### 1. Technique Breakdown: T1221

* What it is: Template Injection. Adversaries may use template injection to execute malicious code via template relationships inside Microsoft Office documents. When a victim opens a document, the application fetches and loads a remote template containing malicious macros or exploit code, bypassing standard macro inspection.
* Log Source Requirements:
  * Sysmon Process Creation (Event ID 1) capturing Microsoft Office applications spawning child command shells or interpreters to execute injected code.
* Coverage Check:
  * HIDS (Sysmon): YES. Office processes launching interpreters generates telemetry.
  * NIDS (Zeek/Suricata): NO. Endpoint process telemetry is required to identify the parent-child relationships.
* Log Sources Covered:
  * Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
  * Network flow logs (does not capture process relationship detail).

---

### 2. Custom Sigma Rule

The following rule monitors the process creation log for child command interpreters or script hosts spawned by Microsoft Office binaries (such as Word, Excel, PowerPoint), which is highly characteristic of template injection exploitation.

```yaml
title: Microsoft Office Application Spawning Script Interpreter (AN2119)
id: f1a2b3c4-e5f6-7a8b-9c0d-1e2f3a4b5c80
status: experimental
description: "Detects command-line script interpreters or shell utilities (cmd.exe, powershell.exe, mshta.exe, wscript.exe, cscript.exe) running as child processes of Microsoft Office applications (Word, Excel, PowerPoint), which is a common indicator of remote template injection or macro-based execution."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: process_creation
    product: windows
detection:
    selection_parent:
        ParentImage|endswith:
            - '\winword.exe'
            - '\excel.exe'
            - '\powerpnt.exe'
            - '\outlook.exe'
    selection_child_images:
        Image|endswith:
            - '\cmd.exe'
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\mshta.exe'
            - '\rundll32.exe'
            - '\regsvr32.exe'
    selection_child_ofn:
        OriginalFileName:
            - 'Cmd.Exe'
            - 'PowerShell.EXE'
            - 'pwsh.exe'
            - 'wscript.exe'
            - 'cscript.exe'
            - 'mshta.exe'
            - 'rundll32.exe'
            - 'regsvr32.exe'
    filter_legitimate_child:
        Image|endswith: '\rundll32.exe'
        CommandLine|contains: 'shell32.dll'
    condition: selection_parent and (selection_child_images or selection_child_ofn) and not filter_legitimate_child
fields:
    - ParentImage
    - Image
    - CommandLine
    - User
falsepositives:
    - Legitimate enterprise add-ins or custom office extensions that launch scripting interpreters to generate reports or integrate with database backends.

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: In-process exploitation (DDE/Exploits)
  * The Issue: If the attacker exploits a vulnerability in Word (like CVE-2017-11882 Equation Editor) to execute code directly inside the office process memory or via `eqnedt32.exe` without spawning standard command shells, this child process check will miss the behavior.
  * The Fix: Add `eqnedt32.exe` to the parent selection or monitor process access handle requests from office binaries to other processes.
* Problem 2: Legitimate VBA macro automation
  * The Issue: Some legacy corporate spreadsheets contain legitimate VBA macros that call shell commands to archive files or move data, generating frequent alerts.
  * The Fix: Baseline the specific scripts, limit exclusions to the exact hashes of the spreadsheets, or restrict execution to trusted service accounts.
* Problem 3: DLL loading via office folders
  * The Issue: The template can perform sideloading of an anomalous DLL into the Office application space directly, avoiding process creation altogether.
  * The Fix: Monitor Image Loads (Event ID 7) inside office processes for files loaded from Temp or non-standard paths.

  * The Issue: A single utility execution is a weak signal. An attacker usually runs several discovery tools in sequence (e.g. whoami then systeminfo then ipconfig).

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Exploitation via signed kernel drivers
  * The Issue: If the attacker loads a signed vulnerable vendor driver (BYOVD) to write directly to physical memory and reprogram the SPI flash chip, no user-mode bios flash utility will be executed.
  * The Fix: Monitor Sysmon Event ID 6 (Driver Load) for vulnerable firmware update drivers (e.g. ASUS/Gigabyte bios drivers) and trace anomalous system calls.
* Problem 2: Vendor-specific update agents
  * The Issue: Dell, HP, Lenovo, and ASUS update clients run firmware checkers periodically, which matches keywords like `bios` or `firmware` and triggers alerts.
  * The Fix: Whitelist the specific executable hashes and parent processes (like vendor update services) in your environment.
* Problem 3: Local script commands
  * The Issue: Scripting queries using WMI classes (e.g., `Get-WmiObject -Class Win32_BIOS`) will trigger alerts due to broad keyword matching.
  * The Fix: Exclude read-only query parameters like `get` or `list` from matching command-line scopes.

### 1. Technique Breakdown: T1620

* What it is: Reflective Code Loading. Adversaries may reflectively load code in-memory to execute malicious binaries, scripts, or DLLs without writing them to disk. It is commonly achieved by using PowerShell to invoke assembly reflective load methods (e.g. `[System.Reflection.Assembly]::Load`) or memory copy APIs.

* Coverage Check:

  * NIDS (Zeek/Suricata): NO. PowerShell execution is entirely local to the endpoint.
* Log Sources Covered:
  * PowerShell Operational Event ID 4104 (Script Block Logging)
* Log Sources Missing / Unused:
  * Sysmon Event ID 1 (cannot trace reflective APIs invoked within scripts).

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Obfuscation of Script Block Text
  * The Issue: If the script performs advanced string encryption or character array reconstruction before compiling the assembly load string, standard contains filters might fail to capture the base classes.
  * The Fix: Enable PowerShell Antimalware Scan Interface (AMSI) auditing to inspect script blocks after they have been decrypted and reassembled in memory at the engine tier.
* Problem 2: Legitimate software assembly loads
  * The Issue: Certain application frameworks (like SharePoint administration modules or custom corporate toolkits) legitimately call `Assembly.Load` to bootstrap components.
  * The Fix: Create exclusions in the SIEM for specific trusted script paths or signing certificate authorities.
* Problem 3: Non-PowerShell reflective loading
  * The Issue: If the reflective loading is performed in a custom C/C++ loader or Go executable using direct Win32 memory APIs, no PowerShell Script Block logs are generated.
  * The Fix: Combine this with a rule monitoring Sysmon Event ID 8 (CreateRemoteThread) or Event ID 10 (ProcessAccess) to track thread injection.

  * Sysmon Process Creation (Event ID 1) capturing command line delay flags and loop intervals.
* Coverage Check:
  * HIDS (Sysmon): YES. Spawning delays via CLI commands generates process creation logs.
  * NIDS (Zeek/Suricata): NO. local timer delays do not trigger network metadata.
* Log Sources Covered:
  * Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
  * None.

### 2. Custom Sigma Rule

The following rule monitors the process creation log for command configurations that execute artificial delays using native Windows tools (such as `ping`, `timeout`, `choice`, or `powershell -sleep`).

```yaml
title: Artificial Execution Delay or Anti-Sandbox Sleep (AN2126)
id: f1a2b3c4-e5f6-7a8b-9c0d-1e2f3a4b5c87
status: experimental
description: "Detects command-line execution parameters that execute artificial delays or sleeping patterns (such as pinging 127.0.0.1 a large number of times, using timeout, choice with short defaults, or PowerShell Start-Sleep) commonly used to evade sandbox analysis."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: process_creation
    product: windows
detection:
    selection_ping:
        Image|endswith:
            - '\ping.exe'
        CommandLine|re: '(?i)ping.*(127\.0\.0\.1|localhost).*-n\s+(\d{3,})'
    selection_ping_ofn:
        OriginalFileName: 'ping.exe'
        CommandLine|re: '(?i)ping.*(127\.0\.0\.1|localhost).*-n\s+(\d{3,})'
    selection_ps_sleep:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
        CommandLine|re: '(?i)Start-Sleep\s+-s(econds)?\s+(\d{3,})'
    selection_ps_sleep_ofn:
        OriginalFileName:
            - 'PowerShell.EXE'
            - 'pwsh.exe'
        CommandLine|re: '(?i)Start-Sleep\s+-s(econds)?\s+(\d{3,})'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: (selection_ping or selection_ping_ofn or selection_ps_sleep or selection_ps_sleep_ofn) and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - User
falsepositives:
    - Administrative scripts that use timeout or choice to wait for a service to start, or ping loops to verify connection status before proceeding.
level: medium
tags:
    - attack.defense_evasion
    - attack.t1678
    - analytic.an2126
    - detection.det0983
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: API sleeping inside custom code
  * The Issue: If the attacker calls the kernel API `Sleep()` or `NtDelayExecution()` inside a compiled binary, no command line tools like `ping.exe` or `timeout.exe` are spawned.
  * The Fix: Rely on security sandbox runtime API hook analysis or debug logging.
* Problem 2: Batch script cleanup delays
  * The Issue: Legitimate software uninstallers often use `ping 127.0.0.1 -n 5` to wait for the main process to exit before deleting files, generating noise.
  * The Fix: Tune the count parameter (e.g., look for larger delay intervals like `-n 30` or higher, or filter known software directories).
* Problem 3: PowerShell command obfuscation
  * The Issue: If the `Start-Sleep` string is obfuscated (e.g. `s`+`leep`), the process creation parser will fail to match the literal.
  * The Fix: Enable PowerShell Script Block Logging (Event ID 4104) to review scripts in deobfuscated format.

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Registry updates using SYSTEM account
  * The Issue: In our implementation, we do not restrict the user, which is correct; however, standard installers might use SYSTEM to write exclusions.
  * The Fix: Scrutinize exclusions added by SYSTEM using ParentImage checks to ensure they are verified software deployment systems (like SCCM).
* Problem 2: Obfuscated PowerShell parameters
  * The Issue: If `Add-MpPreference` is run via encoded Base64 command lines (`powershell -e ...`), this process CLI rule will fail to match the contains filter.
  * The Fix: Rely on a companion rule looking for PowerShell Encoded Commands (AN2106) or inspect script block logs (Event ID 4104).
* Problem 3: Exclusion of administrative folders
  * The Issue: legitimate administrative applications might legitimately add exclusions, creating alerts.
  * The Fix: Baseline standard folder paths (e.g. SQL directories or IIS folders) and whitelist them if they are configured by verified scripts.

### 3. Blind Spots & Tuning (The "Problems")

  * The Issue: In MSHTA execution, the HTML file can construct the credential popup dynamically, preventing detection of strings in the process creation logs.
