### 1. Technique Breakdown: T1001

* What it is: Data Obfuscation. Adversaries may obfuscate command and control traffic or payloads to bypass network security checks or file scanners. This includes using steganography to hide data inside media files (like images or audio) before transmission, or applying custom mathematical wrappers to payload streams.
* Log Source Requirements:
  * Sysmon Process Creation (Event ID 1) logging commands associated with known steganography tool usage or wrapping programs.
* Coverage Check:
  * HIDS (Sysmon): YES. Processes spawned to perform steg operations leave process telemetry.
  * NIDS (Zeek/Suricata): NO. Payloads inside network traffic are obfuscated and require inspection at the endpoint.
* Log Sources Covered:
  * Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
  * Network flow logs (cannot decode the payload streams).

---

### 2. Custom Sigma Rule

The following rule monitors for the execution of common command-line steganography utilities used by adversaries to hide or extract embedded payloads in media files.

```yaml

description: "Detects the execution of known command-line steganography tools (e.g., steghide, openstego, outguess) commonly used by threat actors to embed or extract hidden payloads inside images or audio files to bypass network monitoring."
author: Krishna Gupta
date: 2026-07-01

    selection_steg_images:

            - '\steghide.exe'

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Custom Steganography scripts
  * The Issue: Python or PowerShell scripts that perform pixel manipulation or LSB encoding will not execute under these binary names and will bypass this rule.
  * The Fix: Implement script block logging filters to search for libraries like Python's `PIL` or `stegano` being imported by unknown scripts.
* Problem 2: Compiled custom wrappers
  * The Issue: If the attacker writes a custom compiled C/Go tool to perform XOR/AES wrapping, the tool will have a unique name and hash, bypassing known steg utility signatures.
  * The Fix: Rely on behavioural heuristics of the child processes or file writing anomaly detection (e.g., a non-standard process writing large volumes of encoded data).
* Problem 3: Multi-purpose archive tools
  * The Issue: Archivers like WinRAR or 7-Zip can embed data into self-extracting comments or append data to file ends, which is not flagged by these specific steg binaries.
  * The Fix: Monitor for execution of zip utilities with anomalous parameters or non-standard file appends.

### 1. Technique Breakdown: T1006

* What it is: Direct Volume Access. This is typically done to extract protected system files (like the SAM registry hive or NTDS.dit database) or to overwrite disk sectors.

* Coverage Check:

* Log Sources Covered:

* Log Sources Missing / Unused:
  * Standard Windows file system audit logs (since direct volume access bypasses standard NTFS file access audits).

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Custom C/C++ compiled binaries
  * The Issue: If the attacker runs a custom compiled utility that opens a handle to `CreateFileW` with the `\\.\PhysicalDrive0` path, the string will not appear in the process creation command line.
  * The Fix: Enable Sysmon Event ID 10 (Process Access) or Event ID 25 (Process Tampering) / Event ID 11 (File Event) monitoring for direct device object handle requests, or look for anomalous device driver openings.
* Problem 2: Disk volume drive letter variations
  * The Issue: Drive letters beyond A-F (e.g. `\\.\X:`) will not be matched by the specific drive lists in selection_cli.
  * The Fix: Replace containing strings with a generic regex check to match any single character drive letter path: `\\\\.\\\\[a-zA-Z]:`
* Problem 3: Volume Shadow Copy service noise
  * The Issue: Backup agents run `vshadow.exe` periodically, which triggers alerts.
  * The Fix: Whitelist known backup service account names or specific parent processes of enterprise backup agents.

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Inline C# or Python script C2 fallback
  * The Issue: If the fallback channel is built directly into memory (e.g., via a PowerShell script block executing `System.Net.WebClient` or a custom python agent), no external binary like `tor.exe` or `chisel.exe` is spawned.
  * The Fix: Implement script block logging filters to inspect remote connection logic, and monitor network logs for anomalous HTTPS beacons to secondary hostnames.
* Problem 2: Port forwarding via standard SSH/RDP
  * The Issue: Attackers using standard admin tools for tunnels might match basic proxy parameters (like `-L` or `-R`).
  * The Fix: Scrutinize the parent-child process tree. For example, `plink.exe` spawned from a user temp folder or CMD is highly anomalous compared to standard administrative shell hosts.
* Problem 3: Public VPN client usage
  * The Issue: Legitimate VPN clients use parameters like `tunnel` or `socks` and trigger false alarms.
  * The Fix: Whitelist standard enterprise VPN executables by hash or signer certificate.

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Native service command loads (sc.exe)
  * The Issue: If the attacker loads a kernel driver using the native Windows command `sc.exe create [name] binPath= [path] type= kernel`, this rule will not trigger.
  * The Fix: Ensure you deploy a companion rule that explicitly flags `sc.exe` executions where `type= kernel` or `type= filesys` is present in the command line (e.g., AN0778 service creation rule).
* Problem 2: Custom compiled BYOVD tools
  * The Issue: Attackers using custom compiled utilities that interact directly with the LSA/Kernel via IOCTL calls to load drivers without DSEfix or KDU will bypass this signature.
  * The Fix: Monitor Sysmon Event ID 6 (Driver Load) and verify loaded drivers against a whitelist of known legitimate hashes.
* Problem 3: Process Hacker false positives
  * The Issue: Process Hacker is used legitimately by developers and administrators, leading to frequent medium/high alerts.
  * The Fix: Scope alerts for Process Hacker to non-admin directories or unexpected execution paths (e.g. C:\Users\Public\).

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Local Policy files injection (scripts.ini)
  * The Issue: If the attacker drops the script directly into the local Group Policy templates folder (e.g. `C:\Windows\System32\GroupPolicy\User\Scripts\scripts.ini`) without modifying the `UserInitMprLoopbackScript` registry key, this rule will not trigger.
  * The Fix: Implement a companion rule targeting Sysmon Event ID 11 (File Creation) for any `.ini` files written to the `GroupPolicy` subfolders by non-standard processes.
* Problem 2: Active Directory logon script path
  * The Issue: If the script is configured directly in the Active Directory user object properties (the `scriptPath` attribute in AD) rather than the local machine registry, this rule will not trigger.
  * The Fix: Enable auditing for Directory Service Changes (Event ID 5136) on Domain Controllers and monitor changes to the `scriptPath` attribute of user objects.
* Problem 3: Normal administrative loopback script configurations
  * The Issue: In corporate environments using folder redirection or mapped drives, admins might legitimately configure loopback scripts, causing false positives.
  * The Fix: Create exclusions in the SIEM for trusted central domain paths (e.g. `\\domain.local\SysVol\`).

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Fixed secondary hard drives (D:\)
  * The Issue: Many enterprise computers have fixed secondary data drives (D:\ or E:\) where users store data and run tools legitimately, generating high false positives.
  * The Fix: Exclude specific known folders on secondary drives (e.g. `D:\Data\`) or map drive types using registry logs to determine if the drive is a removable USB disk vs. a fixed SSD.
* Problem 2: LNK shortcuts or autorun triggers
  * The Issue: If the attacker drops an LNK file that triggers an execution path, the command line structure might vary from standard parameters.
  * The Fix: Combine this rule with Sysmon Event ID 11 (File Event) rules to monitor the dropping of `.lnk` or `.inf` (autorun) files onto removable drives.

  * The Issue: If a script block is loaded directly into memory from a script on a USB drive without the drive letter appearing in the process creation command line (e.g. using `Get-Content`), this rule will not trigger.
  * The Fix: Enable PowerShell Script Block Logging (Event ID 4104) and look for script text containing file read operations on drive letters `[D-Z]:\`.

### 3. Blind Spots & Tuning (The "Problems")

  * The Fix: Use Group SIDs (such as `S-1-5-32-544` for local Administrators or `S-1-5-21-*-512` for Domain Admins) instead of text strings when querying group addition events.
* Problem 2: Mass administration automation noise
  * The Issue: Service accounts running provisioning scripts (like IAM tools or azure sync agents) add hundreds of users legitimately, causing alerts.
  * The Fix: Whitelist the specific IAM service account usernames in `filter_machine_accounts` or create a separate baseline rule for automated accounts.
* Problem 3: Delegated rights directly to active directory objects
  * The Issue: If permission delegation is configured directly on an AD organizational unit (OU) rather than altering group memberships, Event ID 4728/4732 will not trigger.
  * The Fix: Enable auditing for Directory Service changes (Event ID 5136) and monitor write permissions onto OU ACLs.

ANALYTIC: AN2115  TECHNIQUE: T1111  DET: DET0972  TACTIC: Credential Access
TITLE   : Custom Security Support Provider or LSA Package Registration
FOLDER  : credential-access
================================================================================

### 1. Technique Breakdown: T1111

* What it is: Multi-Factor Authentication Interception. Adversaries may intercept multi-factor authentication credentials, codes, or tokens to bypass security controls. A common method to capture both credentials and MFA codes is by registering custom LSA (Local Security Authority) plugins or Security Support Providers (SSPs). These providers reside in the LSA address space and intercept plaintext credentials during logon.
* Log Source Requirements:
  * Sysmon Registry Value Set (Event ID 13) capturing modifications to the LSA Security Packages or SSP registry values.
* Coverage Check:
  * HIDS (Sysmon): YES. Modifying LSA package settings in the registry generates Event ID 13.
  * NIDS (Zeek/Suricata): NO. LSA configuration is entirely local to the Windows host.
* Log Sources Covered:
  * Sysmon Event ID 13 (registry_event)
* Log Sources Missing / Unused:
  * None.

---

### 2. Custom Sigma Rule

The following rule monitors the registry for updates to LSA security packages, authentication providers, or security providers, which are abused by attackers to install custom credential-intercepting SSP DLLs.

```yaml
title: Custom Security Support Provider or LSA Package Registration (AN2115)
id: f1a2b3c4-e5f6-7a8b-9c0d-1e2f3a4b5d98
status: experimental
description: "Detects modifications to registry values under HKLM\\SYSTEM\\CurrentControlSet\\Control\\Lsa (Security Packages, Authentication Packages) or SecurityProviders, which can be abused by adversaries to register custom Security Support Providers (SSPs) to intercept plaintext passwords and MFA credentials."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: registry_set
    product: windows
detection:
    selection_registry_paths:
        TargetObject|contains:
            - '\System\CurrentControlSet\Control\Lsa\Security Packages'
            - '\System\CurrentControlSet\Control\Lsa\Authentication Packages'
            - '\System\CurrentControlSet\Control\SecurityProviders\SecurityProviders'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: selection_registry_paths and not filter_installer
fields:
    - TargetObject
    - Details
    - Image
    - User
falsepositives:
    - Standard enterprise software (like backup tools or custom endpoint security agents) registering their own security support packages during system installation.
level: high
tags:
    - attack.credential-access
    - attack.t1111
    - analytic.an2115
    - detection.det0972
```

---

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Sysmon bypass via direct driver access
  * The Issue: If the rootkit directly alters kernel memory pointers to reference the custom authentication package without touching the registry, Sysmon Event ID 13 will not fire.
  * The Fix: Rely on Sysmon Event ID 7 (Image Load) to detect anomalous DLLs loaded by `lsass.exe` (specifically DLLs loaded outside of `C:\Windows\System32\`).
* Problem 2: Legitimate software registration false positives
  * The Issue: Certain corporate VPNs or third-party authentication utilities (like Duo or Okta LSA integrations) register custom providers, causing alerts.
  * The Fix: Whitelist the specific names or details of the trusted provider DLLs registered by these tools.
* Problem 3: File dropping blind spot
  * The Issue: The registry key only references the DLL name. If the DLL is dropped in a non-standard location or overwrites an existing DLL, it bypasses the registry check.
  * The Fix: Combine this with a rule monitoring file drops (`EID 11`) in the `C:\Windows\System32\` folder for unsigned or newly dropped DLLs.

ANALYTIC: AN2116  TECHNIQUE: T1132  DET: DET0973  TACTIC: Command and Control
TITLE   : Process Command Line Data Encoding or Decoding Activity
FOLDER  : command-and-control
================================================================================

### 1. Technique Breakdown: T1132

* What it is: Data Encoding. Adversaries may encode data (e.g., using Base64, Hexadecimal, or custom schemes) to obscure payload delivery or command and control traffic. This helps evade basic content filters or signature-based intrusion detection systems. Detecting the CLI execution of command parameters that invoke encoding functions (such as PowerShell base64/hex conversions) helps flag these obfuscation attempts.
* Log Source Requirements:
  * Sysmon Process Creation (Event ID 1) capturing process command-lines containing explicit data encoding/decoding keywords.
* Coverage Check:
  * HIDS (Sysmon): YES. Processes run with encoding/decoding arguments leave command-line logs.
  * NIDS (Zeek/Suricata): PARTIAL. Network logs can capture encoded payloads, but endpoint rules correlate the action to specific local processes.
* Log Sources Covered:
  * Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
  * None.

---

### 2. Custom Sigma Rule

The following rule monitors the command line parameters of shell hosts and scripting utilities for operations executing explicit base64, hexadecimal, or custom conversions.

```yaml
title: Process Command Line Data Encoding or Decoding Activity (AN2116)
id: d4e5f6a7-b8c9-4d0e-9f0a-1b2c3d4e5f95
status: experimental
description: "Detects process command-line parameters indicating the execution of data encoding or decoding operations (e.g., PowerShell conversion classes, certutil hex transformations, or base64 decoding utilities) commonly used to mask payload execution or exfiltration streams."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: process_creation
    product: windows
detection:
    selection_images:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\cmd.exe'
            - '\certutil.exe'
            - '\wscript.exe'
            - '\cscript.exe'
    selection_ofn:
        OriginalFileName:
            - 'PowerShell.EXE'
            - 'pwsh.exe'
            - 'Cmd.Exe'
            - 'certutil.exe'
            - 'wscript.exe'
            - 'cscript.exe'
    selection_cli:
        CommandLine|contains:
            - 'FromBase64String'
            - 'ToBase64String'
            - '[System.Convert]'
            - '-encodehex'
            - '-decodehex'
            - 'base64 -d'
            - 'base64 --decode'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: (selection_images or selection_ofn) and selection_cli and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - User
falsepositives:
    - Legitimate administrative scripts or software installation tools that decode configuration values or license keys from base64 or hex during setup.
level: medium
tags:
    - attack.command-and-control
    - attack.t1132
    - analytic.an2116
    - detection.det0973
```

---

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Obfuscation inside script blocks
  * The Issue: If the script is obfuscated and constructs the base64 conversion strings dynamically at runtime (e.g., using string concatenation or character arrays), the literal keywords like `FromBase64String` will not appear in the initial process creation command line.
  * The Fix: Enable PowerShell Script Block Logging (Event ID 4104) and look for script block telemetry after runtime deobfuscation has occurred.
* Problem 2: Standard application setup false positives
  * The Issue: Certain installers (like Microsoft SQL server or exchange agents) run setup cmdlets that legitimately use base64 conversions, causing noise.
  * The Fix: Whitelist known administrative parent processes or specific installer directories (e.g. `C:\Windows\Temp\`).
* Problem 3: Custom XOR encoding
  * The Issue: If the attacker uses simple custom XOR loops or bit-shifting instead of standard Base64/Hex classes, the keywords in `selection_cli` will not trigger.
  * The Fix: Monitor for anomalous network payloads or process memory access behaviors.

ANALYTIC: AN2117  TECHNIQUE: T1211  DET: DET0974  TACTIC: Stealth
TITLE   : Anomalous Handle Access to System Process for Exploitation or Stealth
FOLDER  : stealth
================================================================================

### 1. Technique Breakdown: T1211

* What it is: Exploitation for Stealth. Adversaries may exploit software vulnerabilities to bypass security tools, disable auditing, or hide their presence on target systems. A common technique involves process hollowing or process injection into trusted OS processes. This is detected by monitoring anomalous memory access requests (specifically write and mapping access rights) targeting critical system processes.
* Log Source Requirements:
  * Sysmon Process Access (Event ID 10) capturing handle requests to system processes with high-privilege access rights.
* Coverage Check:
  * HIDS (Sysmon): YES. Handle openings to critical processes with write or operation rights generate Event ID 10.
  * NIDS (Zeek/Suricata): NO. Process memory access is local to the operating system kernel.
* Log Sources Covered:
  * Sysmon Event ID 10 (process_access)
* Log Sources Missing / Unused:
  * None.

---

### 2. Custom Sigma Rule

The following rule monitors Sysmon process access logs (Event ID 10) for handle requests to core system binaries (e.g., lsass, svchost, explorer) requesting high-risk write or virtual memory operation privileges from non-standard source images.

```yaml
title: Anomalous Handle Access to System Process for Exploitation or Stealth (AN2117)
id: c3d4e5f6-7a8b-9c0d-1e2f-3a4b5c6d7e95
status: experimental
description: "Detects anomalous handle access requests (Sysmon Event ID 10) targeting critical system processes (like lsass.exe, svchost.exe, or explorer.exe) with high-risk access permissions (such as PROCESS_ALL_ACCESS or VM Write/Operation rights), indicating potential process injection or hollowing for stealth."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: process_access
    product: windows
detection:
    selection_target:
        TargetImage|endswith:
            - '\lsass.exe'
            - '\svchost.exe'
            - '\explorer.exe'
            - '\winlogon.exe'
            - '\csrss.exe'
    selection_access:
        # VM_WRITE (0x0020), VM_OPERATION (0x0008), or PROCESS_ALL_ACCESS (0x1F0FFF)
        GrantedAccess:
            - '0x1F0FFF'
            - '0x1f0fff'
            - '0x1010'
            - '0x1410'
            - '0x1438'
            - '0x143a'
    filter_legitimate_source:
        SourceImage|endswith:
            - '\taskmgr.exe'
            - '\resmon.exe'
            - '\processhacker.exe'
            - '\msiexec.exe'
    condition: selection_target and selection_access and not filter_legitimate_source
fields:
    - SourceImage
    - TargetImage
    - GrantedAccess
    - SourceUser
falsepositives:
    - Legitimate debugging tools, system monitors, or security agents accessing system processes to collect diagnostic telemetry.
level: high
tags:
    - attack.defense_evasion
    - attack.t1211
    - analytic.an2117
    - detection.det0974
```

---

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Administrative tools false positives
  * The Issue: Custom administration tools or internal system checkers may open handles with full access rights, leading to persistent alerts.
  * The Fix: Create exclusions in the SIEM for trusted administration source images based on code signing certificate or hash check values.
* Problem 2: DLL injection via load library
  * The Issue: If the attacker performs DLL injection by dropping a library file that is naturally loaded by a process rather than accessing process memory remotely, Event ID 10 will not trigger.
  * The Fix: Enable Sysmon Event ID 7 (Image Load) and monitor for unsigned or newly dropped DLLs loaded by system processes.
* Problem 3: Low-privilege handle access
  * The Issue: If the attacker exploits a process using low-privilege access rights first, and escalates privileges inside the process memory directly, this rule will bypass the initial check.
  * The Fix: Deploy companion rules looking for child process creation (EID 1) from these target system processes.

### 2. Custom Sigma Rule

The following rule monitors the process creation log to detect command shells, interpreters, or administrative binaries spawned as child processes of the Windows Print Spooler service (`spoolsv.exe`), indicating active credential service exploitation.

```yaml
title: Print Spooler Service Spawning Suspicious Child Process (AN2118)
id: f1a2b3c4-e5f6-7a8b-9c0d-1e2f3a4b5d99
status: experimental
description: "Detects command shells, interpreters, or system administrative utilities spawned as child processes of spoolsv.exe (Windows Print Spooler), which is a common indicator of successful exploitation of Print Spooler vulnerabilities (such as PrintNightmare CVE-2021-34527) to perform local execution or credential harvesting."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: process_creation
    product: windows
detection:
    selection_parent:
        ParentImage|endswith:
            - '\spoolsv.exe'
    selection_parent_ofn:
        ParentOriginalFileName: 'spoolsv.exe'

            - '\cmd.exe'
            - '\powershell.exe'

            - '\wscript.exe'
            - '\cscript.exe'
            - '\rundll32.exe'
            - '\regsvr32.exe'
            - '\whoami.exe'
            - '\nltest.exe'

        OriginalFileName:
            - 'Cmd.Exe'
            - 'PowerShell.EXE'

            - 'rundll32.exe'
            - 'regsvr32.exe'
            - 'whoami.exe'
            - 'nltest.exe'

* Problem 3: Execution under renamed spoolsv.exe
  * The Issue: The rule targets child processes of `spoolsv.exe` using ParentImage and ParentOriginalFileName, which is robust against renaming spoolsv itself; however, if the spooler service is run via generic `svchost.exe` hosting, the parent is svchost.
  * The Fix: Monitor svchost spawning command shells under unusual service group environments.
