### 1. Technique Breakdown: T1674

* What it is: Input Injection. Adversaries may inject inputs into systems to bypass security controls or automate interactions (such as clicking warning popups, executing payloads via UI fields, or simulating keystrokes). This can be done by running keystroke automation engines (like AutoIt, AutoHotkey) or using scripting classes (like WScript.Shell SendKeys) to send keystrokes to target windows.
* Log Source Requirements:
  * Sysmon Process Creation (Event ID 1) capturing command line keywords related to input injection/automation execution.
* Coverage Check:
  * HIDS (Sysmon): YES. Spawning automation scripting engines generates process log traces.
  * NIDS (Zeek/Suricata): NO. Keystroke simulation is entirely local to the host desktop session.
* Log Sources Covered:
  * Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
  * None.

### 2. Custom Sigma Rule

The following rule monitors the process creation log for execution of scripting hosts or automation tools running input simulation parameters (such as `SendKeys` or AutoIt interpreter configurations).

```yaml
title: Input Keystroke Automation or Injection Tool Execution (AN2125)
id: f1a2b3c4-e5f6-7a8b-9c0d-1e2f3a4b5c86
status: experimental
description: "Detects the execution of input injection/automation engines (such as AutoIt3, AutoHotkey) or command line calls executing SendKeys routines to automate keystrokes or UI interactions to bypass warning boxes."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: process_creation
    product: windows
detection:
    selection_autoit_images:
        Image|endswith:
            - '\autoit3.exe'
            - '\autohotkey.exe'
    selection_autoit_ofn:
        OriginalFileName:
            - 'AutoIt3.exe'
            - 'AutoHotkey.exe'
    selection_ps:
        Image|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
    selection_ps_ofn:
        OriginalFileName:
            - 'PowerShell.EXE'
            - 'pwsh.exe'
    selection_ps_cli:
        CommandLine|contains:
            - 'SendKeys'
            - 'SendInput'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: (selection_autoit_images or selection_autoit_ofn or ((selection_ps or selection_ps_ofn) and selection_ps_cli)) and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - User
falsepositives:
    - Legitimate administrative script macros that automate software installation inputs or test execution scripts.
level: medium
tags:
    - attack.defense_evasion
    - attack.t1674
    - analytic.an2125
    - detection.det0982
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: API injection via SetWindowsHookEx
  * The Issue: If the attacker compiles a custom C binary that registers a global hook using `SetWindowsHookExW` or calls `SendInput` natively via Win32 APIs, no script interpreter keywords like `SendKeys` will appear in the command line.
  * The Fix: Monitor process calls targeting user interface elements or load events of hooks libraries.
* Problem 2: Desktop automation frameworks
  * The Issue: RPA (Robotic Process Automation) software like UIPath or BluePrism regularly automates inputs, generating false positives.
  * The Fix: Exclude known, signed RPA execution service folders from the detection scope.
* Problem 3: Multi-purpose script engines
  * The Issue: A general PowerShell script might use SendKeys and trigger alerts, requiring analysis of the parent process context.
  * The Fix: Investigate the parent process of any PowerShell binary invoking SendKeys to verify user interaction.
