### 1. Technique Breakdown: T1480

* What it is: Execution Guardrails. Adversaries may build execution guardrails into their payloads to ensure that they only execute when specific target conditions (e.g., domain membership, hostname, environment variables, or registry paths) are met. This is monitored by detecting commands attempting to resolve domain and target environment details before payload loops.
* Log Source Requirements:
  * Sysmon Process Creation (Event ID 1) to audit environmental queries (domain, system configuration, username) run in quick succession.
* Coverage Check:
  * HIDS (Sysmon): YES. Host query utilities leave process creation events.
  * NIDS (Zeek/Suricata): NO. System discovery commands execute locally on the host.
* Log Sources Covered:
  * Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
  * None.

### 2. Custom Sigma Rule

The following rule monitors the process creation log for execution of environment queries (systeminfo, net.exe, whoami) that check target system parameters, representing potential execution guardrails.

```yaml
title: Execution Guardrails Target Discovery Query (AN2120)
id: f1a2b3c4-e5f6-7a8b-9c0d-1e2f3a4b5c81
status: experimental
description: "Detects the execution of discovery tools (such as systeminfo, whoami, gpresult, or net.exe querying domain membership) used by payloads to evaluate target environment conditions before executing subsequent payload execution phases."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: process_creation
    product: windows
detection:
    selection_images:
        Image|endswith:
            - '\systeminfo.exe'
            - '\whoami.exe'
            - '\gpresult.exe'
            - '\quser.exe'
    selection_ofn:
        OriginalFileName:
            - 'systeminfo.exe'
            - 'whoami.exe'
            - 'gpresult.exe'
            - 'quser.exe'
    selection_cli:
        CommandLine|contains:
            - ' /domain'
            - ' /fqdn'
            - 'user /domain'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: (selection_images or selection_ofn) and selection_cli and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - User
falsepositives:
    - Administrative scripts collecting system inventory details or checking Active Directory configurations.
level: medium
tags:
    - attack.defense_evasion
    - attack.t1480
    - analytic.an2120
    - detection.det0977
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Query API calls inside compiled code
  * The Issue: If the attacker calls Win32 APIs directly (e.g. `GetComputerNameExW` or `NetGetJoinInformation`) inside their compiled C/C++ malware binary, no subprocesses like `whoami.exe` or `systeminfo.exe` are spawned.
  * The Fix: Rely on behavioural indicators or API monitoring to trace DLL functions called by unknown processes.
* Problem 2: Administrative inventory scripts
  * The Issue: Domain admins run inventory collection tools that query domain names and local configurations regularly, producing noise.
  * The Fix: Baseline administrative service account names and exclude processes executed under those specific users.
* Problem 3: Multi-command sequence identification
  * The Issue: A single utility execution is a weak signal. An attacker usually runs several discovery tools in sequence (e.g. whoami then systeminfo then ipconfig).
  * The Fix: Set up a correlation rule that triggers when 3 or more distinct discovery commands are executed by the same parent process within 60 seconds (AN2120 correlation).
