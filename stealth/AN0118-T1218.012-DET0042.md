### 1. Technique Breakdown: T1218.012

* What it is: Verclsid. Adversaries abuse `verclsid.exe`, a signed Windows binary (part of the Windows Shell), to execute arbitrary COM objects by supplying a CLSID argument. Since `verclsid.exe` is a trusted, Microsoft-signed binary, security products often allow it to instantiate COM objects. Attackers register a malicious COM object (or point to a remote SCT/HTA scriptlet via an existing CLSID) and invoke it through `verclsid.exe /S /C {CLSID}`. If the CLSID resolves to remote content, `verclsid.exe` makes outbound network connections, loading and executing the remote scriptlet.
* Log Source Requirements: Sysmon process creation logs (Event ID 1), Sysmon network connection logs (Event ID 3), and Sysmon registry modification logs (Event ID 12/13) capturing custom CLSID creation.
* Coverage Check:
    * HIDS (Sysmon + Wazuh): YES. Sysmon Event ID 1 captures `verclsid.exe` process creation with CLSID arguments. Event ID 3 captures outbound network connections initiated by `verclsid.exe`. Event ID 12/13 detects custom CLSIDs written to user classes.
    * NIDS (Suricata + Zeek): PARTIAL. Outbound network traffic from verclsid.exe can be captured, but local host context is needed for correlation.
* Log Sources Covered:
    - Sysmon Event ID 1 (process_creation)
    - Sysmon Event ID 3 (network_connection)
    - Sysmon Event ID 12/13 (registry_set)
* Log Sources Missing / Unused:
    - None.

### 2. Custom Sigma Rule

The detection logic is split into three rules targeting process creation execution, outbound network sockets, and registry hive CLSID writes separately.

Rule 1 of 3: Verclsid LOLBin Execution (Process Creation)
```yaml
title: Verclsid LOLBin Abuse for COM Object Execution (AN0118-A)
id: 8b41ebed-bac9-4c77-8092-4b8fa9d1c14d
status: experimental
description: Detects abuse of verclsid.exe (a signed Windows Shell binary) to execute arbitrary COM objects via CLSID arguments, which may load malicious scriptlets or DLLs.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: process_creation
    product: windows
    # Relies on Sysmon Event ID 1
detection:
    selection:
        - Image|endswith: '\verclsid.exe'
        - OriginalFileName: 'verclsid.exe'
    selection_args:
        CommandLine|contains:
            - ' /S '
            - ' /C '
            - '{{'
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: selection and selection_args and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - ParentCommandLine
    - CurrentDirectory
    - User
    - LogonId
falsepositives:
    - Legitimate Windows shell or COM infrastructure operations triggered by Windows Explorer during COM object verification.
level: high
tags:
    - attack.defense-evasion
    - attack.t1218.012
    - analytic.an0118
    - detection.det0042
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Legitimate Windows Explorer COM Verification
  * The Issue: Windows Explorer itself calls verclsid.exe to verify COM objects when rendering shell namespaces, during drag-and-drop, or when launching context menu handlers. This generates legitimate noise when the parent is explorer.exe.
  * The Fix: Filter alert cases where the parent process is explorer.exe and the CLSID is from a known Windows system registration path. Focus alerting on verclsid.exe spawned by unusual parents (e.g. wscript.exe, cmd.exe, mshta.exe, or Office apps).

* Problem 2: Remote Scriptlet Fetch Not Directly Attributed
  * The Issue: When verclsid.exe fetches a remote SCT scriptlet, the process creation event shows the verclsid.exe launch, but the actual malicious payload execution may happen inside scrobj.dll loaded in-process. The network request may appear as a normal HTTP GET from verclsid.exe.
  * The Fix: Correlate Sysmon Event ID 3 (network connections) from verclsid.exe to external, non-Microsoft IP addresses or domains, especially when paired with CLSID arguments in the process creation event.

* Problem 3: CLSID Registered in HKCU (User Hive)
  * The Issue: Adversaries may register a malicious COM object in the current user's registry hive (HKCU\SOFTWARE\Classes\CLSID\) without requiring administrative privileges, making registry-based detection require monitoring of user-writable hives specifically.
  * The Fix: Monitor Sysmon Registry Event IDs 12/13 for new CLSID entries being written to HKCU\SOFTWARE\Classes\CLSID\, particularly by command shells or scripting engines, followed shortly by verclsid.exe execution referencing the same CLSID.
