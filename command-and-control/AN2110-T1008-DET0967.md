### 1. Technique Breakdown: T1008

* What it is: Fallback Channels. Adversaries may deploy secondary or redundant command and control (C2) channels to preserve system access in the event that primary communication pathways are discovered and severed by defender response actions. This commonly involves running local proxy or network tunneling daemons that tunnel traffic through alternative ports or protocols (e.g., Tor or proxy-over-DNS).
* Log Source Requirements:
  * Sysmon Process Creation (Event ID 1) to audit C2 proxy binaries and socks tunnel wrappers.
* Coverage Check:
  * HIDS (Sysmon): YES. Spawning fallback tools or proxies triggers process creation logging.
  * NIDS (Zeek/Suricata): PARTIAL. Network tools capture Tor handshake packets or DNS tunneling, but endpoint rules provide context on which local process initiated the channel.
* Log Sources Covered:
  * Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
  * None.

### 2. Custom Sigma Rule

The following rule monitors the execution of common proxy agents, Tor daemons, or tunneling utilities running with CLI flags that establish fallback communication paths.

```yaml
title: Redundant Fallback Channel Proxy Execution (AN2110)
id: d4e5f6a7-b8c9-4d0e-9f0a-1b2c3d4e5f80
status: experimental
description: "Detects the execution of Tor daemons, tunneling clients, or socks proxy wrappers configured with fallback command-line parameters (e.g., configuring proxy bypasses or redundant routing) to establish secondary command and control paths."
author: Krishna Gupta
date: 2026-07-01
logsource:
    category: process_creation
    product: windows
detection:
    selection_anomalous_images:
        Image|endswith:
            - '\tor.exe'
            - '\dnscrypt-proxy.exe'
            - '\frpc.exe'
            - '\chisel.exe'
    selection_anomalous_ofn:
        OriginalFileName:
            - 'tor.exe'
            - 'dnscrypt-proxy.exe'
            - 'frpc.exe'
            - 'chisel.exe'
    selection_plink_image:
        Image|endswith:
            - '\plink.exe'
    selection_plink_ofn:
        OriginalFileName:
            - 'plink.exe'
    selection_plink_cli:
        CommandLine|contains:
            - ' -R '
            - ' -L '
            - ' -D '
            - ' -socks '
            - ' -N '
    filter_installer:
        ParentImage|endswith:
            - '\msiexec.exe'
            - '\setup.exe'
    condition: (selection_anomalous_images or selection_anomalous_ofn or ((selection_plink_image or selection_plink_ofn) and selection_plink_cli)) and not filter_installer
fields:
    - Image
    - OriginalFileName
    - CommandLine
    - ParentImage
    - User
falsepositives:
    - IT administrators using SSH/Plink or Chisel for legitimate remote support tunnels.
    - Security tools performing vulnerability scans with custom tunneling binaries.
level: high
tags:
    - attack.command-and-control
    - attack.t1008
    - analytic.an2110
    - detection.det0967
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Inline C# or Python script C2 fallback
  * The Issue: If the fallback channel is built directly into memory (e.g., via a PowerShell script block executing `System.Net.WebClient` or a custom python agent), no external binary like `tor.exe` or `chisel.exe` is spawned.
  * The Fix: Implement script block logging filters to inspect remote connection logic, and monitor network logs for anomalous HTTPS beacons to secondary hostnames.
* Problem 2: Port forwarding via standard SSH/RDP
  * The Issue: Attackers using standard admin tools for tunnels might match basic proxy parameters (like `-L` or `-R`).
  * The Fix: Scrutinize the parent-child process tree. For example, `plink.exe` spawned from a user temp folder or CMD is highly anomalous compared to standard administrative shell hosts.
* Problem 3: Public VPN client usage
  * The Issue: Legitimate VPN clients use parameters like `tunnel` or `socks` and trigger false alarms.
  * The Fix: Whitelist standard enterprise VPN executables by hash or signer certificate.
