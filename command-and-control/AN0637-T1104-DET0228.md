### 1. Technique Breakdown: T1104

* What it is: Multi-Stage Channels. Adversaries use multiple command and control channels to segment their activity. A first-stage channel (typically a script, HTA, or light loader) connects to a remote server to download secondary tooling. Once executed, the second-stage process (often a more robust RAT or beacon) establishes outbound connections to a completely different, unrelated destination. This isolates command infrastructure and complicates analysis.
* Log Source Requirements: Host process creation and command line logs (Sysmon Event ID 1 / Windows Security Event ID 4688) and Network Connection logs (Sysmon Event ID 3).
* Coverage Check:
    * HIDS (Sysmon + Windows Defender): YES. Sysmon Event ID 1 captures process creation. Event ID 3 logs outbound network connections.
    * Windows Security Logs: PARTIAL. Security logs EID 4688 captures command lines if enabled.
* Log Sources Covered:
    - Sysmon Event ID 3 (network_connection)
    - Sysmon Event ID 1 (process_creation)
* Log Sources Missing / Unused:
    - None.

### 2. Custom Sigma Rule

The detection logic is split into two rules targeting network connections and process spawning contexts separately.

Rule 1 of 2: Multi-Stage C2 Channel Process spawning with Network Connection (Network Connection)
```yaml
title: Multi-Stage C2 Channel Process spawning with Network Connection (AN0637-A)
id: d9279647-6486-4fc5-9acc-a2408d186487
status: experimental
description: Detects process creation patterns typical of multi-stage C2 channels, where a scripting host (stage 1) spawns an unexpected child process (stage 2) that immediately initiates outbound network connections.
author: Krishna Gupta
date: 2026-06-07
logsource:
    category: network_connection
    product: windows
    # Relies on Sysmon Event ID 3
detection:
    selection_parent:
        ParentImage|endswith:
            - '\powershell.exe'
            - '\pwsh.exe'
            - '\wscript.exe'
            - '\cscript.exe'
            - '\mshta.exe'
            - '\hh.exe'
    selection_child_network:
        # The child process itself initiates network activity
        Image|endswith:
            - '\cmd.exe'
            - '\rundll32.exe'
            - '\regsvr32.exe'
            - '\schtasks.exe'
            - '\certutil.exe'
            - '\installutil.exe'
            - '\cvtres.exe'
    condition: selection_parent and selection_child_network
fields:
    - Image
    - ParentImage
    - CommandLine
    - User
    - DestinationHostname
    - DestinationIp
    - DestinationPort
    - Initiated
    - SourceIp
    - SourcePort
falsepositives:
    - Administrative orchestration scripts (e.g. software deployment, patch installation) that execute helper binaries to perform network checks.
level: high
tags:
    - attack.command-and-control
    - attack.t1104
    - analytic.an0637
    - detection.det0228
```

### 3. Blind Spots & Tuning (The "Problems")

* Problem 1: Process Injection Evasions
  * The Issue: Instead of spawning a child process to initiate the second-stage connection, stage-1 loaders often perform process injection (e.g. process hollowing or DLL injection) into a running, trusted Windows process (like explorer.exe or svchost.exe). In this case, network connections appear under the injected process, bypassing parent-child process checks.
  * The Fix: Enable and monitor Sysmon Event ID 8 (CreateRemoteThread) and Sysmon Event ID 10 (ProcessAccess) targeting system processes, and correlate process injection logs with immediate network socket activity.

* Problem 2: Use of Legitimate LOLBins for Stage 2
  * The Issue: Attackers can use built-in Windows applications like msiexec.exe or mobsync.exe as the second-stage network interface, which may produce heavy false alerts due to administrative updates.
  * The Fix: Audit and whitelist standard update processes by comparing certificate digital signatures, whitelisting corporate domain controllers/update servers, and alerting on unsigned binaries.

* Problem 3: Script-Only Multi-Stage Operations
  * The Issue: The loader can run stage-2 entirely inside the same process space (e.g., executing a second script block in the same PowerShell window), which does not generate parent-child process logs.
  * The Fix: Enable PowerShell Script Block Logging (Event ID 4104) to audit scripts executing in memory, and detect script code containing network connection commands (e.g., Net.WebClient or Invoke-WebRequest).
